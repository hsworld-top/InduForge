# 开发约定和规则

## 文档创建规则

**重要：在创建或修改文档文件之前，必须先向用户确认。**

文档文件包括但不限于：
- README.md 文件
- 任何 `.md` 文档文件
- API 文档
- 设计文档
- 架构文档
- 用户手册
- 开发指南

### 文档输出目录

**所有项目文档必须输出到 `docs/` 目录下。**

目录结构：
```
docs/
├── backend/          # 后端相关文档
├── datacenter/       # 数据中心文档
├── designer/         # 设计器文档
├── api/              # API 文档
├── guides/           # 使用指南
└── architecture/     # 架构设计文档
```

例外情况：
- 根目录的 `README.md`（项目主文档）
- 各子项目根目录的 `README.md`（如 `dev_core/README.md`）
- `.kiro/steering/` 目录下的 steering 规则文件

### 确认流程

1. 当用户请求创建文档时，先询问：
   - 文档的目标受众是谁？
   - 文档应该包含哪些具体内容？
   - 文档的详细程度（简要概述 vs 详细说明）
   - 文档的语言（中文/英文）
   - 文档应该放在 `docs/` 的哪个子目录下？

2. 获得用户明确确认后，再创建文档

3. 例外情况：
   - 用户明确指定了文档的具体内容和格式
   - 用户要求"直接创建"或"不需要确认"

### 示例

❌ 错误做法：
```
用户：帮我写个 API 文档
AI：好的，我来创建 api-docs.md... [直接创建到根目录]
```

✅ 正确做法：
```
用户：帮我写个 API 文档
AI：好的，在创建 API 文档之前，我想确认几点：
1. 这个文档是给谁看的？（前端开发者/后端开发者/第三方集成）
2. 需要包含哪些 API？（全部/特定模块）
3. 详细程度如何？
4. 使用中文还是英文？
5. 我会将文档创建到 docs/api/ 目录下，文件名是？
```

## Git 提交规范

遵循 Conventional Commits 规范：

- `feat`: 新功能
- `fix`: 修复 bug
- `docs`: 文档更新
- `style`: 代码格式调整（不影响功能）
- `refactor`: 重构
- `test`: 测试相关
- `chore`: 构建/工具链相关
- `perf`: 性能优化

## 代码注释规范

### 后端（JavaScript/Node.js）
- 使用 JSDoc 风格注释
- 函数必须包含参数说明和返回值说明
- 复杂业务逻辑必须添加注释

### 前端（Vue 3）
- 组件必须包含功能说明注释
- 复杂的 computed 和 watch 需要注释
- Props 和 Emits 使用 TypeScript 类型或详细注释

## 错误处理规范

### 后端
- 使用 `AppError` 类抛出业务错误
- 错误码统一在 `constants/errorCodes.js` 定义
- 所有 API 返回统一的错误格式

### 前端
- 使用 Element Plus 的 `ElMessage` 显示错误
- API 错误在拦截器中统一处理
- 用户友好的错误提示信息

## 数据库操作规范

- 使用 Sequelize 事务处理关联操作
- 避免 N+1 查询问题，使用 `include` 预加载
- 敏感数据（密码）必须加密存储
- 使用参数化查询防止 SQL 注入

## API 设计规范

- RESTful 风格
- 统一的响应格式（使用 `response.js` 工具）
- 版本控制（`/api/v1/`）
- 使用中间件进行认证和权限验证
- 所有接口必须有 Swagger 文档注释
