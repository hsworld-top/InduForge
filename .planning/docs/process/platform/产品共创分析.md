# 产品共创分析

## 一、平台定位共创结论

### 当前已实现

- 这是一个面向工业场景的低代码平台，具备工程管理、设计、数据配置、节点控制主干。

### 共创后建议目标

- 将平台定义为“工业应用低代码交付平台”，不是单纯页面设计器。
- 其核心价值不只是设计页面，而是完成从设计、数据建模、发布、部署到节点运行的闭环交付。

### 待确认

- 本期主要目标是“内部试点可用”还是“对外可售卖产品原型”。

## 二、目标用户

### 当前可识别用户

- 平台管理员
- 系统管理员
- 工程管理员
- 运维管理员
- 工程开发人员

### 建议补全用户画像

- 方案架构师：负责工程模板和交付规范
- 可视化开发工程师：负责页面搭建与基础逻辑配置
- 数据集成工程师：负责连接、查询、Tag、数据点设计
- 运维工程师：负责节点注册、部署、回滚、健康巡检
- 现场使用方：最终在 Runtime 页面中查看和操作应用

## 三、核心问题

### 当前已解决的问题

- 多模块分工基本清楚
- 节点控制与平台运维主干已经建立
- 数据接入与设计配置已经可进行

### 当前未解决的问题

- 工程无法稳定运行在真实 Runtime 中
- Designer 输出与 Runtime 消费的契约不稳定
- DataCenter 处理层还未形成
- 旧文档会误导后续 AI 开发方向

## 四、关键使用场景

### 场景1：工程从设计到运行

- 开发人员创建工程
- 设计页面与变量
- 配置数据点与查询
- 发布版本
- 运维选择节点部署
- Runtime 页面运行并展示数据

### 场景2：节点变更与回滚

- 运维查看节点状态
- 下发启动/停止/重启/回滚命令
- 查看失败原因和命令时间线

### 场景3：模板化持续交付

- 后续可以扩展到工程模板、行业模板和标准组件包

## 五、模块边界共创结论

### 当前已实现

- `dev_core` 负责平台编排
- `dev_ide` 负责管理工作台
- `designer` 负责设计态
- `datacenter` 负责数据接入态
- `node_agent` 负责节点控制态

### 建议目标

- RuntimeEngine 负责运行态，不再由其他模块混杂承担
- `designer` 输出静态/半静态工程结构
- `datacenter` 输出数据语义结构
- `dev_core` 输出可部署制品与命令编排
- `node_agent` 只负责启动和监控运行时

### 待确认

- RuntimeEngine 是否采用独立前端 + 独立服务形式，还是最小前后端混合运行形态

## 六、当前阶段合理目标

### 推荐方案

本期只追求 Runtime MVP：

- 支持白名单组件
- 支持基础数据绑定
- 支持基础路由
- 支持健康与状态上报
- 打通发布部署闭环

### 备选方案

#### 方案A：先做完整 Runtime

优点：一步到位
缺点：周期长、风险高、会拖垮当前多模块同步节奏

#### 方案B：先做 Runtime MVP

优点：可落地、能快速验证全链路、便于后续迭代
缺点：首版能力有限

### 推荐原因

- 当前最大的风险不是功能不够多，而是闭环不成立。
- Runtime MVP 能最早验证平台作为“交付系统”而不是“设计系统”的价值。

## 七、非功能要求建议

### 建议目标

- 可观测：节点、部署、命令、运行时状态必须可追踪
- 可演进：Schema、IFP、运行时协议都需要版本化
- 可拆分：每个模块都必须能形成独立 AI 开发上下文
- 可测试：关键主链路至少有 smoke 级自动验证

## 八、演进路径建议

### 阶段1

- Runtime MVP
- 发布制品 V1.1
- 契约冻结

### 阶段2

- DataCenter 处理层一期
- 管理端产品化收口
- 测试补齐

### 阶段3

- 运行时权限
- 多端支持
- 高级动作与主题系统

## 九、产品缺口结论

### 当前已实现

- 管理主干、数据接入主干、设计主干、节点控制主干

### 共创后建议目标

- 运行时闭环、契约冻结、产品化交付

### 待确认

- 是否接受“本期不做高级能力，只做闭环 MVP”的范围约束
