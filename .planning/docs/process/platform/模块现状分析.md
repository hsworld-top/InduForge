# 模块现状分析

## 一、平台总体现状

### 当前已实现

- `dev_core` 已具备用户、租户、工程、数据连接、设计页面、发布、部署、节点、命令链路等核心后端能力。
- `dev_ide` 已具备主工作台、运维中心、工程管理、用户管理、系统设置、国际化等主界面能力。
- `datacenter` 已具备关系库、SQL 查询、MQTT、数据点主干能力。
- `designer` 已具备 editor-core、页面锁、变量、绑定、设计态 UI 与预览主干。
- `runtime/node_agent` 与 `runtime/node_agent_front` 已具备节点控制面能力。

### 当前未完成

- `runtime/engine_core`、`runtime/engine_data`、`runtime/engine_front` 为空目录。
- 真正的 RuntimeEngine 业务面尚未落地。
- 平台主链路的“发布后真实运行”仍缺闭环。
- 前端自动化测试与端到端验证明显不足。

## 二、模块分项分析

## 2.1 dev_core

### 当前职责

- 平台核心后端
- 工程与页面主数据管理
- 发布版本管理
- 节点注册审批与状态汇总
- 部署、回滚、命令编排

### 当前已实现能力

- `v1` 路由已覆盖认证、租户、用户、角色、项目、日志、设计、数据、节点、发布、部署。
- 模型层已覆盖 `Project`、`DesignPage`、`DataPoint`、`Deployment`、`Node`、`NodeDeployment`、`NodeCommand` 等核心实体。
- 发布服务能收集页面、连接、查询、数据点并生成基础 IFP。
- 部署服务能处理 DEV/RELEASE、启动/停止/重启、撤销部署、回滚。
- 节点服务能处理注册、审批、心跳、离线检测、部署状态回调、命令超时重试。

### 当前边界

- 更偏平台编排层，不应承担 RuntimeEngine 具体渲染和业务逻辑。
- 当前导入导出能力存在，但仍不等于正式制品标准。

### 当前依赖

- 依赖 `designer` 输出页面结构。
- 依赖 `datacenter` 提供连接/查询/数据点。
- 依赖 `node_agent` 消费部署命令并回传状态。

### 当前问题

- `publishService` 仍偏基础打包器，资产打包与运行时元数据不足。
- 设计器导出结构与运行时契约未冻结。
- 测试重点集中在 DSL，发布/部署链路自动化不足。

### 与历史文档差异

- 文档中的发布流水线成熟度高于实际实现。
- 实际部署与节点能力比旧文档更完整。

## 2.2 dev_ide

### 当前职责

- 平台统一工作台
- 工程入口与运维监控入口
- 用户与系统配置入口

### 当前已实现能力

- 标签化 Dashboard 工作台
- 工程管理、用户管理、系统日志、系统设置
- 运维中心节点视图、审批、命令时间线、失败详情、日志查看
- 中英双语主干
- 顶部品牌、主题切换、个人资料弹窗入口

### 当前边界

- 负责管理体验，不负责运行时业务渲染。
- 是产品收口层，不应承载 RuntimeEngine 逻辑。

### 当前依赖

- 强依赖 `dev_core` 接口稳定性。
- 依赖 `runtime` 输出节点状态、部署状态、失败原因。

### 当前问题

- 仍有品牌、欢迎语、头像、设置入口等产品化细节待收口。
- 文档严重落后于代码。
- 自动化测试不足。

### 与历史文档差异

- 文档仍称运维待开发，但代码已成熟。

## 2.3 datacenter

### 当前职责

- 数据连接与数据建模中心
- 数据点统一抽象层

### 当前已实现能力

- 关系库连接管理
- SQL 查询编辑与保存
- MQTT 连接、订阅、Tag 管理、消息查看
- 数据点列表与主干能力

### 当前边界

- 当前仍以数据接入层为主，处理层只停留在规划。

### 当前依赖

- 依赖 `dev_core` 存储与 API。
- 被 `designer` 和后续 Runtime 消费。

### 当前问题

- 计算单元与报警单元仍是占位。
- 自动发现与批量导入尚未闭环。
- 测试不足。

### 与历史文档差异

- 数据中心总览总体可信，但规划文档多于实现文档。

## 2.4 designer

### 当前职责

- 工程页面设计器
- 负责页面结构、绑定、变量、入口配置输出

### 当前已实现能力

- editor-core：DocumentModel、History、Command、Selection、PageLock
- editor-store：页面、变量、入口、保存、导出主干
- 大量设计态 UI：左侧组件/页面/资源面板，右侧属性/绑定/事件面板，顶栏与预览
- 数据层：ExpressionEngine、DataService、VarsStore、DiagnosticsStore

### 当前边界

- 当前是“设计态能力强、运行态契约弱”。
- 不应再无边界扩展高级功能，需优先收敛输出结构。

### 当前依赖

- 依赖 `datacenter` 数据点与查询模型。
- 依赖 `dev_core` 保存与发布。
- 最终依赖 `runtime` 消费输出结构。

### 当前问题

- refactor 文档中的目标态远超实际运行闭环。
- Schema 与 Runtime 契约尚未冻结。
- 测试不足。

### 与历史文档差异

- M1 基本可信，M2+ 大部分仍是目标设计。

## 2.5 runtime/node_agent 与 node_agent_front

### 当前职责

- 节点控制面
- 接收中心命令并管理 Runtime 进程

### 当前已实现能力

- NodeAgent Go 后端
- 本地/远程运维双模式前端
- 中心绑定、审批轮询、配置保存、健康检查、静态资源嵌入
- 执行器、状态机、存储、日志、路由与 API
- 多个 `*_test.go` 测试文件

### 当前边界

- 当前是控制面，不是 RuntimeEngine 本体。

### 当前依赖

- 依赖 `dev_core` 提供中心 API 与制品下载地址。
- 依赖未来 RuntimeEngine 作为被控进程。

### 当前问题

- 控制面较完整，但真正运行工程的引擎不存在。
- 前端测试不足。
- 嵌入式前端构建来源需后续统一。

### 与历史文档差异

- 文档基本方向正确，但少量实现细节已过时。

## 2.6 runtime/engine_*

### 当前职责

- 设计上应承担运行时业务面。

### 当前已实现能力

- 无。

### 当前边界

- 目前仅为预留目录。

### 当前问题

- 这是当前平台最关键的缺口。

### 与历史文档差异

- 旧文档将其描述为规划成熟，但代码尚未开始。

## 三、总体判断

### 当前已实现

- 平台管理主干已成型。
- 运维控制面已成型。
- 数据接入主干已成型。
- 设计器编辑内核已具备。

### 建议目标

- 下一阶段必须聚焦 RuntimeEngine MVP 与发布闭环。

### 待确认

- 本期是否将 RuntimeEngine 作为绝对一号目标。
- 本期是否限制 Designer 只对白名单组件承诺运行时支持。
