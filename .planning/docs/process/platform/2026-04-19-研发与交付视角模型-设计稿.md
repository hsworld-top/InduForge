# 研发与交付视角模型设计稿

> 当前文件属于过程设计稿，用于收口 `docs/研发与交付视角模型.md` 的定位、结构与写法边界，不作为正式规范源。

## 1. 背景

在本轮正式文档治理中，`docs/` 已被明确限定为最终态、稳定口径、正式契约与模块说明的承载空间，`.planning/` 则负责阶段计划、过程分析与历史决策。

当前平台级正式文档已经完成以下收口：

- `docs/产品定义.md`：明确最终态产品分层与一级模块地图。
- `docs/高层设计.md`：明确共享运行内核、双数据服务、节点侧网关与运行引擎结构。
- `docs/详细设计.md`：明确平台对象、运行对象与关键机制。

但治理类正式文档仍存在空缺，尤其缺少一份能够从产品经理、架构师、研发经理、开发主管、测试经理等视角统一审视整套正式文档与系统交付边界的文档。由于当前项目主要由单开发者推进，这份文档不应写成多人协作制度，而应写成“单开发者如何以多角色视角审视系统和文档”的长期方法模型。

## 2. 文档定位

正式文档名称确定为：`docs/研发与交付视角模型.md`

该文档的定位是：

- 说明单开发者长期维护 InduForge 时，需要同时使用哪些角色视角审视系统。
- 说明正式文档体系分别应承接哪些角色问题。
- 说明平台分层、模块与关键交付件应如何被这些角色视角共同检查。
- 说明一套稳定的研发与交付闭环，而不是阶段计划、执行清单或多人协作流程。

该文档不承担以下职责：

- 不写当前阶段优先级和里程碑。
- 不写任务拆分与计划推进。
- 不写审批流、协作流、多人分工制度。
- 不重复替代 `产品定义`、`高层设计`、`详细设计`、`测试与质量策略` 的正文内容。

## 3. 选定方案

本次设计采用混合型结构。

### 3.1 未采用方案

- 按角色展开：
  角色感强，但容易在多个章节中重复描述同一模块与同一文档。
- 按文档体系展开：
  适合作为写作指南，但对模块与交付件的约束不够直观。

### 3.2 最终采用方案

采用“文档体系 + 模块层级 + 交付闭环 + 角色矩阵”的混合结构：

- 前半部分先说明多角色视角各自关心什么。
- 中间部分说明正式文档体系怎样承接这些视角。
- 后半部分说明平台分层、模块与关键交付件怎样被这些视角共同检查。
- 末尾使用角色视角矩阵做总览，方便快速发现缺口。

该方案适合当前项目，因为它同时满足两个目标：

- 为正式文档重写提供统一写法标准。
- 为后续模块 README、测试策略和契约文档提供统一审视框架。

## 4. 正式文档目标结构

正式文档 `docs/研发与交付视角模型.md` 采用以下目录结构：

1. 文档定位
2. 多角色视角总览
3. 正式文档体系如何承接这些视角
4. 平台分层与模块如何被多角色共同审视
5. 关键交付件视角
6. 单开发者的研发与交付闭环
7. 角色视角矩阵
8. 文档关系

## 5. 各章节写法约束

### 5.1 文档定位

必须写清：

- 这份文档不是团队协作规范。
- 这份文档不是阶段计划。
- 这份文档用于指导单开发者以多角色视角维护正式文档与系统交付。

### 5.2 多角色视角总览

固定承接以下五个视角：

- 产品经理视角
- 架构师视角
- 研发经理视角
- 开发主管视角
- 测试经理视角

本章只写每个视角最关心的问题，不写模块细节。

### 5.3 正式文档体系如何承接这些视角

必须覆盖以下正式文档类型：

- `产品定义`
- `高层设计`
- `详细设计`
- `测试与质量策略`
- 模块 `README`
- `contracts`

每类文档都要回答三件事：

- 主要承接哪些角色问题。
- 不该写什么。
- 与其他正式文档如何分工。

### 5.4 平台分层与模块如何被多角色共同审视

按平台层级组织，再在层内点模块：

- 设计层：`designer`
- 平台数据层：`datacenter`、`data_service`
- 控制与管理层：`dev_core`、`dev_ide`
- 共享运行内核层
- 运行与节点层：`runtime_gateway`、`runtime_engine`、`runtime_data_service`、`runtime/node_agent`、`runtime/node_agent_front`

每层都要从四个角度简述：

- 产品价值
- 架构边界
- 研发与实现焦点
- 质量风险

这一章不重复模块职责清单，职责清单仍以 `产品定义`、`高层设计`、`详细设计` 为准。

### 5.5 关键交付件视角

必须抽出长期治理所需的关键交付件：

- 工程定义
- 数据域定义
- 发布制品
- 部署计划
- 节点运行单元
- 正式契约
- 模块说明文档

本章要说明这些交付件分别需要被哪些视角检查，以及检查重点是什么。

### 5.6 单开发者的研发与交付闭环

本章只写长期稳定的方法论，不写当前阶段顺序：

1. 收产品边界
2. 定架构边界
3. 落详细设计
4. 补模块说明与契约
5. 做测试与质量收口
6. 统一正式文档入口

### 5.7 角色视角矩阵

使用总表做快速检查：

- 横向：产品经理、架构师、研发经理、开发主管、测试经理
- 纵向：正式文档、模块层级、关键交付件

矩阵的目标是帮助快速发现是否存在“某个对象无人从某种视角约束”的缺口。

### 5.8 文档关系

必须明确：

- 与 `产品定义` 的关系：定义最终态产品边界。
- 与 `高层设计` 的关系：定义系统架构与模块连接方式。
- 与 `详细设计` 的关系：定义关键对象与关键机制。
- 与 `测试与质量策略` 的关系：定义质量目标与验证分层。
- 与模块 `README` 的关系：定义模块级正式说明落点。
- 与 `.planning/` 的关系：`.planning/` 只承接当前阶段与过程材料，不承接该文档的长期正式角色。

## 6. 与当前平台主口径的对齐要求

正式文档落地时，必须与以下已确认口径保持一致：

- `dev_core` 负责租户、用户、平台角色、`dev_ide` 接口、`designer` 设计中心接口、工程管理、发布部署编排。
- `datacenter` 是平台数据工作台前端。
- `data_service` 是平台侧与开发态数据域服务。
- `runtime_data_service` 是工程级运行态数据引擎组，多实例用于负载均衡。
- `runtime_engine` 是页面运行引擎。
- 开发态预览与运行态共享同一套运行内核，但接入不同环境的数据服务。
- 节点侧采用 `nginx + runtime_gateway + runtime_engine + runtime_data_service 组 + node_agent` 的结构。
