# 产品决策确认版（归档）

> 本文档已从 `docs/` 降级到过程文档区，作为历史阶段决策记录保留。
> 当前正式口径以 `docs/产品定义.md` 及后续正式设计文档为准。

## 1. 文档定位
- 本文档记录当前阶段已经确认的产品方向与架构决策。
- 本文档优先级高于历史规划性描述，用于约束后续任务拆分和模块下发。

## 2. 已确认决策
### 2.1 主线优先级
- 当前阶段第一目标不是独立运行态部署，而是开发态预览。
- 运行态部署、NodeAgent 托管、完整部署闭环后置到下一阶段。

### 2.2 架构策略
- 采用“共享渲染内核 + 开发态预览宿主 + 运行态宿主后置”的方案。
- 开发态预览与未来运行态应尽量复用同一套渲染解释与绑定求值能力。

### 2.3 Schema 策略
- 预览直接消费发布态 Schema。
- 不再为预览单独设计一套独立结构。
- 发布态严格裁剪，不携带编辑器内部状态字段。

### 2.4 数据策略
- 预览阶段先直连现有 `dev_core/datacenter` 接口。
- 预览阶段支持三类数据来源：
  - 真实数据
  - Mock 数据
  - 降级占位

### 2.5 组件范围
- 首批组件白名单固定为：
  - `text`
  - `image`
  - `button`
  - `table`
  - `container`

### 2.6 事件范围
- 预览阶段只支持基础交互，不进入完整动作系统。

### 2.7 后置范围
- `runtime_node_agent`
- 独立运行态宿主
- 完整部署链路
- 复杂运维协议

## 3. 对模块优先级的影响
### 提前
- `designer`
- 共享渲染内核（由 `runtime_engine` 先承接）
- `dev_core` 预览数据和工程聚合接口

### 后置
- `runtime_node_agent`
- 独立 Runtime 宿主
- 运维闭环增强

## 4. 设计原则
- 先统一解释和渲染，再做托管和部署。
- 先让设计器内可预览，再做节点独立运行。
- 不允许为了预览方便而发明与发布态不兼容的新结构。

## 5. 后续执行要求
- 模块任务拆分必须以本决策为准。
- 如后续重新提升运行态优先级，必须先更新本决策文档。
