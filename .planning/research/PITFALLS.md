# PITFALLS

## 1. 接口契约分叉
- 现象：部分路由直接 `res.json`，部分走统一响应封装。
- 预警信号：前端同类接口出现多套错误处理分支；联调文档频繁补丁。
- 预防策略：建立统一响应适配层，分批改造并补充契约测试。
- 建议处理阶段：Phase 1。

## 2. 发布产物契约不完整
- 现象：manifest 或 assets 缺项，部署成功但运行异常。
- 预警信号：节点启动后页面/资源缺失，回滚频率升高。
- 预防策略：发布前 schema+manifest 校验，失败即阻断发布。
- 建议处理阶段：Phase 2。

## 3. 运行态可观测断层
- 现象：NodeAgent 能执行但平台看不到稳定状态演进。
- 预警信号：故障排查依赖人工登录节点，告警滞后。
- 预防策略：落实 `/health` 与 `/status` 契约，统一状态映射与展示。
- 建议处理阶段：Phase 3。

## 4. 开发环境鉴权旁路外溢
- 现象：开发便利逻辑掩盖真实权限问题。
- 预警信号：测试环境出现“本地可用、线上拒绝”或越权问题。
- 预防策略：旁路显式开关化、默认关闭，并增加权限回归用例。
- 建议处理阶段：Phase 4。

## 5. 运维脚本与执行行为不一致
- 现象：Makefile 目标、日志策略与文档描述不一致。
- 预警信号：交付脚本偶发失败，问题无法复盘。
- 预防策略：清理重复目标、统一日志追加策略、补 smoke test。
- 建议处理阶段：Phase 5。

## 结论
本项目的主要风险不是“功能不会做”，而是“跨模块边界不一致”。路线图应优先消除边界不确定性。
