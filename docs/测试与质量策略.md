# 测试与质量策略

## 1. 文档定位

本文档定义 InduForge 的最终态测试分层、质量目标、发布前最低验证要求，以及当前仓库已经具备的测试基线与后续缺口。

本文档的重点不是记录某一阶段的测试计划，而是定义平台长期需要如何被验证，确保正式文档、系统架构、关键交付件和节点运行链路都具备可验证性与可回归性。

## 2. 质量目标

InduForge 的长期质量目标包括：

- 核心业务链路可用  
  设计、数据、发布、部署、运行、运维等主链路必须存在稳定验证方式。

- 模块边界稳定  
  `dev_core`、`data_service`、`runtime_data_service`、`runtime_engine`、`node_agent` 等模块之间的职责边界不能靠隐式实现维持。

- 契约持续可验证  
  正式契约、发布态结构、节点协议和运行状态协议必须能够通过测试或验证流程发现漂移。

- 预览与运行行为一致  
  开发态预览与运行态必须共享核心运行语义，避免同一页面在两种环境下出现长期分叉。

- 发布与部署可回归  
  制品生成、部署计划下发、节点落地、运行单元启动、状态回传必须具备稳定回归能力。

## 3. 测试分层

InduForge 的长期测试分层采用以下结构：

### 3.1 单元测试

用于验证单一函数、单一对象、单一规则或局部状态转换是否正确，重点覆盖：

- 纯工具函数
- 领域模型校验
- 绑定、解析、转换、归一化逻辑
- 节点侧局部执行与状态处理规则

### 3.2 组件与交互测试

用于验证前端组件、页面局部交互、状态编排和局部 UI 行为，重点覆盖：

- `designer` 组件面板、页面树、属性编辑器、预览入口
- `dev_ide` 平台管理核心界面
- `datacenter` 数据工作台关键页面
- `node_agent_front` 本地管理关键页面

### 3.3 服务与集成测试

用于验证单模块内跨对象、跨仓储、跨接口的业务能力，重点覆盖：

- `dev_core` 的服务层、发布部署编排、节点控制接口
- `data_service` 的连接、查询、数据点、协议、计算、预览会话
- `runtime/node_agent` 的执行器、编排器、存储与 API
- 节点运行单元关键状态切换

### 3.4 契约测试

用于验证模块之间必须共同遵守的结构和接口不会漂移，重点覆盖：

- 设计器发布态 Schema
- IFP Manifest
- NodeAgent 启动协议
- Runtime 健康状态协议
- 开发态与运行态共享的数据域契约

### 3.5 端到端与冒烟测试

用于验证真实主链路是否可用，重点覆盖：

- 设计到预览
- 数据配置到数据消费
- 发布制品生成到部署下发
- 节点运行单元启动到状态回传
- 本地运维与平台运维的关键入口

### 3.6 部署与运行验证

用于验证节点侧运行组合、切换、恢复和健康检查行为，重点覆盖：

- `nginx -> runtime_gateway -> runtime_engine` 访问链路
- `runtime_engine -> runtime_data_service` 数据访问链路
- `node_agent` 的托管、探活、摘流、加流与状态回传

## 4. 模块质量责任

### 4.1 设计层：`designer`

- 必须具备单元测试和组件/交互测试。
- 必须验证页面定义、组件编排、属性配置、绑定配置和预览接入行为。
- 质量风险集中在发布态结构漂移、预览与运行语义不一致、局部交互回归。

### 4.2 平台数据层：`datacenter`、`data_service`

- `datacenter` 至少需要关键页面冒烟测试和数据工作台主交互验证。
- `data_service` 必须具备服务与集成测试，重点覆盖连接、查询、数据点、协议接入、计算和预览会话。
- 质量风险集中在开发态数据域与运行态数据域不一致、接口契约漂移、预览数据链路不稳定。

### 4.3 控制与管理层：`dev_core`、`dev_ide`

- `dev_core` 必须具备服务测试、接口测试和发布部署链路验证。
- `dev_ide` 至少需要关键管理入口、发布部署入口和节点视图的冒烟测试。
- 质量风险集中在工程管理与部署控制脱节、平台边界不清、节点状态展示与真实状态不一致。

### 4.4 共享运行内核与运行态组件

覆盖对象：共享运行内核、`runtime_gateway`、`runtime_engine`、`runtime_data_service`

- 必须验证共享运行内核在预览与运行态的行为一致性。
- `runtime_gateway` 必须验证项目级路由注册、切换和访问分发。
- `runtime_engine` 必须验证页面解释、运行上下文和数据访问接入。
- `runtime_data_service` 必须验证工程级数据引擎组、多实例负载和运行态数据接口。
- 质量风险集中在运行语义漂移、节点侧路由错误、数据引擎组不稳定和项目切换影响已有访问。

### 4.5 节点托管与本地运维：`runtime/node_agent`、`runtime/node_agent_front`

- `node_agent` 必须具备执行器、编排器、存储、API 和恢复逻辑测试。
- `node_agent_front` 至少需要节点初始化、绑定、项目状态查看和本地运维入口的冒烟测试。
- 质量风险集中在托管状态与真实运行状态不一致、恢复与回滚失败、节点本地信息缺乏可观测性。

## 5. 跨模块关键验收链路

InduForge 至少需要长期保持以下关键验收链路可验证：

### 5.1 设计到预览链路

验证 `designer` 页面定义是否能被共享运行内核正确解释，并通过平台侧 `data_service` 完成开发态预览。

### 5.2 数据配置到数据消费链路

验证 `datacenter` 中配置的数据域对象能否被 `data_service` 正确提供，并被设计态预览和运行态消费。

### 5.3 发布制品到部署下发链路

验证 `dev_core` 是否能正确聚合工程定义、数据快照与运行配置，生成制品并下发部署计划。

### 5.4 节点运行链路

验证节点侧是否能拉起 `runtime_gateway`、`runtime_engine` 和 `runtime_data_service` 组，并形成稳定访问路径。

### 5.5 状态回传与运维链路

验证 `node_agent` 的状态、健康信息和运行结果能否回到平台侧并被 `dev_ide` 或 `node_agent_front` 正确展示。

## 6. 质量门禁与发布前最低验证项

InduForge 的正式发布前最低验证项应遵循以下策略：

- 涉及变更的模块必须完成本模块最接近的测试类型验证。
- 涉及契约变更时，必须同步检查 `docs/contracts/` 与相关正式文档是否一致。
- 涉及设计态、预览态或发布态结构变更时，必须验证设计到预览链路。
- 涉及数据域变更时，必须验证开发态数据服务与运行态数据服务之间的数据连续性。
- 涉及节点侧运行逻辑变更时，必须验证部署、启动、健康检查、状态回传和访问切换行为。
- 涉及平台治理、工程管理或发布部署编排变更时，必须验证相关管理入口和主业务流程。

这里的质量门禁强调“必须验证哪些对象和链路”，而不是绑定固定覆盖率数字或固定命令阈值。

## 7. 当前基线与缺口

以下基线来源于当前仓库已有脚本与测试目录，反映的是当前现实，不等同于最终目标已全部达成。

| 模块/对象                  | 当前基线                                                               | 当前缺口                                         |
| -------------------------- | ---------------------------------------------------------------------- | ------------------------------------------------ |
| `designer`                 | 已有 `vitest` 测试、`typecheck`、构建入口                              | 缺少更明确的预览到运行一致性回归层               |
| `dev_core`                 | 已有 `jest` 测试入口                                                   | 需要继续补强发布部署、节点协同和契约回归         |
| `data_service`             | 已有 Go 单测与集成测试，覆盖连接、查询、数据点、协议、计算、预览会话等 | 需要继续强化与平台契约、运行态数据连续性的验证   |
| `runtime/node_agent`       | 已有 Go 测试、`make test`、`vet`、竞争检测等入口                       | 需要继续补齐运行组合、切换、恢复和状态回传主链路 |
| `dev_ide`                  | 已有自定义测试入口 `tests/run-tests.js`                                | 需要形成更稳定的正式测试分层与关键页面冒烟策略   |
| `datacenter`               | 具备构建与 lint 入口                                                   | 缺少正式自动化测试脚本与关键页面验证层           |
| `runtime/node_agent_front` | 具备构建入口                                                           | 缺少正式自动化测试脚本与本地运维页面冒烟层       |
