# 运维体系实现与验收

## 1. 用户模型与范围

运维管理面向两个角色：运维管理员负责物理节点、运行环境和基础服务；工程开发人员只在运维管理中选择运行环境执行工程部署，工程发布仍属于工程管理。界面只使用“物理节点、运行环境、基础服务、工程部署”等业务概念，不向最终用户暴露 K3s、Pod、容器或命名空间。

运行环境只有一种模型：一个环境可以关联一台或多台 Linux 标准运行节点。单节点只是该模型只有一个成员的特例，不再提供“单机 / 集群”两套入口。系统初始化时为租户自动建立不可删除的默认运行范围，并自动纳入中心节点和后续审批通过的 Linux 标准运行节点。只有一个范围时，运维入口直接显示运行概览且隐藏环境选择；只有存在多个范围时才显示范围切换器。Windows 节点仅承担采集，不加入运行环境，也不承载基础服务。

本阶段正式交付以下闭环：

- 中心 IDE/Nginx、控制面、中心数据库、缓存和对象存储运行在 `induforge-system`，并固定调度到中心节点；
- `induforge-centerctl` 在中心前端不可用时提供宿主命令行诊断和恢复入口；
- Linux 节点包离线携带固定版本的 K3s、基础服务镜像、NodeAgent、宿主运维进程及工程运行能力程序；
- 物理节点一次性接入、审批、心跳、资源监测、离线与恢复；
- 中心内置节点初始化唯一 K3s Server、外部 Linux 节点审批后加入为工作节点；
- 运行环境创建及节点关联；同一物理节点可被多个逻辑运行环境复用；
- 八项基础服务按单实例分布到一台或多台节点，持续回传真实状态并支持原分配修复；
- 运维事件记录环境、节点、运行底座和基础服务的重要状态变化。

工程按运行环境部署、基础服务主备 / 集群和 Windows 采集节点现场验收不属于本阶段完成项。前端为主备与集群模式保留置灰文案，但不得伪造任务或运行结果。

## 2. 节点包与版本基线

Linux 标准运行节点包可以安装在已具备 Docker 的服务器上，但 K3s 默认使用自身携带的 containerd，不使用 Docker Engine 的镜像库和容器列表。因此 `docker ps`、`docker images` 为空是正常现象；运维诊断使用安装数据目录中的 kubeconfig 和 containerd 配置，例如 `k3s kubectl --kubeconfig <数据目录>/server/cred/admin.kubeconfig get pods -A`、`k3s crictl --config <数据目录>/agent/etc/crictl.yaml ps -a` 和 `images`。K3s 使用包内固定二进制和离线镜像，不依赖公网安装脚本。当前版本基线为：

| 类别 | 固定版本 / 内容 |
| --- | --- |
| 运行底座 | K3s `v1.36.4+k3s1`，内置 Traefik `3.7.8` |
| 数据服务 | TimescaleDB `2.26.4-pg16`、Redis `7.2-alpine` |
| 消息服务 | EMQX `5.6.1`、NATS `2.12.8-alpine`（JetStream） |
| 对象服务 | SeaweedFS `3.85` |
| 入口服务 | Nginx `1.28-alpine`、K3s 内置 Traefik |
| 时间同步 | Chrony `4.5-1ubuntu4.2` 及 Ubuntu 24.04 离线依赖 |
| 节点程序 | NodeAgent、Node Hostd、Node Hostctl、Gateway、Runtime API、RuntimeEngine、Linux Collector |

包内所有 K3s 资产和基础服务镜像都有 SHA-256 清单。构建脚本对 K3s 上游资产校验后才组包；节点侧 Hostd 在写入宿主前再次核对清单。版本不得由中心请求任意指定，节点只接受本发布线固定的 K3s 版本和固定服务清单。

安装时用户只指定中心地址、一次性接入码和节点数据目录。K3s 数据、容器状态及本地持久卷统一放在该数据目录下；界面不允许逐服务配置宿主路径，磁盘监测也只报告安装时选定的数据盘。

平台不负责校准中心服务器时间。中心 Chrony 不配置公网时间源，以本机时钟作为集群基准，并使用 `-x` 明确禁止修改中心系统时钟；所有 Linux 工作节点只允许向中心节点同步。中心和工作节点分别使用独立的 Chrony 频率估算文件，节点角色切换时不继承旧偏移，避免中心对外发布的时间与其当前系统时间分离。节点心跳上报时间源、当前偏差和状态：偏差不超过 5 秒为已同步，超过 5 秒为校准中，超过 30 秒或无法连接中心时间源为同步异常。状态变化写入集群和运行环境事件，但同步异常不阻断其他运维命令。

## 3. 运行环境和基础服务

每个 Center 只维护一套运行集群。中心安装流程通过 `IF_OPS_CENTER_NODE_ID` 固化一个“中心内置节点”，该节点初始化 K3s Server 和 embedded etcd；管理员审批的其他 Linux 标准节点固定以工作节点加入。中心节点不能在运维界面移除或提升替换，工作节点移除才会卸载本机 K3s Agent 并撤销节点凭据。

中心系统与工程运行共用 K3s 底座但不共用业务资源：`induforge-system` 保存中心控制面，`if-env-*`
保存运行环境。中心数据库、缓存、对象存储、IDE 资源和代码工作区使用中心安装数据目录，不能挂载运行
环境 PVC。中心 NodeAgent、Hostd 和 K3s systemd 服务始终位于 K3s 之外，作为故障恢复边界。当前单
中心版本不允许把中心 StatefulSet 简单扩容为多副本。

运行环境是该集群上的逻辑命名空间、基础服务和工程调度边界，不拥有独立 K3s，也没有“单节点 / 集群”类型。默认运行范围由中心初始化流程幂等创建，不能删除；额外范围及新建入口收纳在“管理运行范围”高级入口中。关联或取消分配节点只改变该环境允许使用的节点集合，不安装或卸载 K3s；同一物理节点可以分配给多个环境。底层的中心 / 工作节点、Server / Agent、Pod 和命名空间均不在最终用户界面暴露。

基础服务固定为八个业务项：IF 实时库、IF 历史库、IF 时序库、IF 消息库、IF 对象库、NATS JetStream、Nginx、Traefik。IF 历史库与 IF 时序库共享同一个 TimescaleDB 实例，因此必须分配到同一节点；其余服务可分布到不同节点。当前每项只有一个实例，不承诺高可用或自动故障转移。

首次部署会记录八项服务到节点的完整分配并产生新的期望 generation。再次点击“重新应用 / 修复”
只能提交完全相同的分配，控制面提升 generation，节点重新导入固定镜像并应用固定清单。“调整分布”
会为变更项记录原节点：无状态入口直接重建，有状态服务先停源实例、复制和校验数据，再切换目标清单，
失败时尝试恢复原分配。该能力不等同于在线主备或自动故障转移，主备和集群模式仍未开放。

基础服务默认只通过集群内部地址互访。SeaweedFS S3 拒绝匿名访问；EMQX MQTT 拒绝匿名连接并由一次性初始化任务写入运行凭据。凭据由节点使用集群令牌派生，不出现在基础服务计划、前端或运维事件中。

## 4. 故障与事件语义

节点默认每 10 秒主动向 Center 心跳。Center 超过 45 秒未收到心跳后：

1. 将物理节点标记为离线，并使所在运行环境进入“需关注”；
2. 只记录一次 `node_offline` 运维事件，避免每轮巡检重复刷屏；
3. 拒绝向包含离线或运行底座未就绪节点的环境下发新的基础服务部署 / 修复；
4. 不主动停止或删除离线节点上已经运行的容器和进程。

心跳恢复后节点自动标记在线并记录一次 `node_online` 事件，期望 generation 保持不变，Agent 继续调和未完成操作。

基础服务状态以真实工作负载观测为准，不能仅以 systemd、PID 或清单已写入判断成功。镜像不存在、Pod 等待原因、容器退出、Job 失败或健康检查未通过都必须使相关服务和运行环境进入异常，并记录一次状态转换事件。异常状态不重复产生相同事件；恢复到部署中或健康状态时再记录对应转换。运维管理员可在保持原分配的前提下执行修复。

主要事件类型包括：

| 事件类型 | 触发条件 |
| --- | --- |
| `default_environment_created` | 中心初始化时创建默认运行范围 |
| `node_auto_assigned` | 中心节点或新审批 Linux 标准节点自动加入默认运行范围 |
| `environment_created` | 创建运行环境 |
| `environment_updated` | 修改运行环境名称 |
| `environment_delete_requested` / `environment_deleted` | 创建删除任务或完成环境清理 |
| `node_added` / `node_removed` | 分配或取消分配运行环境节点 |
| `center_initialized` / `worker_join_requested` / `worker_remove_requested` / `worker_removed` | 全局集群初始化、工作节点加入或物理移除 |
| `cluster_state_changed` | 节点运行底座真实状态变化 |
| `node_offline` / `node_online` | 心跳超时或恢复 |
| `foundation_deploy_requested` | 首次提交八项基础服务分配 |
| `foundation_redeploy_requested` | 保持分配重新应用清单 |
| `foundation_state_changed` | 基础服务在部署中、异常和健康状态之间转换 |

事件保存对象、结果、详细消息、操作人和时间。前端以事件类型完成中英文展示；后端原始消息保留作为诊断证据。

## 5. 安装、升级和卸载边界

NodeAgent 与 root 权限的 Node Hostd 分离。Agent 只能向 Hostd 的 Unix socket 提交固定 schema 的声明式计划；Hostd 拒绝未知字段、任意命令、任意路径、错误节点身份、generation 回退和非固定版本。生产环境的 Center 地址必须为 HTTPS，只有同机回环地址允许 HTTP。

卸载 Linux 标准节点时，无论是否使用 `--purge`，都必须停止 K3s、清理容器 shim、挂载点、CNI 网络接口和规则，并删除安装状态中精确记录的 K3s 数据目录；该目录包含本地持久卷，因此卸载属于数据破坏操作。默认卸载保留 NodeAgent 身份、配置和日志，便于在同一中心重装；`--purge` 额外删除这些内容。卸载不会根据用户输入或未解析变量递归删除目录，也拒绝符号链接和不安全的数据目录。

整个平台卸载中心节点前会清理受管运行环境；即使 API Server 已损坏，宿主清理仍继续。早期节点包没有清理脚本时，新版 Hostd 会依据已校验的本地状态补齐脚本，保证原地升级后可卸载。

默认卸载会保留一条不含宿主路径和密钥的 `not-installed` 集群状态墓碑。按原身份重装后，Agent 先用它通知 Center 将观测 generation 清零，Center 再重新下发同一全局集群计划；不能因为 Center 仍保存上次的 `ready` 状态而跳过重装。完整灾后重建顺序固定为“中心内置节点 → 工作节点 → 各运行环境基础服务”。

取消环境的节点分配前，控制面检查该节点在环境内不再承载基础服务或工程部署；成功后只删除环境关联，节点仍属于中心运行集群。物理移除工作节点则要求它不再被任何环境或工程使用且处于在线状态，随后下发 K3s Agent 卸载，收到 `not-installed` 后撤销凭据。中心内置节点永远拒绝物理移除。

删除运行环境要求输入环境名称确认，并在存在工程部署时拒绝。中心节点异步删除该环境固定命名空间；Kubernetes 接受幂等删除后 Agent 立即回报，避免长时间 Pod 终止阻塞心跳。完成后环境从正常列表隐藏，但全局 K3s 集群、物理节点和其他环境保持运行。

## 6. 正式验收顺序

验收必须在真实 Linux 服务器执行，不得以单元测试或虚假心跳替代：

1. **制品**：构建目标架构安装包，校验版本 sidecar、包内文件和 SHA-256；确认无空壳二进制。
2. **中心安装**：在中心服务器初始化 K3s Server，部署 `induforge-system`，验证所有中心 Pod 固定到
   中心节点、`induforge-centerctl doctor` 通过、中心入口可登录且数据库记录保留；停止中心 Pod 时仍
   可通过宿主命令行诊断。
3. **节点安装**：在额外 Linux 主机安装节点包，验证服务账户、目录权限、NodeAgent / Hostd 和接入码一次性领取；若主机已安装 Docker，明确验证 K3s 工作负载位于内置 containerd 而非 Docker Engine。
4. **节点审批**：在中心核对主机名、IP、架构和能力后审批；验证未审批节点不能取得运行计划。
5. **集群组建**：中心安装流程绑定中心内置节点并先初始化 K3s Server，再审批工作节点加入；验证唯一控制面和两台节点均 Ready。
6. **环境组建**：创建运行环境并关联一台或多台已就绪节点；验证该操作不重装 K3s，且同一节点可关联多个环境。
7. **基础服务部署**：把八项服务分布到两台节点，验证真实工作负载、持久卷、JetStream、对象库鉴权、MQTT 鉴权、Nginx 和 Traefik；中心必须显示 8 / 8 健康。
8. **节点离线**：停止一台 NodeAgent 超过 45 秒，验证一次离线事件、禁止新操作、既有工作负载继续运行；恢复 Agent 后验证一次恢复事件和环境自动恢复。
9. **服务异常**：制造一个可控的镜像或容器异常，验证服务 / 环境转为需关注且只产生一次异常事件；恢复镜像并执行修复，验证回到 8 / 8。
10. **环境删除**：删除一个已部署基础服务的环境，验证命名空间被清理、Agent 心跳不中断、全局集群和其他环境继续运行。
11. **工作节点移除与恢复**：先解除所有环境分配，再物理移除工作节点；检查 K3s Agent、本机挂载和数据被清理且凭据撤销，重新接入后仍只能作为工作节点加入。
12. **时间同步**：断开公网后确认中心 Chrony 没有外部源且以 `-x` 运行，工作节点唯一源为中心；制造 5 秒和 30 秒两档偏差，验证校准中 / 异常状态、恢复事件，并确认中心时间不会被平台修改。
13. **前端**：在浅色 / 深色和中文 / 英文下检查四个运维模块、环境详情、固定分页、异常提示、接入与基础服务对话框；界面不得出现假任务、假部署或底层 K3s 术语。

## 7. 自动化验证入口

```bash
make -C runtime/node_agent test
make -C runtime/node_agent vet
bash runtime/node_agent/packaging/install_linux_test.sh
(cd dev_core && go test ./...)
(cd dev_ide && pnpm build)
(cd dev_ide && pnpm exec vitest run tests/unit/ops-management-console.test.ts tests/unit/ops-api.test.ts tests/unit/ops-presentation.test.ts tests/unit/permissions.rules.test.ts)
```

最终验收证据至少包含：两台节点的 systemd / 运行底座状态、节点列表、工作负载分布、八项基础服务状态、对象库与 MQTT 的匿名拒绝及凭据成功结果、离线 / 恢复事件、异常 / 修复事件、卸载后的宿主清理结果以及重装后的恢复结果。

## 8. 仍未交付

- 工程按运行环境的端到端部署、Secret 装配、组件启动、升级和回滚；
- 基础服务主备、集群、迁移、自动故障转移和备份恢复；
- Windows 采集节点真实主机安装与工业现场驱动验证；
- 多工程资源配额、调度和进程隔离（客户端口选择与双重冲突检查已具备）。

这些能力未完成前，不得把“多节点运行环境”表述为基础数据库高可用，也不得把节点包内携带工程运行程序表述为工程部署已经交付。
