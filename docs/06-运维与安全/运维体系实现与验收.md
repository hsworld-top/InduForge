# 运维体系实现与验收

## 1. 目的与阅读方式

本文是当前代码事实、验收边界与目标架构之间的对照基线。它补充而不替代
[平台运维体系设计](./平台运维体系设计.md)和
[运维与节点运行态总体架构](../02-系统设计/运维与节点运行态总体架构.md)：前两者描述已经冻结的
目标架构；本文明确哪些能力已经可以验收、哪些仍是规划。因此，文中标为“目标态”的内容不得当作
当前版本已经交付。

当前最小闭环是：中心创建运行集群和一次性接入任务，NodeAgent 领取身份并持续心跳，审批后轮询
工作负载期望状态，再以本机 **DemoRuntime** 子进程回报调和结果。它不是 K3s 工程发布系统，也
不是生产工业采集交付。

## 2. 统一术语与边界

| 概念                          | 定义                                                                                                                                     | 当前实现对应物                                              | 不能混同为                                              |
| ----------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------- | ------------------------------------------------------- |
| 中心（Center）                | `dev_core`、`dev_ide` 所在的控制面，负责租户范围内的接入任务、审批、期望状态和运维展示。                                                 | `/api/v1/ops/*` 与“运行管理”页面。                          | 现场运行集群、站点或工程数据面。                        |
| 运行集群（RuntimeCluster）    | 中心登记的、可承载运行工作负载的逻辑目标；当前字段为名称、编码及 `single_node/high_availability` 标签。                                  | `runtime_clusters`。                                        | 已经建成的 K3s 集群、Site 或 HA 承诺。                  |
| 站点（Site）                  | 一个现场自治运行域：现场网络、一个独立 K3s/公共基础设施（如适用）、宿主机和工程部署的归属边界。                                          | **未建模、未实现**；当前 `RuntimeCluster` 不能替代 `Site`。 | 平台安装环境、运行集群记录或单台节点。                  |
| 宿主节点（HostNode）          | 一台受管的物理机或虚机，拥有 OS、资源、机器指纹和一个 NodeAgent；K3s Node 只是它可能具备的一种能力。                                     | `host_nodes`。                                              | Site、K3s Node 或 Collector 工作负载。                  |
| 运维代理（NodeAgent）         | K3s 外的宿主机进程，主动向中心领取身份、心跳、拉取命令并托管本机受授权的进程。                                                           | `runtime/node_agent/internal/ops`。                         | site-controller、infrastructure-controller 或中心 API。 |
| 工作负载（Workload）          | `ProjectDeployment` 下可独立期望/观测的逻辑角色，如 `compute`、`alert`、`collector`。                                                    | `workloads`；当前每 deployment 每角色至多一个记录。         | Pod、原生进程实例或副本。                               |
| 副本（Replica）               | 同一工作负载角色的并发实例数；只有明确的无状态或单写者方案后才可扩展。                                                                   | 保存 `replicasDesired/Observed`，当前 Demo 不创建多副本。   | 多台 HostNode 或一个工作负载记录。                      |
| 工程部署（ProjectDeployment） | 一个工程版本在某运行目标上的部署记录；当前含 `development/production` 模式和 `demo-v1` 默认版本。                                        | `project_deployments`。                                     | 目标态按 `deploymentId` 隔离的完整 Site 部署实例。      |
| 环境（Environment）           | 说明中心自身的安装环境时使用 `platformEnvironment`；说明工程部署策略时使用 `deploymentStage`（目标态：development/staging/production）。 | 当前仅实现 `deploymentMode=development/production`。        | Site、RuntimeCluster 或拓扑规格。                       |

目标态中，`Site` 与 `ProjectDeployment(deploymentId)` 才是隔离 Namespace、NATS Account、数据空间、
域名、Secret 和 Collector Assignment 的主键；`RuntimeCluster` 是当前接入与 Demo 的过渡模型，不能
据此推断 K3s、站点、环境或高可用已经存在。

## 3. 已实现的接入与调和闭环

### 3.1 首次安装与一次性接入码

1. 具有节点审批权限的中心用户创建运行集群（`runtime_linux` 必须关联该记录），再创建角色为
   `runtime_linux`、`collector_linux` 或 `collector_windows` 的接入任务。接入码最长 24 小时，
   中心仅保存其 SHA-256 摘要；明文只在创建响应中返回一次。
2. 运维人员下载匹配角色的安装包并配置中心地址和接入码。Linux 安装器可传
   `--server-url`、`--enrollment-code`，Windows 安装器可传 `-ServerUrl`、`-EnrollmentCode`；
   也可在安装后的 `config.yaml` 填写 `agent.ops.serverUrl` 和 `agent.ops.enrollmentCode`。接入码
   不是日常凭据；两个值齐全时安装器才会启动服务。
3. Agent 启动后以 `POST /api/v1/ops/agent/enrollments/claim` 领取：提交接入码、主机名、OS、架构、
   机器指纹、Agent 版本和能力摘要。有效、未过期且未被领取的码会原子地变为 `claimed`，中心创建
   一个 `HostNode`，并仅在本次响应返回 `hostNodeId + agentToken`。中心同时校验角色与安装平台：
   Linux 运行/采集包只接受 `amd64/arm64`，Windows 采集包只接受 `amd64`，避免误用接入码。
4. Agent 将身份写入 `dataDir/ops-agent-identity.json`，文件权限为 `0600`；已应用 generation 写入
   `dataDir/ops-agent-applied-generations.json`。成功落盘后以原子替换方式清空配置中的
   `agent.ops.enrollmentCode`。中心只保存 `agentToken` 的哈希，不能再读取明文。

若 claim 失败，当前实现会保留接入码，并在后续调和周期继续重试；它不会自动清码。claim 成功但
清空配置失败时，Agent 也会继续重试清空，且在完成前不会进入持身份心跳，避免一份已使用接入码
长期留在配置中。现场撤销或更换尚未领取的接入码时，应停止服务、人工更新配置后再启动，不能把
旧码视为长期身份。

### 3.2 待审批、审批与拒绝

```text
created --claim--> claimed / HostNode(pending_approval)
claimed --approve--> approved / HostNode(等待下一次心跳后 online)
claimed --reject--> rejected / HostNode(revoked)
```

- `claimed` 前后的首次心跳可上报主机资源，但待审批或已吊销节点拿不到命令，且其工作负载观测
  不会写入中心。
- 审批只接受 `claimed` 任务；审批将该 HostNode 置为 `offline`，下一次带有效 Agent Token 的心跳
  才会显示 `online` 并开始获取命令。
- 审批任务状态、HostNode 状态及审批时间在同一数据库事务内更新。`single_node` 集群会锁定集群行，
  只允许一个已审批且启用的运行节点；`high_availability` 可先接入多个节点，但当前版本仍禁止在其上
  创建工程部署，直到主备选举、工作负载归属与故障转移完成。
- 拒绝会将节点置为 `revoked`。当前没有“重新签发/撤销现有 Agent Token/删除身份文件”的专用
  API；拒绝后的本地凭据仍应按安全事件处理，重新接入须使用新的接入任务。

### 3.3 心跳、拉取命令与调和

Agent 以配置的 `heartbeatEvery`（包默认 10 秒）执行下面的顺序；任一次网络失败只结束本轮，已运行
的本机进程不会因此被主动停止：

```text
POST heartbeat（CPU 核数/使用率、内存、当前目录磁盘、Agent 版本、已托管进程观测）
→ GET commands（完整目标工作负载集合）
→ 按 workloadId 比较 desiredGeneration
→ start / stop / restart 本机 Demo 子进程
→ 下次 heartbeat 回报 observedGeneration、状态与 replicasObserved
```

中心每轮都向已审批 Agent 返回其完整目标工作负载集合，而非仅返回
`desiredGeneration != observedGeneration` 的条目。低于已持久化值的 generation 被忽略；相同
generation 只有在本机进程已满足目标状态时才跳过。因此容器或 Agent 重启后，即使中心最后一次观测
仍为 `running`，Agent 也会在同 generation 下恢复丢失的本机进程。成功处理后持久化 generation；
中心根据全部 workload 的观测 generation 和状态结束 `DeploymentRun`，并保存副本数用于展示。当前
命令是 HTTP 轮询，不是 mTLS、WebSocket/gRPC stream、签名命令账本或站点控制器协议。

当前本机 Supervisor 在进程 `running` 或 `stopping` 时报告 `replicasObserved=1`，其余状态报告 `0`，
中心将该值写入 workload 观测。这个字段使完成条件不再把“进程存在”误当作未报告副本；它仍只表示
Demo 单进程事实，不提供多副本调度或 HA。

采集节点可以没有 `runtimeClusterId`。中心以目标 `hostNodeId` 匹配 collector workload，并在涉及运行
集群的查询中将空字符串用 `NULLIF` 转为 SQL `NULL`，避免把空值强制转换为 UUID 后导致观测更新失败。
除“没有匹配目标”外，心跳中的 SQL 错误会返回给 Agent，不再静默吞掉并让工作负载长期停留在 pending。

创建部署只接受已审批、启用、在线且 45 秒内有心跳的目标节点；运行集群还必须处于 ready，并至少有
一个满足上述条件的 Linux 运行节点。采集工作负载必须明确绑定一个可调度的 Linux/Windows 采集节点。
同一租户内，同一工程在同一运行集群只能有一条部署记录；重复发布会在预检或数据库唯一约束处返回
明确冲突，后续状态变更应在已有部署上操作。同一部署同一时刻最多存在一个 pending run；启动、停止
和重启会在数据库锁内串行化，防止并发操作生成互相覆盖的期望状态。外部传入的工程、集群和采集节点
ID 也会在进入数据库前校验 UUID 格式。

### 3.4 部署时间线与进度

`ProjectDeployment` 的 List 与 Get 均返回 `latestRunId`；列表进度取按 `startedAt` 最新的 run，而不是
历史 run 的最大进度。管理端将 `latestRunId` 作为详情轮询的 `runId`，打开或刷新详情时加载最新事件
时间线和当前进度。这保证执行 stop/start/restart 后，详情不会继续展示旧 run 的 100% 或旧事件。
自动轮询超过 60 秒或连续读取失败后会转为“状态待确认”，继续禁用服务操作，并提供“刷新详情”和
“刷新任务”入口；它不会把超时误当作成功或失败，读到真实终态后才解除互斥。

### 3.5 当前可观测数据与失联语义

当前中心保存 CPU、内存和当前工作目录所在磁盘的简要指标、最后心跳、Agent 版本及 Demo 进程状态。
中心在最后心跳超过 45 秒后显示 `offline`。这只是当前 UI/API 的近似在线判断，不能表述为“现场
已宕机”；也尚未实现目标态的 `FRESH/STALE/EXPIRED`、有界离线队列、按序回补、告警规则、日志/追踪
及 OpenTelemetry Gateway。

## 4. 三类安装包与当前支持矩阵

构建入口是根目录 `scripts/release/build-node-agent-packages.sh`。它输出到默认被忽略的
`.data/node-packages/`，中心只从配置目录读取以下固定文件名并提供下载，不会现场构建包。
三个包均内置 `README.md`，说明安装目录、中心地址、一次性接入码、服务生命周期和卸载边界。

| 包 / 角色                                                    | 目标系统与架构         | 安装形态                                           | 当前可验收范围                                                                                                                                                                       |
| ------------------------------------------------------------ | ---------------------- | -------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `induforge-node-runtime-linux.tar.gz` / `runtime_linux`      | Linux `amd64`、`arm64` | systemd 服务；`--no-service` 可用于容器/手工验证。 | 接入、审批后心跳，以及 `compute`、`alert` 的 Demo 进程调和。K3s 配置入口默认关闭，不安装或管理 K3s。                                                                                 |
| `induforge-node-collector-linux.tar.gz` / `collector_linux`  | Linux `amd64`、`arm64` | systemd 服务；支持 `--no-service`。                | 接入、审批后心跳，以及 `collector` 角色的 Demo 进程调和；不交付工业驱动、真实设备连接、WAL 或 Collector Assignment。                                                                 |
| `induforge-node-collector-windows.zip` / `collector_windows` | Windows `amd64`        | 原生 Windows Service；`-NoService` 可只释放文件。  | 代码具备接入、审批后心跳和 `collector` Demo 进程路径。安装器生成服务包装脚本，向 `--service` 进程传入配置、工作目录和数据目录；已有安装器静态检查，尚无 Windows 真实服务端到端验收。 |

安装器默认不会覆盖已有 `config.yaml`。Linux 默认安装到 `/opt/induforge/node-agent`，配置在
`/etc/induforge/node-agent/config.yaml`；Windows 默认安装到
`%ProgramFiles%\InduForge\NodeAgent`，配置在 `%ProgramData%\InduForge\NodeAgent\config.yaml`。
Linux systemd 会设置 `NODE_AGENT_CONFIG`、`NODE_AGENT_WORKDIR` 和 `NODE_AGENT_DATA_DIR`；容器验收也
必须显式设置这些变量。Windows 安装器生成的 `node-agent-service.cmd` 也会设置同三个变量，再以
`--service` 启动 Agent；该模式由原生 Service Control Manager 入口接收停止/关机信号，而非把普通
控制台进程直接交给 `sc.exe`。

Agent 的本机进程状态与日志接口可供同机诊断；启动、停止、重启等变更只接受 `POST`，并要求请求头
`X-InduForge-Local-Operation: 1`。该约束用于避免浏览器、探针或误发 GET 触发本机进程变更，不替代
目标态的本机身份认证和授权。

普通卸载会停止并删除服务、删除 Agent 二进制，但保留配置、数据目录和日志，避免误删身份与诊断
证据。Linux 的 `uninstall.sh --purge`、Windows 的 `uninstall.ps1 -Purge` 才会清除安装目录和配置目录；
该操作会删除身份令牌、已应用 generation 与日志，必须先完成节点下线和凭据处置。卸载不等同于中心
撤销节点身份，当前没有自动联动。

### 4.1 DemoRuntime 的严格范围

DemoRuntime 使用 NodeAgent 自己的 `demo-workload` 子命令模拟进程，并由本机 Supervisor 记录 PID、
状态和滚动日志。`runtime_linux` 只有 `demoRuntime=true` 时才调和 `compute`/`alert`；两个 Collector
角色只调和 `collector`，当前同样实际启动 Demo 子进程，不会执行真实采集器。它证明“期望 generation
→ 本机启停 → 观测回传”的链路，不证明以下能力：

- 真实 `runtime-engine` 的 compute/alert 处理、工程 Release、容器、K3s 或 site-controller；
- 工业 Collector 二进制、驱动、设备访问、采集配置、密钥、WAL、断线补传和安全写入；
- 多副本、滚动升级、事务/检查点、Lease/epoch 单写者或生产回滚。

因此，当前页面中的“生产运行”和工作负载“运行中”仅表示 Demo 控制记录和进程观测，不能作为生产
可用或工业采集验收结论。`high_availability` 当前只能用于提前登记多个节点，管理端不允许选择，后端
也明确拒绝在该拓扑上创建部署，不能作为 HA 验收结论。

## 5. 目标生产态：边界与演进方向（未实现）

### 5.1 K3s 与原生 Collector 的职责分界

目标生产站点在 Linux 上以 K3s 承载工程 Web/API/运行工作负载：`project-nginx`、`runtime-api`，以及
`runtime-engine` 的 `compute`、`alert`（还有 writer、query、coord 等逻辑角色）。`site-controller`
在已分配 Namespace 中调和工程资源；`infrastructure-controller` 用独立身份管理 Namespace、Ingress、
NATS Account、数据空间、备份和公共底座。中心不保存站点 kubeconfig。

Windows 和 Linux 的工业 Collector 保持宿主原生进程，由各自 HostNode 的 NodeAgent 托管；纯采集节点
不要求安装 K3s。NodeAgent 只处理已校验的部署/采集契约和本机生命周期，不解析工程页面、数据点或
工业地址。该分界也意味着生产 `compute/alert` 不能继续由当前 NodeAgent Demo Supervisor 承载。

### 5.2 发布、升级、HA 与断线

- 无状态 K3s 工作负载可按 `maxUnavailable/maxSurge`、readiness、PDB 和观察窗口滚动；PDB 不替代
  业务排空。
- writer、alarm、compute、定时任务和 Collector 必须先预热、排空、持久化 checkpoint，再以
  Lease + epoch + 幂等键转移唯一业务所有权；设备写入缺少硬 fencing 时，歧义故障期间应暂停写入。
- `site-ha` 的目标是至少 3 台奇数 K3s Server、关键 JetStream Stream/Consumer R3、存储 HA 及跨
  故障域放置。两台机器、`high_availability` 标签或多个 Demo 进程均不构成 HA。
- 中心失联时，已提交的站点计划按持久决议继续，工程不依赖中心实时运行；NodeAgent/站点控制器应
  以有界磁盘队列缓存心跳、事件和结果，恢复后按 revision/commandId 幂等回补。当前代码尚未实现该
  队列、决议、site-controller 或离线回补。

### 5.3 可观测性方向

控制遥测保留为 Agent/控制器的轻量心跳、命令结果和资源摘要；详细指标、日志与追踪采用“主机
Collector（需要时）→ 站点 OpenTelemetry Gateway → 中心”的分层出口。每条数据应带稳定的
`siteId/nodeId/deploymentId/component` 标签，并对 HA 副本去重或区分。完整指标目录、告警和保留策略
见[平台运维体系设计](./平台运维体系设计.md)，当前均为后续实现项。

## 6. 工程 Web 发布入口

工程 Vite 构建得到的静态产物在目标态默认由每工程的 **`project-nginx`** 托管，并在同一入口代理
受控的 Runtime API 和 WebSocket：浏览器 → 站点 Ingress → `project-nginx` → 当前 Release 静态文件，
`/api`、`/ws` 再转至 `runtime-api`。Nginx 是工程发布产物的默认 Web 服务器；它不等于站点 Ingress
Controller，也不负责中心平台的管理入口。

仅当站点确实需要 Kubernetes Ingress 的动态路由、跨 Namespace/工程 TLS 与域名配置、证书自动化、
多入口策略或统一入口观测时，才部署 Traefik（或经评审选定的其他 Ingress Controller）。Traefik
负责站点入口路由，不取代每工程 `project-nginx` 的静态托管和 API/WebSocket 代理；当前仓库尚未
交付该 K3s/Traefik 发布路径。

## 7. 当前验收与未实现清单

### 7.1 可执行验收

1. 构建三类包：`bash scripts/release/build-node-agent-packages.sh`，确认三个固定文件名存在。
2. 运行 Linux 闭环：`bash scripts/test/ops-runtime/run-e2e.sh`。该脚本先静态核对 Linux/Windows
   安装器的服务入口、配置变量和接入参数，再在 Docker 中覆盖 runtime 与 collector Linux 包的
   claim、心跳、命令拉取、start/stop/restart、PID 变化和 Demo 日志。它使用 mock control plane，
   不验证 `dev_core` 数据库、审批、Windows Service Control Manager 或真实工业设备。
3. 使用已启动的中心进行人工链路：创建接入码 → Linux Agent claim → 检查 `claimed/pending_approval`
   → 审批 → 等待下一心跳显示在线 → 创建 compute/alert/collector Demo workload → 核对
   `desiredGeneration/observedGeneration`、`replicasObserved`、DeploymentRun 事件、本机日志和最新 run
   的详情时间线。
4. **本次最终人工验收已完成**：在右侧浏览器完成计算 stop/start、报警 restart、采集 restart；三个
   操作均观察到对应进程 PID 变化、部署任务完成进度为 100%，并成功下载 Windows 安装包。该结果证明
   已启动中心上的 Demo 控制链路和管理端最新时间线可用，不等于 Windows 服务已在真实 Windows 主机
   安装或 claim 成功。
5. 安全回归：确认接入码在 claim 后从配置清空、`ops-agent-identity.json` 为 `0600`、重复/过期码被拒；
   待审批/被拒节点只能心跳且拿不到命令；普通卸载保留状态，purge 才删除。

### 7.2 明确未实现，不能验收为完成

- `Site`、DeploymentBinding、Release/Artifact 下载与校验、SiteBootstrapPlan、site-controller、
  infrastructure-controller、K3s 安装/修复和工程 Namespace 调和。
- 真正的 `runtime-engine` compute/alert、`runtime-api`、`project-nginx`、工程发布、滚动升级、
  回滚快照和生产健康门禁。
- 原生工业 Collector 的能力包、配置实例化、设备 Secret、WAL、断线缓存/回补、驱动矩阵和设备写入
  fencing。
- 生产 HA、Leader/Lease、epoch、跨故障域副本、备份恢复/灾备、OpenTelemetry、告警、完整审计和
  心跳新鲜度模型。
- Agent mTLS、证书轮换/吊销、离线文件注册、命令签名/持久化命令账本，以及 Windows Service 的
  真实主机端到端安装、启动、停止、重装与 claim 验收。
