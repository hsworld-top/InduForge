# 运维体系实现与验收

## 1. 当前验收结论

当前仓库已经从 Demo 子进程改为**本机 allowlist 服务组托管**的实现切片：Center 管理物理节点和工程单节点部署；NodeAgent 仅能调和本机显式配置的 `project_entry`、`data_runtime`、`collector`。这不是完整工程发布系统，也不是多节点分布式或高可用交付。

验收和对外表述只能使用“物理节点接入”“工程单节点部署”“可选采集”。不得向用户暴露或以资源池、K3s、Pod、容器、集群标签来描述当前部署模型。

## 2. 安全与安装边界

Center 与 NodeAgent 是独立服务。即使同机也必须：

- 使用不同服务账户、程序目录、数据目录和日志目录；
- 使用独立监听端口；Runtime API 必须仅监听回环地址，Project Gateway 才能暴露工程入口；
- 通过 NodeAgent 主动到 Center 的 API 调用完成领取、心跳和拉取命令；Agent 已强制生产 Center 使用 HTTPS，仅同机 loopback 允许 HTTP；
- 节点安装命令中的 Center 地址必须从目标物理节点视角可访问；`localhost`、`127.0.0.0/8` 和 `::1`
  只能用于 Center 与 NodeAgent 同机安装，远程节点必须改用可访问的 HTTPS 入口；
- 不共享 Agent token、中心数据库凭据、Release 根或运行时 Secret；
- 不把 Center 作为 NodeAgent 的内嵌库、子进程或同目录安装物。

Linux 安装包默认将 NodeAgent 程序安装在 `/opt/induforge/node-agent`，配置在 `/etc/induforge/node-agent/config.yaml`；身份、generation 和 Supervisor 状态应放在 NodeAgent 私有数据目录。包默认包含 `installed: true`、`enabled: false` 的 `project_entry` 与 `data_runtime` 模板（Collector 仅在显式安装选项后标记为已安装）；它们可用于领取节点身份，但因没有 Release/命令/健康配置，**不会**启动 Demo 或任何工程组件。

## 3. 已实现的管理闭环

| 能力           | 已实现事实                                                              | 验收要点                                                       |
| -------------- | ----------------------------------------------------------------------- | -------------------------------------------------------------- |
| 物理节点接入   | 一次性接入码领取，审批后使用 Agent token 心跳/取命令                    | 码只返回一次；Agent 成功领取后持久化身份并清除配置中的接入码   |
| 节点能力       | `project_entry`、`data_runtime`、`collector`，由本机 ServiceConfig 派生 | 节点必须至少声明一项；中心命令不能增加能力                     |
| 工程单节点部署 | 指定工程、正式版本、物理节点和 `enableCollector`                        | 生成入口、数据运行与可选采集三类服务记录；只能操作固定服务类型 |
| 命令安全       | Agent 检查 nodeId、服务组、local allowlist、generation                  | 验证未知服务、非本节点命令和倒退 generation 均被拒绝           |
| 进程恢复       | Supervisor 持久化 PID/组件 PID/状态，重启后检查已配置进程               | 恢复不得采纳未配置服务或远端任意命令                           |
| Release 选择   | 解析 `releaseRoot/current`，校验 release 内 manifest 的 SHA-256         | current 越界、可执行路径越界、摘要不符必须拒绝                 |
| 健康探测       | HTTP GET 且仅 loopback URL；服务组全部组件健康才运行                    | 健康 URL 不能被配置为外网；停止应走 drain timeout              |

Center 管理 API 位于 `/api/v1/ops/*`，Agent API 位于 `/api/v1/ops/agent/*`。中心只保留部署服务的期望/观测状态、generation、入口 URL 和运行记录；中心不会远程提供 shell、路径、参数、环境或 Secret。

当前还未形成按工程隔离 Release、端口、Secret 和进程目录的 `DeploymentBinding`，因此一台物理节点最多创建一个工程部署。中心会在事务内锁定租户工程与物理节点并再次检查冲突；从零创建的基线数据库还以 `(tenant_id, node_id)` 唯一约束兜底。仓库不提供迁移或启动时修复：若既有数据库已存在同节点多工程脏数据，必须按数据库基线重建流程处理，不能让服务自动猜测保留哪条记录，也不得通过手工写库绕过限制。

## 4. 正式单节点服务配置

每一项本地 `ops.services` 必须由节点运维人员写入，包含 group、component、releaseRoot、current、releaseDigest、executable、arguments、environment、workingDir、healthUrl、健康及排空超时。正式工程至少配置：

| 组              | 必须组件/资源                                       | 说明                                                           |
| --------------- | --------------------------------------------------- | -------------------------------------------------------------- |
| `project_entry` | `project-gateway`、`runtime-api`、`release/client/` | 静态 `client/` 只是 Gateway 读取的文件；不是组件、服务或 PID   |
| `data_runtime`  | `runtime-engine`、RuntimeEngine config/index/Secret | Engine 使用 `runtime-engine.config.v2`，release 根必须实际只读 |
| `collector`     | `industrial_collector`（确有采集需要时）            | 无采集需求时不要启用、不要创建服务记录                         |

Project Gateway 与 Runtime API 必须同时属于 `project_entry`，且 API 的监听地址和 Gateway 的 upstream 都为同节点 loopback。Gateway 才是工程公共入口。配置中的命令、参数、环境和 release 路径是本地可信输入；中心命令只选择已存在服务组的启动、停止或重启。

## 5. 真实单节点验收清单

以下是尚需在隔离测试物理机执行的验收，不得用单元测试或虚假心跳代替：

1. 安装 Center 与 NodeAgent 为独立账户/目录/端口；同机场景证明它们仍只通过 Agent API 通讯。
2. 将完整、受控的 Release 放入节点 release 根；切换 `current` 并校验 `release-manifest.json` 摘要。为 RuntimeEngine 以只读 bind/挂载提供 v2 `artifactMount.mountPath`。
3. 写入本地 ServiceConfig，至少在 `project_entry` 配置 Gateway 与 Runtime API，在 `data_runtime` 配置 Engine；确认默认空配置不启动任何 Demo。
4. 领取、审批物理节点，创建工程单节点部署；验证 Center 发出的每个命令均只含本节点的 serviceId/type/status/generation。
5. 启动入口、数据运行及按需采集的服务组，核对所有真实 `/health`；Gateway 访问静态 `index.html`、同源 Runtime API/WS 代理和入口身份头。
6. 验证 RuntimeEngine 读取 v2 配置、拒绝可写 release 根、路径越界、符号链接与错误 SHA-256；验证 SIGTERM drain 和 Agent 停止超时。
7. 重启 NodeAgent，确认仅恢复现有 allowlist 中且 PID 仍有效的进程；向 Agent 发送未知组、错误 nodeId、低 generation 和外网 health URL 的负向用例。
8. 断开 Center 网络，确认已运行本机进程不会被本轮网络失败主动停止；恢复网络后确认观测回传。

最终证据应包含 Center 运行记录、Agent 日志、各组件 status/health、release manifest 摘要以及拒绝路径的错误记录。不得用“PID 存在”代替业务或工业采集成功。

## 6. 当前未交付或未完成验收

- **工程发布链**：创建部署前已会拒绝缺少正式 `2.0` Manifest、Artifact 摘要或
  供应链/预检声明的旧源码 IFP；但中心从工程版本生成/签名/上传完整 Release、Agent
  下载/验签/解包/原子切换和 Secret 装配，仍未形成完整端到端链；当前仅有本地 `current` 解析与
  manifest 摘要选择。
- **多工程节点隔离**：正式 `DeploymentBinding`、每工程端口分配、Release/Secret/目录隔离尚未交付；当前以“一台节点最多一个工程”阻断错误 Release 和假成功。
- **安装包全链路**：构建脚本会真实构建 Linux Gateway/API/Engine 和 Collector；缺工具链会失败。但真实 Linux 安装—接入—部署运行与 Windows 服务端到端尚未在本文件证明完成。
- **基础依赖装配**：RuntimeEngine 不创建 PostgreSQL schema、NATS Stream/Consumer；这些依赖、Secret 和只读挂载仍由现场运维受控提供。
- **Runtime API 写能力**：设备写入、报警动作和人工计算运行当前返回 `501 / code=50031`。
- **统一状态契约**：Project Gateway、Runtime API 与 RuntimeEngine 的 `/api/v1/status` 已携带 `runtime-health-status.v1` 的组件、部署、进程和业务新鲜度身份；Industrial Collector 保持自己的完整采集状态对象，详见健康协议。
- **Collector 生产验证**：构建并不证明现场驱动、连接、WAL、补传、权限和设备写入已验收。

上述任一项未补齐时，不得把“工程服务已启动”表述为“完整工程发布已交付”或“工业现场已生产可用”。

## 7. 多节点分布式部署和高可用（未来）

当前版本明确禁用多节点工程部署。后续分布式交付至少需要冻结并验证：跨节点 Release/Secret 一致性、数据角色分片、唯一 owner/epoch/fencing、checkpoint/排空、故障检测、切换策略、回滚和故障注入。完成这些前：

- 多台已接入物理节点不是工程分布式部署；
- 多个本机进程不是副本系统；
- `replicasObserved=1` 不是高可用证明；
- 不能承诺自动故障转移、无中断升级或数据零丢失。
