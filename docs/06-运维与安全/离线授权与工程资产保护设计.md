# 离线授权与工程资产保护设计

## 1. 文档定位

本文档定义 InduForge 在离线或局域网环境下如何做产品授权、节点授权、工程资产授权、授权管理界面、授权提醒和后端校验。

这里的“授权”不是用户登录权限，也不是工程内角色权限。它解决的是商务和资产保护问题：

- 客户买了哪些能力。
- 客户能用多久。
- 客户能启用多少租户、多少开发用户、多少服务运行节点、多少点位。
- 工程数量、服务运行节点数量、HA、协议采集等能力是否在授权范围内。
- 一级用户开发出来的工程包能不能只给指定客户运行。

设计前提：

1. 大部分客户现场无法访问公网。
2. 不提供在线授权服务。
3. 不使用深思锁这类硬件锁。
4. 使用授权文件交付。
5. 我们内部只给平台实例颁发平台授权，不按每台节点机器码单独出授权。
6. 一级用户是平台使用者，只具备工程资产授权能力，不能颁发平台授权或节点授权。
7. 客户可能拥有服务器管理员权限，所以只能提高破解成本，不能承诺绝对防破解。

## 2. 核心结论

1. 授权采用离线授权文件，现场只做本地验签和本地校验。
2. 授权分三类：平台授权、节点授权、工程资产授权。
3. `dev_core` 是平台侧授权管理中心，负责导入授权、展示授权、配置租户授权分配、控制开发态配额和给节点下发授权结果。
4. 平台授权只绑定平台安装实例的机器码，不要求我们采集或签发节点机器码。
5. 节点授权随节点注册从平台获取，是平台授权派生出来的运行凭证。
6. `node_agent` 必须本地校验节点授权，不能只相信 `dev_core` 接口返回值。
7. 只在采集盒子里运行 collector、本地 WAL 和上行能力的纯采集 `node_agent` 不占用节点数量名额，也不再给采集盒子设置独立数量名额；它只跟随已授权运行工程使用。
8. `runtime_api`、`runtime-engine`、collector 也要校验关键能力，避免只改一个地方就绕过授权。
9. 工程资产授权用于保护一级用户开发的工程包，不等同于 InduForge 平台授权。
10. 到期不应直接打断生产，应按“提醒、限制新增、宽限、强限制”分阶段处理。

## 3. 名词解释

| 名词         | 简单说明                                                                           |
| ------------ | ---------------------------------------------------------------------------------- |
| 授权文件     | 写明能用什么、能用多久、数量限制是多少。平台授权由我们发放，工程授权由一级用户发放 |
| 签名         | 用私钥给授权文件盖章，现场用公钥验证，防止用户自己改文件                           |
| 私钥         | 平台授权私钥只在我们内部；工程授权私钥由一级用户自己保管；私钥不能进最终客户现场   |
| 公钥         | 可以放在产品里，用来验证授权文件是不是真的                                         |
| 平台授权     | 我们颁发给客户的 InduForge 产品授权                                                |
| 租户授权分配 | 平台管理员把平台总授权配置给具体租户的本地分配记录                                 |
| 平台机器码   | 平台安装实例生成的机器识别码，我们只根据它给平台出授权                             |
| 节点授权     | 平台授权派生出来的节点运行凭证，节点注册到平台后获取                               |
| 工程资产授权 | 一级用户给自己开发的工程包加密，并基于对方平台机器码生成解密授权                   |
| 节点注册身份 | 节点第一次注册到平台时生成的身份，不作为我们内部出授权的机器码                     |
| 宽限期       | 授权到期后给客户处理续期的缓冲时间，避免生产现场突然停机                           |

## 4. 授权类型

### 4.1 平台授权

平台授权由 InduForge 内部颁发，建议文件名为 `platform.lic`。平台授权只绑定平台安装实例，也就是 `dev_core` 所在平台的机器码或安装实例码。我们不要求客户提供每个 `node_agent`、服务运行节点或采集盒子的机器码。

它控制开发平台和运行平台能使用的总能力。总能力不是直接给某个租户使用的明细，多个租户场景下还需要平台管理员在现场把授权内容分配到每个租户。

| 授权项         | 说明                                                                      |
| -------------- | ------------------------------------------------------------------------- |
| 有效期         | 授权起止时间                                                              |
| 租户数量       | 最多可启用多少租户                                                        |
| 开发平台用户数 | 最多可启用多少平台用户，首版建议按命名用户数                              |
| 工程数量       | 同一时间最多允许多少工程处于部署或运行状态                                |
| 节点数量       | 最多可注册或启用多少个服务运行节点；纯采集 `node_agent` 不计入            |
| 点位数量       | 全平台或单工程可用点位数量档位                                            |
| 协议能力       | S7、OPC UA、Modbus、MQTT、HTTP、数据库连接等                              |
| 数据能力       | 实时、历史、报警、计算、关系查询                                          |
| HA 能力        | 是否允许 `site-ha`、`collector-ha`、`runtime-sharding`、`site-dr` 等能力 |
| 原生采集能力   | 是否允许 Windows / Linux 原生采集；纯采集 `node_agent` 不单独设置数量配额 |
| 工程资产保护   | 是否允许一级用户导出加密工程包和工程授权                                  |
| OEM / 白标     | 是否允许替换品牌、隐藏平台标识                                            |

不建议首版强控 CPU、内存、吞吐量。工业现场负载波动大，按这些指标限制容易误伤正常生产。

### 4.1.1 租户授权分配

如果平台授权允许多个租户，必须给每个租户配置授权内容。推荐做法是：我们在 `platform.lic` 中签发一组租户授权包，现场在“授权管理 / 租户授权分配”中把授权包绑定到具体租户。这样不需要给每个租户单独发授权文件，也不允许客户在现场随意把某个租户额度改大。

如果某些客户只购买平台总量，不需要精细控制每个租户，也可以支持“总量内手工分配”模式。但默认设计建议采用签名的租户授权包，商务边界更清楚。

租户授权分配建议包含：

| 分配项           | 说明                                                           |
| ---------------- | -------------------------------------------------------------- |
| 租户启用状态     | 当前租户是否允许启用                                           |
| 开发平台用户数   | 当前租户最多可启用多少开发用户                                 |
| 工程数量         | 当前租户同一时间最多允许运行多少工程                           |
| 服务运行节点数量 | 当前租户最多可使用多少服务运行节点；纯采集 `node_agent` 不计入 |
| 点位数量         | 当前租户可使用的点位数量档位                                   |
| 协议能力         | 当前租户可使用哪些协议接入能力                                 |
| 数据能力         | 当前租户可使用实时、历史、报警、计算、关系查询等哪些能力       |
| HA 能力          | 当前租户可使用的站点高可用、采集冗余、分片和灾备能力           |
| 原生采集能力     | 当前租户是否允许 Windows / Linux 原生采集                      |
| 工程资产保护     | 当前租户是否允许加密导出工程包和生成工程授权                   |

分配规则：

- 所有租户授权包加起来不能超过平台授权总量。
- 租户授权包不能打开平台授权里没有购买的能力。
- 新建租户默认没有业务授权，必须在“授权管理 / 租户授权分配”中绑定或配置授权内容后，才能启用开发用户、发布工程和部署运行。
- 租户详情界面只展示当前租户分到的授权内容和当前使用量，不允许在详情页修改平台授权或其他租户的分配。
- 租户被停用后，不应删除其历史工程和数据，但不能继续新增用户、发布、部署或扩容。

节点数量和工程数量是两个独立限制：

- 节点数量控制“平台最多能注册多少个服务运行节点”。
- 工程数量控制“平台最多允许多少工程进入运行态”。

例如授权允许 2 个服务运行节点、1 个工程时，用户可以注册两个服务运行节点，但同一时间只能运行一个工程。这个工程可以部署在节点 A，也可以切换部署到节点 B；如果要让两个不同工程同时运行，就需要购买 2 个工程名额。

创建、保存、停用、归档的工程不占用工程数量授权。工程数量只在工程进入部署或运行态时计算，避免客户因为历史工程、备份工程或停用工程占用授权而难以理解。

授权中的 HA 只控制“客户是否有权启用某项能力”，不直接定义技术拓扑。`edge-single`、
`site-standard`、`site-ha` 是站点拓扑 Profile；`collector-ha`、`runtime-sharding` 和
`site-dr` 是可组合能力。具体节点数量、JetStream 副本、存储和故障域必须由
[运维与节点运行态总体架构](../02-系统设计/运维与节点运行态总体架构.md)校验，不能因为授权
包含“HA”就把不满足多数派的两节点部署显示为高可用。

服务站点、采集站点是工程部署拓扑里的角色，不是平台授权里的动态工作负载判断。授权里的
“节点数量”统计注册时被标记为 `service-capable` 且处于启用/保留状态的 HostNode；K3s 此刻是否
恰好把 `project-nginx`、`runtime-api`、数据写入、报警、计算或 IF 内置库 Pod 调度到该主机，
不改变名额占用。纯 `collector-only` HostNode 不占服务运行节点名额。

如果某个 `node_agent` 只部署在盒子里做采集，只运行 collector、本地 WAL 和上行能力，不运行服务侧能力，则不占用节点数量名额，也不再按采集盒子数量单独限额。它只跟随某个已授权运行工程使用：只要这个工程已经占用到工程数量名额，就可以按工程部署拓扑把采集任务下发到盒子里。协议能力、原生采集能力可以作为工程能力校验，但不是采集盒子的数量限制。

### 4.2 节点授权

节点授权是 `dev_core` 根据平台授权、租户授权分配、节点注册信息和当前授权配额生成的运行凭证，建议叫 `node-runtime-grant`。

节点授权不是给用户看的主授权文件，而是给 `node_agent`、`runtime_api`、数据引擎校验用。

节点授权不由 InduForge 内部单独颁发，也不绑定我们采集到的节点机器码。节点注册到平台时，由当前平台在自身平台授权范围内生成节点运行凭证。

节点授权用于让 `node_agent` 本地校验自己能启动哪些能力。只有服务运行节点会占用平台授权里的节点名额，纯采集节点不占用节点名额。用户不想再使用某台机器做服务运行节点时，可以在平台里删除或停用该节点，释放节点名额。新机器重新注册为服务运行节点后，只要授权名额未超限，就可以获得新的 `node-runtime-grant`。

节点授权至少包含：

| 字段         | 说明                                                                                                             |
| ------------ | ---------------------------------------------------------------------------------------------------------------- |
| 授权 ID      | 来自哪个平台授权                                                                                                 |
| 客户 ID      | 授权属于哪个客户                                                                                                 |
| 平台实例 ID  | 当前平台安装实例                                                                                                 |
| 节点 ID      | 授权给哪个节点                                                                                                   |
| 允许执行方式 | 当前节点允许使用的执行方式，例如 `service-linux-container`、`collector-windows-native`、`collector-linux-native` |
| 节点注册身份 | 节点注册时生成的身份或公钥摘要                                                                                   |
| 允许能力     | 可以启动哪些运行能力                                                                                             |
| 有效期       | 节点凭证有效时间                                                                                                 |
| 签名         | 防止用户伪造                                                                                                     |

节点启动时不能只问 `dev_core`“授权是否有效”。正确做法是：`node_agent` 拿到 `node-runtime-grant` 后自己验签、自己校验平台实例 ID、节点 ID、节点注册身份、有效期和能力。

节点名额释放规则：

| 操作               | 授权影响                                                    |
| ------------------ | ----------------------------------------------------------- |
| 新服务运行节点注册 | 占用 1 个节点名额                                           |
| 新纯采集节点注册   | 不占用节点名额，但只能承接某个已授权运行工程的采集任务      |
| 停用节点           | 节点不可再接收新部署，可按策略释放或保留名额                |
| 删除节点           | 释放节点名额，并吊销该节点当前 `node-runtime-grant`         |
| 已删除节点再次上线 | 因 grant 已吊销或节点记录不存在，应拒绝新启动并提示重新注册 |
| 新机器注册         | 只要名额未超限，可以注册并获取新的节点授权                  |

为了防止反复删除、注册来规避授权，节点删除、停用、重新注册都必须写入授权审计日志。必要时可以对短时间内频繁释放节点名额做人工确认或冷却时间限制。

### 4.3 工程资产授权

工程资产授权是给一级用户保护工程文件用的，建议文件名为 `project.lic`。一级用户是平台使用者，只能给自己开发的工程包加密，并基于对方平台机器码生成工程解密授权，不能生成 `platform.lic`，也不能绕过平台授权直接给节点发运行授权。

典型场景：

```text
一级用户开发工程
  -> 选择加密导出 project.ifp
  -> 向最终客户索要对方平台机器码
  -> 基于对方平台机器码生成 project.lic
  -> 把 project.ifp + project.lic 交付给最终客户
  -> 最终客户只能在对应平台实例中解密和导入
```

工程资产授权只控制“能否被对方平台解密导入”，不控制工程内部用户数量、运行节点数量、HA、点位数量、运行时间等商业能力。这些能力统一由接收方的平台授权和租户授权分配控制。

工程资产授权只需要包含：

| 授权项         | 说明                                     |
| -------------- | ---------------------------------------- |
| 目标平台机器码 | 这个工程授权给哪个平台实例解密           |
| 工程 ID / 版本 | 限制具体工程或版本                       |
| 工程解密密钥   | 用于解开加密工程包，由目标平台机器码保护 |
| 签名           | 防止工程授权文件被篡改                   |

工程资产授权不替代平台授权。它只在加密工程包导入和解密时使用；工程一旦合法导入，后续能否部署、运行、启用 HA、注册节点、使用点位等，仍由接收方平台授权、租户授权分配和节点授权控制。

加密工程导入时需要满足：

```text
平台授权有效
平台授权允许工程资产导入
工程资产授权匹配当前平台机器码
```

运行时需要满足：

```text
平台授权有效
节点授权有效
工程数量、服务运行节点数量、HA 等平台授权总配额和当前租户分配配额都未超限
```

## 5. 租户管理中的授权界面

授权管理放在 `dev_ide` 的“租户管理”模块中，但不是放进某一个租户详情页里，而是在租户管理左侧菜单栏中作为单独菜单。

这样做的原因是：平台授权先限制整个平台能启用多少租户，再把用户数、工程数量、服务运行节点、点位、协议、HA 等能力落到每个租户。这个动作天然属于租户管理，但不能只挂在某一个租户下面。

授权对象分两层：

- 平台授权：我们内部颁发的 `platform.lic`，控制平台总额度和总能力。
- 租户授权分配：把 `platform.lic` 中的租户授权包绑定到具体租户，或在总量内配置租户可用额度。

每个租户详情界面只展示当前租户分到的授权内容和使用量，不展示其他租户的分配，也不承载平台授权上传、卸载和总量配置。

### 5.1 页面入口

建议入口：

```text
租户管理
├─ 租户列表
├─ 授权管理
│  ├─ 平台授权
│  ├─ 租户授权分配
│  ├─ 授权使用量
│  ├─ 节点运行授权
│  ├─ 工程资产授权
│  └─ 授权日志
└─ 租户详情
   └─ 授权信息
      ├─ 当前租户授权内容
      ├─ 当前租户使用量
      └─ 当前租户授权提醒
```

不同角色看到的内容不同：

| 角色                  | 可见内容                                                                   | 可操作内容                                                                         |
| --------------------- | -------------------------------------------------------------------------- | ---------------------------------------------------------------------------------- |
| 平台超级管理员        | 平台授权、租户授权分配、全平台使用量、节点运行授权、工程资产授权、授权日志 | 上传、更新、卸载、查看平台授权；配置每个租户的授权内容；查看和重新生成节点运行授权 |
| 租户管理员 / 一级用户 | 当前租户授权内容、当前租户使用量、当前租户授权提醒、工程资产授权           | 只读查看当前租户授权；上传、更新、卸载、查看本租户工程资产授权                     |
| 普通开发用户          | 授权提醒                                                                   | 只读查看与自己操作相关的限制原因                                                   |

### 5.2 平台授权

用于让客户一眼看懂当前买了什么。

展示内容：

- 客户名称。
- 平台机器码。
- 授权版本。
- 授权类型，例如标准版、企业版、OEM 版。
- 有效期。
- 当前状态：正常、即将到期、宽限期、已过期、授权异常。
- 授权文件编号。
- 导入时间。
- 最近一次校验时间。

按钮：

- 上传授权文件。
- 更新授权文件。
- 卸载授权文件。
- 导出平台机器码。
- 查看授权详情。
- 下载授权诊断包。

其中“导出平台机器码”用于平台授权申请。客户把平台机器码发给我们，我们返回 `platform.lic`。卸载授权只删除当前导入的授权记录和缓存，不删除客户数据；卸载后平台进入未授权状态，只允许查看、备份和重新上传授权。

### 5.3 租户授权分配

用于把平台总授权落到具体租户。推荐模式下，平台超级管理员在这里选择某个租户，并绑定我们在 `platform.lic` 中签发的租户授权包；如果采用总量内手工分配模式，则在这里配置该租户可使用的授权内容。

示例：

| 租户   | 开发用户 | 工程数量 | 服务运行节点 | 点位          | 协议能力   | HA   |
| ------ | -------- | -------- | ------------ | ------------- | ---------- | ---- |
| A 工厂 | 20 / 20  | 1 / 1    | 2 / 2        | 50000 / 50000 | S7、OPC UA | 热备 |
| B 产线 | 8 / 10   | 0 / 1    | 0 / 1        | 12000 / 20000 | Modbus     | 冷备 |

配置时必须做两层校验：

- 平台总量校验：所有租户授权包或已分配数量相加不能超过 `platform.lic` 的总授权。
- 租户使用校验：如果某个租户当前已用量超过新分配值，不允许直接调低，必须先停用用户、停止工程或释放节点。
- 签名包校验：如果租户授权内容来自 `platform.lic`，现场只能绑定、解绑或更换授权包，不能直接修改包内额度和能力。

租户详情页里的“授权信息”只读展示当前租户这一行，包括已分配、已使用、即将到期提醒和能力开关，不展示其他租户的授权分配。

### 5.4 授权使用量

用表格或卡片展示“已用 / 上限”。授权管理菜单里展示全平台总量和各租户分配汇总；租户详情页只展示当前租户。

全平台示例：

| 项目         | 已用  | 上限   | 状态 |
| ------------ | ----- | ------ | ---- |
| 租户         | 2     | 5      | 正常 |
| 开发用户     | 38    | 50     | 正常 |
| 工程数量     | 1     | 5      | 正常 |
| 服务运行节点 | 2     | 10     | 正常 |
| 点位         | 86000 | 100000 | 正常 |

接地气的提示语比技术错误码更重要：

- “服务运行节点名额已用完，请先删除或停用不用的服务运行节点，再注册新的服务运行节点。”
- “工程数量已用完，请先停止一个已部署工程，再部署新的工程。”
- “授权将在 14 天后到期，请联系供应商续期。”
- “当前授权不包含热备能力，不能启用热备部署。”

### 5.5 节点运行授权

展示每个服务运行节点是否拿到了可运行的节点授权。纯采集 `node_agent` 可以展示在线状态、绑定工程和采集能力校验结果，但不计入节点数量。

| 节点    | 执行方式         | 授权状态           | 最近校验            | 问题               |
| ------- | ---------------- | ------------------ | ------------------- | ------------------ |
| node-01 | Linux 容器       | 正常               | 2026-05-26 10:00:00 | 无                 |
| node-02 | Windows 原生     | 正常               | 2026-05-26 10:00:00 | 无                 |
| node-03 | Linux 原生       | 异常               | 2026-05-26 10:00:00 | 节点注册身份不匹配 |
| box-01  | Windows 原生采集 | 正常，不占节点名额 | 2026-05-26 10:00:00 | 已绑定 project-01  |

可操作项：

- 重新下发节点授权。
- 查看节点授权详情。
- 导出节点诊断信息。
- 解除离线服务运行节点占用。

解除离线服务运行节点占用必须有审计日志，避免客户反复解绑来绕过数量限制。

节点名额允许正常迁移。比如授权允许 1 个服务运行节点，用户原来把 A 机器注册为服务运行节点，后来不想用了，可以在租户管理中删除或停用 A 节点来释放名额，再把 B 机器注册为新的服务运行节点。只做采集的盒子不占用这个名额。

### 5.6 工程资产授权

工程资产授权界面服务两类人：

1. 接收方平台管理员：导出本平台机器码，导入别人给的加密工程包和工程授权。
2. 一级用户：基于对方平台机器码，加密导出工程包并生成工程授权。

导入场景展示：

- 工程包是否签名可信。
- 工程授权是否匹配当前平台机器码。
- 是否允许当前平台导入。

导出场景展示：

- 对方平台机器码。
- 是否启用工程包加密。

工程加密交付流程：

```text
接收方
  -> 在租户管理 / 授权管理导出平台机器码
  -> 发给一级用户

一级用户
  -> 在工程导出时选择“加密导出”
  -> 填入对方平台机器码
  -> 生成加密 project.ifp 和 project.lic

接收方
  -> 上传 project.ifp 和 project.lic
  -> 平台校验 project.lic 是否匹配本平台机器码
  -> 匹配后解密工程内容并导入
```

### 5.6 授权日志

授权日志用于排查争议和破解风险。

至少记录：

- 授权导入。
- 授权校验失败。
- 授权即将到期提醒。
- 超出配额拦截。
- 节点授权下发。
- 节点注册身份变化。
- 工程资产授权导入、导出、校验失败。

日志需要包含操作人、时间、来源 IP、节点 ID、授权 ID、错误原因。

## 6. 授权提醒方式

授权提醒分为四级。

| 级别       | 触发条件                  | 表现                                         |
| ---------- | ------------------------- | -------------------------------------------- |
| 普通提醒   | 授权 30 天内到期          | 顶部提示条、授权页黄色提示                   |
| 强提醒     | 授权 7 天内到期或配额 90% | 登录后弹窗一次、运维首页提示                 |
| 宽限期提醒 | 授权已到期但仍在宽限期    | 红色提示、禁止新增和扩容                     |
| 强限制     | 超过宽限期或授权被篡改    | 禁止新建、发布、部署、扩容；运行侧按策略限制 |

### 6.1 开发态策略

开发平台到期后建议：

- 允许登录查看。
- 允许备份和导出。
- 禁止新增租户。
- 禁止新增用户。
- 禁止新建工程。
- 禁止发布新版本。
- 禁止新增节点和扩容。

这样不会把客户数据锁死，也不会继续提供新增商业能力。

### 6.2 节点运行策略

运行侧不能因为授权到期突然停生产。建议：

- 授权即将到期：持续上报告警。
- 进入宽限期：继续运行已有工程，禁止新部署、新扩容、新 HA 切换配置。
- 超过宽限期：默认仍不主动停止已有运行工程，但禁止重新部署和新增采集；具体强限制策略由商务版本决定。
- 授权文件被篡改或签名无效：拒绝启动新进程；已运行进程进入告警状态并等待人工处理。

### 6.3 纯采集节点策略

只部署在盒子里做采集的 `node_agent` 尤其要谨慎：

- 到期提醒不应直接停止采集。
- 宽限期内继续采集和上行。
- 超过宽限期后，默认禁止接收新采集配置。
- 如果所属工程没有工程数量名额，应拒绝下发新的采集任务。
- 协议能力、原生采集能力属于工程能力校验，不作为采集盒子的数量配额。
- 如果必须限制运行，应优先限制新采集任务，而不是立刻停止已有采集或删除本地 WAL。

## 7. 后端实现设计

### 7.1 模块划分

建议在 `dev_core` 中新增授权域能力：

```text
dev_core
├─ licenseService
│  ├─ 导入 platform.lic
│  ├─ 校验签名
│  ├─ 校验租户授权分配
│  ├─ 计算使用量
│  ├─ 判断功能是否允许
│  └─ 生成 node-runtime-grant
├─ tenantLicenseAllocationService
│  ├─ 绑定租户授权包或配置租户授权内容
│  ├─ 校验租户分配不能超过平台总授权或签名授权包
│  └─ 计算租户授权使用量
├─ licenseController
│  ├─ 授权管理 API
│  └─ 授权诊断 API
└─ licenseAuditService
   └─ 授权审计日志
```

节点侧：

```text
node_agent
├─ grant 校验
├─ 节点注册身份校验
├─ 本地 grant 缓存
├─ 启动前能力检查
└─ 状态回传
```

运行侧：

```text
runtime_api / runtime-engine / collector
├─ 本地授权 SDK
├─ 关键能力执行前检查
└─ 授权异常上报
```

### 7.2 授权校验流程

导入平台授权：

```text
管理员上传 platform.lic
  -> dev_core 解析
  -> 校验签名
  -> 校验客户、有效期、版本
  -> 保存授权摘要
  -> 刷新授权缓存
  -> 记录授权日志
```

节点启动：

```text
node_agent 启动
  -> 向 dev_core 注册或续约
  -> 获取 node-runtime-grant
  -> 本地校验 grant 签名
  -> 校验平台实例 ID、节点 ID、节点注册身份、有效期、能力
  -> 允许后启动对应服务或 collector
```

节点离线：

```text
node_agent 无法连接 dev_core
  -> 使用本地缓存 grant
  -> 检查 grant 是否仍在有效期或离线宽限期
  -> 可用则继续运行
  -> 不可用则拒绝新启动，并保留诊断信息
```

工程资产授权：

```text
导入 project.ifp
  -> 校验工程包签名
  -> 校验 project.lic
  -> 判断 project.lic 是否匹配当前平台机器码
  -> 使用 project.lic 包装的工程密钥解密工程内容
  -> 判断平台授权是否允许工程资产导入
  -> 允许导入或拒绝导入
```

### 7.3 建议数据对象

| 对象                       | 归属                      | 说明                                               |
| -------------------------- | ------------------------- | -------------------------------------------------- |
| `PlatformLicense`          | `dev_core`                | 当前平台授权摘要，不保存私钥                       |
| `LicenseEntitlement`       | `dev_core`                | 授权能力清单，来自授权文件                         |
| `TenantLicenseAllocation`  | `dev_core`                | 租户授权分配，记录租户绑定的授权包或总量内分配额度 |
| `LicenseUsageSnapshot`     | `dev_core`                | 授权使用量快照，用于前端展示                       |
| `NodeRuntimeGrant`         | `dev_core` / `node_agent` | 下发给节点的运行授权                               |
| `NodeRegistrationIdentity` | `node_agent`              | 节点注册身份摘要，不作为我们内部出授权机器码       |
| `ProjectAssetLicense`      | `dev_core`                | 工程资产授权摘要                                   |
| `LicenseAuditLog`          | `dev_core`                | 授权相关审计日志                                   |

### 7.4 配额计算规则

授权配额按资源类型分别计算，不能混用。每次发布、部署、注册服务运行节点或新增用户时，都要同时检查平台总授权和当前租户授权分配。

| 配额             | 计算口径                                                       |
| ---------------- | -------------------------------------------------------------- |
| 服务运行节点数量 | 已注册为 `service-capable` 且处于启用/保留状态的 HostNode；不按当前 Pod 调度结果变化，纯 `collector-only` 节点不计入 |
| 工程数量         | 状态为已部署、运行中、降级运行或停止中但仍占用运行位的工程数量 |
| 开发用户数       | 启用状态的平台用户数量                                         |
| 租户数量         | 启用状态的租户数量                                             |

租户分配计算口径：

| 校验对象   | 计算口径                                                             |
| ---------- | -------------------------------------------------------------------- |
| 平台总量   | 所有租户已分配数量相加不能超过平台授权总量                           |
| 租户用量   | 当前租户已使用数量不能超过当前租户分配值                             |
| 能力开关   | 租户不能启用平台授权中没有购买的协议、HA、数据能力或工程资产保护能力 |
| 纯采集节点 | 不占服务运行节点数量，但采集任务必须隶属于当前租户已授权运行工程     |

部署判断示例：

```text
授权：服务运行节点 2 个，工程 1 个

允许：
  node-A 注册为服务运行节点
  node-B 注册为服务运行节点
  box-C 注册为纯采集节点
  project-1 部署到 node-A

不允许：
  project-2 同时部署到 node-B

允许切换：
  停止或卸载 project-1 在 node-A 的部署
  project-1 或 project-2 再部署到 node-B
```

工程从一个服务运行节点切换到另一个服务运行节点时，应先释放原部署占用的工程名额，再占用
新部署名额。site-ha、采集冗余、运行分片和异地灾备是否只算一个工程，由 HA 能力授权策略决定。

## 8. 防破解设计

### 8.1 防用户伪造授权中心

节点不能只相信接口返回。即使用户模拟一个 `dev_core`，也必须拿不出合法签名。

做法：

- 授权文件和节点 grant 都必须签名。
- 私钥不进入客户现场。
- `node_agent`、`runtime_api`、数据引擎都只信签名结果。
- `dev_core` 接口只能传递授权，不能替代本地验签。

### 8.2 防复制授权文件

做法：

- 平台授权绑定安装实例。
- 节点授权绑定平台实例 ID、节点 ID 和节点注册身份。
- 节点注册身份由节点注册流程生成，不作为我们内部给客户出授权的机器码。
- 高价值能力仍只围绕平台机器码做强校验，不要求我们给每台节点单独签发授权。

### 8.3 防修改容器或二进制

纯软件不能绝对防止管理员反编译和修改程序，但可以提高成本。

建议：

- 镜像使用固定 digest。
- 发布包记录镜像 digest 和二进制 hash。
- `node_agent` 启动前校验镜像或二进制完整性。
- 授权文件只读挂载进容器。
- 容器默认非 root、只读文件系统、不挂 Docker socket。
- `runtime_api`、数据引擎、collector 在关键执行点再次校验授权。
- 授权异常写审计日志并回传平台。

### 8.4 防改系统时间

离线环境无法完全依赖网络时间。

建议：

- 本地记录 `lastValidTime`。
- 如果系统时间倒退到 `lastValidTime` 之前，进入授权异常状态。
- 节点和 `dev_core` 都记录最近一次有效校验时间。
- 时间异常先告警，不直接删除数据或停生产。

## 9. 授权失败处理

| 场景                         | 处理方式                                   |
| ---------------------------- | ------------------------------------------ |
| 授权文件签名无效             | 拒绝导入，记录日志                         |
| 授权已过期但在宽限期         | 允许已有运行，禁止新增和扩容               |
| 超出租户或平台总量           | 禁止新增，已有对象不删除                   |
| 超出当前租户授权分配         | 禁止当前租户新增用户、发布、部署或扩容     |
| 超出服务运行节点数量         | 禁止注册新的服务运行节点或下发服务侧 grant |
| 节点注册身份不匹配           | 节点进入授权异常，不启动新服务             |
| 工程资产授权不匹配平台机器码 | 拒绝解密和导入该工程                       |
| 系统时间回退                 | 进入授权异常提醒，要求管理员处理           |

## 10. 分阶段落地建议

### 第一阶段

- 支持 `platform.lic` 导入和本地验签。
- 支持有效期、租户数量、开发用户数、工程数量、服务运行节点数量。
- 租户管理左侧菜单新增“授权管理”，展示平台授权、租户授权分配和使用量。
- 支持给每个租户配置授权内容，租户详情页只读展示当前租户授权内容。
- 授权到期和超限提醒。
- `dev_core` 发布和节点注册时做授权检查。

### 第二阶段

- 支持 `node-runtime-grant`。
- `node_agent` 本地验签和缓存 grant。
- 支持 `node_agent` 注册、服务运行节点名额占用释放、纯采集节点不占名额，以及 Linux 容器、Windows 原生、Linux 原生等执行方式授权。
- `runtime_api`、数据引擎、collector 增加关键能力校验。

### 第三阶段

- 支持工程资产授权。
- 支持工程包签名和加密。
- 支持一级用户基于对方平台机器码导出 `project.lic`。
- 支持工程授权导入和解密校验。

### 第四阶段

- 支持平台机器码强管控。
- 支持镜像和二进制完整性校验。
- 支持更细粒度协议包、HA 能力、OEM 能力授权。

## 11. 非目标

1. 不提供在线授权服务器。
2. 不使用硬件锁。
3. 不承诺在客户拥有管理员权限的机器上做到绝对不可破解。
4. 不把商务授权和用户登录权限混成一套表。
5. 不因为普通授权到期直接删除客户数据。
