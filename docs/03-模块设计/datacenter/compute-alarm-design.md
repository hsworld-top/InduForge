# 数据计算与报警开发态设计

> 更新时间：2026-08-18
> 适用范围：DataCenter 与 data_service 开发态配置

## 1. 模块边界

数据中心负责数据计算和报警的定义、组织、校验、开发调试、快照与发布契约。节点侧负责正式执行。当前报警阶段不实现节点报警计算、报警实例、确认、消音、通知投递或运行态页面。

开发态与节点运行态通过版本化契约衔接：

- 计算使用现有计算单元契约。
- 报警统一使用 `alarm.policy.v1`。
- data_service 可接收后续节点同步代理提交的报警配置增量，但不记录或展示节点来源。

## 2. 数据计算

计算单元继续包含语言、脚本、触发方式、输入绑定、输出绑定、依赖、超时和启用状态。开发态支持手动运行和调试；运行态执行、调度容错和资源隔离由节点实现。

计算脚本可通过开发态 `ctx` SDK 读取已声明的数据点或 SQL 查询输入。计算输出写入计算结果数据点，供其他计算单元、页面和报警配置继续引用。

## 3. 报警产品模型

### 3.1 两种模式

`per_target` 在界面显示为“普通报警”：

- 明确选择一个或多个兼容数据点。
- 同一套条件分别作用于每个点，每点独立形成后续运行态实例。
- 后续新增数据点不会自动加入。
- 保存后默认启用。

`derived` 在界面显示为“组合报警”：

- 配置多个输入点及唯一输入别名。
- 使用组合表达式计算结果。
- 再对结果配置状态、阈值、区间或表达式条件。
- 保存后默认停用，用户确认后再启用。

同一点可被多条策略引用，界面提示但不阻止。数据点被任何报警绑定引用时禁止删除。

### 3.2 目录

目录只用于筛选和整理：

- 支持父子目录、名称、说明和排序。
- 不提供目录启停，也不影响策略实际状态。
- 选择父目录时包含全部后代目录。
- 非空目录禁止删除。
- 前端目录面板默认收起，并记住用户展开状态。

### 3.3 条件与等级

条件类型固定为：

- `threshold`：阈值比较。
- `range`：进入或超出区间。
- `state`：状态相等或不等。
- `transition`：状态变化、上升沿或下降沿。
- `text_match`：文本相等、包含或正则匹配。
- `rate_of_change`：指定窗口变化率。
- `deviation`：相对基准值偏差。
- `offline`：数据点离线。
- `expression`：组合结果表达式。

等级固定为：

| 契约值 | 界面文案 |
| ------ | -------- |
| `info` | 提示     |
| `warning` | 警告  |
| `major` | 重要    |
| `critical` | 紧急 |

每条条件保存触发延时、清除延时和死区。无效质量或离线时暂停普通条件；`offline` 独立判断。恢复后自动清除。确认只属于后续运行态处置留痕，不是策略开关。

## 4. 通知配置

通知采用两层模型：

1. 工程默认通知：触发通知、恢复通知、重复提醒、默认模板和默认渠道。
2. 策略通知：`inherit/off/custom`，默认沿用工程设置。

重复提醒默认关闭，触发和恢复通知默认开启，内置 `runtime_inapp` 默认选中。渠道类型固定为：

- `runtime_inapp`：工程运行用户的节点站内通知。
- `webhook`。
- `dingtalk`。
- `wecom`。

本阶段只校验外部渠道 URL 和必填字段，不发送测试消息。外部密钥使用 `DATA_SERVICE_ALARM_SECRET_KEY` 与 `DATA_SERVICE_ALARM_SECRET_KEY_VERSION` 独立配置 AES-GCM 主密钥和版本，不复用工业采集密钥；普通 API 只返回 `secretStatus`，不返回明文。删除被工程默认或策略引用的渠道时返回资源占用。

模板支持中文变量插入菜单，当前变量包括点位名称、当前值、条件名称、等级和触发时间。

## 5. 数据模型

最终基线只维护以下报警表：

- `data_alarm_policy_groups`：目录。
- `data_alarm_policies`：策略主记录、通知覆盖、递增 `revision` 和契约。
- `data_alarm_policy_bindings`：普通目标点和组合输入点。
- `data_alarm_policy_conditions`：规范化条件。
- `data_alarm_project_settings`：工程默认通知。
- `data_alarm_notification_channels`：外部渠道公开配置和脱敏状态。
- `data_alarm_notification_channel_secrets`：渠道密文。
- `data_alarm_config_sync_state`：工程报警版本与最后接受序号。
- `data_alarm_config_sync_requests`：持久化幂等记录。

不再存在 `data_alarm_rules`，不保留旧接口、旧页面、迁移、回填或兼容字段。

## 6. API

策略统一位于 `/api/v1/data/projects/{projectId}/alarm-policies`，支持后端分页以及名称、模式、等级、状态和目录筛选。策略保存以事务覆盖主记录、绑定、条件和通知覆盖，并递增策略 revision 与工程报警版本。

目录位于 `alarm-policy-groups`；工程通知位于 `alarm-settings`；渠道位于 `alarm-channels`；数据点摘要位于 `datapoints/{datapointId}/alarm-summary`。所有接口使用统一 `code/msg/data/reqId` 包络和项目权限。

## 7. 配置回写

`POST /api/v1/data/projects/{projectId}/alarm-config-sync` 接收：

```json
{
  "syncEpoch": "publish-epoch",
  "sequence": 1,
  "idempotencyKey": "request-id",
  "operations": [
    {
      "resource": "policy",
      "action": "upsert",
      "id": "policy-uuid",
      "data": {}
    }
  ]
}
```

`resource` 支持 `group/policy/settings/channel`，`action` 支持 `upsert/delete`。同一请求永久幂等；同一 epoch 的旧序号拒绝；新 epoch 必须从序号 1 开始；全部操作在一个事务中按顺序执行。和普通开发态编辑同时发生时，以 data_service 实际提交顺序的最后一次提交为准。

该接口由后续 dev_core 节点同步代理使用项目写权限调用。data_service 不关心上报来自哪个节点。一个工程只有一个节点可以开启同步资格的约束，由后续发布配置实现，不属于本阶段。

## 8. 前端交互

报警主页使用紧凑分页表格，列为名称、数据点、条件、最高等级、状态、目录和操作。空状态不渲染编辑器、试算或契约面板。

普通报警抽屉的顺序是：名称与目录、选择点、逐条添加条件、高级设置、开发调试。首次创建有一条“高于”阈值条件，等级为警告，延时和死区为 0。组合报警复用同一抽屉骨架，但增加输入别名和组合表达式。

试算优先使用用户输入的简单模拟值；契约以只读 JSON 显示，二者都在“开发调试”折叠区中。数据点详情提供报警摘要和新建入口；数据点列表批量入口只处理当前明确选中的点，并创建一条统一维护的普通报警，不支持“全部结果”。

## 9. 快照与 Artifact

工程快照导出目录、策略、绑定、条件、通知设置、渠道和渠道密文。覆盖导入时先删除报警引用，再删除渠道、目录和数据点；恢复时先恢复数据点、目录和渠道，再恢复策略与通知，整个过程使用单事务。

Artifact 的 `alarms` 区块包含：

- `schemaVersion: alarm.policy.v1`。
- 目录、普通与组合策略。
- 绑定和条件。
- 工程通知与策略通知覆盖。
- 渠道公开定义。
- 密钥引用和密钥版本。

Artifact 不包含密钥明文或密文；实际节点密钥注入由后续发布实现。

## 10. 当前非目标

- 节点侧报警计算与状态机。
- 报警实例、确认、消音和运行态处置审计。
- 通知队列、真实投递、失败重试和投递记录。
- 发布页“同步报警配置”开关与节点同步资格分配。
- 开发态查看节点在线配置。
- 维护时段、抑制策略、优先级、自动等级升级和旧规则兼容。
