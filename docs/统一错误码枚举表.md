# 统一错误码枚举表

## 1. 目的

本文档是 `indu-forge` 当前所有项目对外 HTTP 错误码的唯一正式规范入口，适用于：

- `dev_core`
- `data_service`
- `dev_ide`
- `datacenter`
- `designer`
- 后续新增的同类 HTTP 服务

后续新增接口、修改错误语义或新增错误码时，必须同步更新本文档，禁止在模块内私自定义另一套编号规则。

## 2. 统一响应约定

所有 HTTP JSON 接口统一返回以下结构：

```json
{
  "code": 0,
  "msg": "操作成功",
  "data": null,
  "reqId": "req-example-1"
}
```

字段含义：

- `code`：业务码，`0` 为唯一成功码，非 `0` 均为失败
- `msg`：对外错误或成功提示
- `data`：响应数据；错误时通常为 `null`
- `reqId`：请求链路标识

补充规则：

- 业务成功失败看 `code`
- 技术异常看 HTTP 状态码
- 二进制/文件流接口允许成功时直接返回文件流，不强制使用 JSON 包络
- 二进制/文件流接口一旦返回错误，仍必须使用统一 JSON 包络

## 3. HTTP 状态码边界

### 3.1 业务失败

业务失败指请求被系统正常接收和处理，但业务条件不满足，例如：

- 资源不存在
- 名称重复
- 权限不足
- 状态不允许
- 参数不满足业务规则

这类场景统一返回：

- `HTTP 2xx`
- `code != 0`

### 3.2 技术异常

技术异常指请求没有被系统正常处理完成，例如：

- 鉴权链路失败
- 请求体无法解析
- 下游服务不可用
- 数据库/缓存/对象存储异常
- 未捕获异常

这类场景统一返回：

- `HTTP 4xx/5xx`
- `code != 0`

## 4. 编号规则

当前统一编号规则如下：

- `0`：唯一通用成功码
- `1xxxx`：认证、鉴权、权限类错误
- `2xxxx`：参数校验、资源状态、业务资源类错误
- `3xxxx`：系统、依赖、未知异常类错误

当前仓库内存在两种来源：

1. `dev_core` 由历史 `A/B/Cxxxx` 码按映射规则公开为整数码
2. `data_service` 使用自身公开整数码常量

### 4.1 dev_core 映射规则

`dev_core` 历史码对外映射为整数：

- `A0001` -> `10001`
- `A1002` -> `11002`
- `B1001` -> `21001`
- `C0001` -> `30001`

映射公式：

- `A + nnnn` -> `10000 + nnnn`
- `B + nnnn` -> `20000 + nnnn`
- `C + nnnn` -> `30000 + nnnn`

### 4.2 data_service 规则

`data_service` 当前直接维护公开整数码常量，对外不再暴露旧字符串码。

## 6. 使用规则

### 6.1 必须遵守

- 新接口成功必须返回 `code = 0`
- 业务失败不得复用 `300xx` 系统类错误码
- 技术异常不得复用 `2xxxx` 业务类错误码
- 前端页面不得再解析旧字段 `success/errorCode/message/requestId`
- 新增错误码必须同步更新本文档和调用方说明

### 6.2 禁止事项

- 禁止在单个模块私自新增另一套字符串错误码作为对外契约
- 禁止同一错误语义在不同接口使用不同整数码
- 禁止把对象存储、数据库、网络超时等技术故障压成 `200 + 业务错误码`

## 7. 后续新增规则

后续新增错误码时，按以下顺序执行：

1. 先确认是业务失败还是技术异常
2. 选择正确号段
3. 在代码中定义
4. 在本文档补充编号、名称、说明、来源
5. 在接口文档中补充该错误码的适用接口

如果无法确定归属，优先按“技术异常”处理，再在评审中收敛。
