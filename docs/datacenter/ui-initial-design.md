# 数据中心 UI 初版设计

> 更新时间：2026-04-24
> 适用范围：`datacenter` 前端信息架构、页面结构与首期改造边界。

## 1. 设计目标

数据中心用于构建、整理和预览项目级数据点，保证设计中心和运行态能够通过统一数据点契约消费数据。

核心目标：

1. 以“数据点”为中心组织数据中心，而不是以具体协议或连接类型为中心。
2. 支持关系库、MQTT、Kafka、TDengine、OPC UA、西门子、三星设备等后续接入扩展。
3. 将接入、计算、报警统一解释为围绕数据点的生产、加工和规则配置能力。
4. 明确数据中心、设计中心、运行态节点侧的职责边界。
5. 保留开发态预览、调试和契约检查能力，但不把数据中心做成运行态运维后台。

## 2. 职责边界

### 2.1 数据中心职责

1. 管理接入源配置。
2. 从接入源生成或维护数据点。
3. 查看、筛选、预览和校验数据点。
4. 构建计算单元脚本任务。
5. 构建报警规则并预览运行态执行契约。
6. 检查数据点、接入源、计算任务、报警规则是否满足运行态消费要求。

### 2.2 设计中心职责

设计中心负责在页面和组件上绑定数据点。数据中心不承载页面级数据源编排，也不决定具体组件如何展示数据。

### 2.3 运行态节点侧职责

运行态节点侧负责真实执行查询、订阅、计算任务和报警规则。报警实例、报警事件、确认、消音等运行态交互不在数据中心展示。

## 3. 总体对象关系

```text
接入源 -> 数据点 -> 设计中心绑定
               -> 运行态查询/订阅
               -> 计算单元读取
               -> 报警单元引用

计算单元 -> 可输出 calc.* 数据点
         -> 也可执行写库、发布消息、外部请求等脚本任务

报警单元 -> 构建规则与运行态契约
         -> 运行态节点侧产生实例与事件
```

关键原则：

1. 数据点是数据中心的主对象。
2. 接入源是数据点来源。
3. 计算单元可以生产数据点，也可以作为有副作用的脚本任务。
4. 报警单元只构建规则，不展示运行态事件。
5. 后续新增协议和设备时，扩展接入源类型，不扩展一级导航。

## 4. 一级导航

数据中心一级导航固定为：

```text
数据点 / 接入源 / 计算单元 / 报警单元
```

不设置独立的“发布”和“日志”一级模块。

辅助能力处理方式：

1. `数据契约检查`：作为顶部全局动作或对象详情动作存在。
2. `记录`：跟随具体对象展示，例如连接测试记录、查询预览记录、MQTT 消息记录、计算调试记录、报警试算记录。

## 5. 数据点页面

### 5.1 页面定位

数据点页面是数据中心默认首页，定位为项目级数据资产目录。

它不鼓励用户手动创建数据点。数据点主要由接入源、计算单元、报警单元自动生成或维护。

### 5.2 页面结构

建议采用四区布局：

1. 左侧一级导航：固定显示 `数据点 / 接入源 / 计算单元 / 报警单元`。
2. 二级筛选栏：按来源类型、消费方式、状态、设备/分组/标签筛选。
3. 主工作区：数据点指标、搜索、列表、批量动作。
4. 右侧详情区：选中数据点的预览、来源、引用、权限和记录。

### 5.3 列表核心字段

数据点列表建议展示：

| 字段 | 说明 |
| --- | --- |
| Path | 数据点唯一路径 |
| 名称 | 用户可读名称 |
| 来源 | `db.query`、`mqtt.tag`、`calc.output`、`alarm.state` 等 |
| 消费方式 | 运行态查询、运行态订阅、仅开发态预览 |
| 当前值 | 最近预览值或运行态同步值 |
| 质量 | `good`、`bad`、`unknown` 等 |
| 状态 | `active`、`invalid`、`error` |
| 引用 | 设计中心页面、计算单元、报警规则引用情况 |

### 5.4 详情区能力

数据点详情建议包含：

1. 基础属性：Path、名称、类型、单位、精度、标签。
2. 预览与验证：当前值、最近变化、质量、更新时间。
3. 运行态权限：是否可查询、是否可订阅、是否对运行态角色可见。
4. 来源追踪：跳转接入源、查询、Tag、计算单元或报警规则。
5. 引用关系：设计中心页面、计算单元、报警规则。
6. 记录：最近预览、解析失败、状态变化等对象级记录。

## 6. 接入源页面

### 6.1 页面定位

接入源统一管理所有能生产数据点的外部系统。

接入源不是简单连接表单，而是承载：

1. 连接配置。
2. 解析或映射规则。
3. 开发态预览。
4. 数据点生成和同步。

### 6.2 接入源分类

| 分类 | 示例 |
| --- | --- |
| 数据库 / 时序库 | MySQL、PostgreSQL、SQL Server、TDengine |
| 消息 / 流 | MQTT、Kafka、WebSocket、HTTP、Redis |
| 工业协议 | OPC UA、Modbus、OPC DA |
| 设备 / 厂商模板 | 西门子 PLC、三星设备等 |

### 6.3 新增接入入口

创建接入源时采用“模板优先、协议高级”的入口顺序。

1. 默认入口：从设备或系统模板创建。
2. 高级入口：从技术协议创建。
3. 其他入口：从已有配置导入。

示例：

1. 普通用户选择“西门子 PLC”，再填写设备参数和地址表。
2. 高级用户选择“S7 协议”，直接配置协议连接和地址映射。
3. 普通用户选择“MQTT Broker”，再配置 Topic 和 Tag 自动发现。
4. 高级用户选择“Kafka”，直接配置 Broker、Topic、Schema 和样本预览。

### 6.4 接入源详情标签

每类接入源详情统一包含：

```text
概览 / 配置 / 解析或映射 / 预览 / 数据点 / 记录
```

不同接入类型只在标签内部体现差异：

1. 关系库：表、SQL 查询、查询预览、生成 `db.query` 数据点。
2. MQTT/Kafka：Topic、Schema、消息样本、Tag 或流式数据点。
3. OPC UA/S7：节点浏览、地址表、订阅预览、设备点位。
4. 设备模板：厂商参数、地址表、驱动选项、底层协议映射。

## 7. 计算单元页面

### 7.1 页面定位

计算单元是可调度脚本任务，不强制输出数据点。

它支持三种模式：

| 模式 | 说明 |
| --- | --- |
| 输出数据点模式 | 脚本结果生成或更新 `calc.*` 数据点 |
| 执行任务模式 | 不输出数据点，直接写库、发布消息或调用外部请求 |
| 混合模式 | 同时输出 `calc.*` 数据点并执行外部动作 |

### 7.2 页面结构

计算单元页面建议采用：

1. 左侧对象列表：计算单元列表、触发方式筛选、能力分类筛选。
2. 主工作区：脚本编辑器、模式选择、触发配置、调试输入输出。
3. 能力库面板：平台封装方法文档、示例插入、权限说明。
4. 右侧详情区：输出模式、触发策略、能力权限、副作用检查、运行态契约。

### 7.3 脚本能力库

计算脚本建议注入统一 `ctx` 能力对象。

基础能力：

| 方法 | 说明 |
| --- | --- |
| `ctx.datapoint.get(path)` | 获取数据点当前值 |
| `ctx.sql.query(source, sql, args)` | 对关系库接入源执行只读参数化 SQL |
| `ctx.sql.execute(source, sql, args)` | 对目标库执行写入 SQL |
| `ctx.mqtt.publish(source, topic, payload)` | 发布 MQTT 消息 |
| `ctx.kafka.publish(source, topic, payload)` | 发布 Kafka 消息 |
| `ctx.http.get(url, options)` | 调用外部 GET 请求 |
| `ctx.http.post(url, body, options)` | 调用外部 POST 请求 |
| `ctx.math.*` | 常见数学、统计、取整、限幅方法 |
| `ctx.text.*` | 字符串格式化、正则、模板方法 |
| `ctx.json.*` | JSONPath、对象路径读取、转换方法 |

示例：

```javascript
const point = await ctx.datapoint.get("mqtt.EMQX.LineA.temperature");

const rows = await ctx.sql.query(
  "生产库",
  "SELECT rated_power FROM device WHERE id = ?",
  [inputs.deviceId]
);

outputs.power = point.value * rows[0].rated_power;
```

执行任务示例：

```javascript
const total = await ctx.sql.query(
  "生产库",
  "SELECT SUM(power) AS value FROM meter WHERE day = ?",
  [inputs.day]
);

await ctx.sql.execute(
  "报表库",
  "INSERT INTO daily_power(day, value) VALUES(?, ?)",
  [inputs.day, total.rows[0].value]
);

await ctx.mqtt.publish("EMQX", "report/daily_power", {
  day: inputs.day,
  value: total.rows[0].value
});
```

### 7.4 触发方式

计算单元支持：

1. 手动调试：开发态执行，用于验证脚本。
2. 定时执行：按 Cron 或固定周期执行。
3. Bool 数据点触发：建议按边沿触发，例如 `false -> true` 执行一次。
4. 数据点变化触发：输入数据点变化后执行。

Bool 数据点触发必须具备防重复能力：

1. 支持边沿触发。
2. 支持最小触发间隔。
3. 支持执行中跳过、排队一个或禁止并发等策略。

### 7.5 副作用治理

执行任务模式和混合模式存在副作用，必须治理：

1. SQL 写入必须显式授权目标接入源。
2. SQL 必须参数化。
3. MQTT/Kafka 发布必须限制 Topic 范围。
4. HTTP 请求必须使用域名白名单、超时和密钥引用。
5. 支持超时、重试、失败策略。
6. 支持幂等键，避免定时或触发抖动造成重复写入或重复发布。
7. 调试时应明确提示 dry-run 或真实执行。
8. 所有副作用动作应保留对象级调试记录和审计信息。

## 8. 报警单元页面

### 8.1 页面定位

报警单元只负责构建规则、校验目标数据点、样本试算和预览运行态节点执行契约。

数据中心不展示：

1. 运行态报警实例。
2. 运行态事件时间线。
3. 最近事件。
4. 确认、消音等运行态操作。

这些能力属于运行态节点侧和运行态页面。

### 8.2 页面结构

报警单元页面建议采用：

1. 左侧规则分组：按业务分组、规则类型、状态筛选。
2. 主工作区：规则构建器、规则列表。
3. 右侧详情区：目标数据点检查、样本试算、节点执行契约预览。

### 8.3 规则构建器

规则配置建议优先可视化，表达式作为高级能力。

基础字段：

| 字段 | 说明 |
| --- | --- |
| 目标数据点 | 规则引用的数据点 path |
| 数据质量要求 | 如 `quality == good` |
| 规则类型 | 高高、高、低、低低、偏差、变化率、表达式 |
| 触发条件 | 阈值、持续时间、触发延时 |
| 清除条件 | 清除阈值、清除延时、回差 |
| 严重度 | 提示、低、中、高、紧急 |
| 抑制策略 | 合并窗口、重复触发策略 |
| 消息模板 | 运行态报警消息模板 |

### 8.4 样本试算与契约预览

数据中心可提供开发态试算：

1. 使用当前数据点值试算。
2. 使用用户手工输入样本试算。
3. 检查目标数据点是否 active。
4. 检查目标数据点是否能在运行态订阅或查询。
5. 生成节点侧执行契约预览。

契约预览示例：

```json
{
  "ruleType": "high",
  "targetPath": "mqtt.EMQX.LineA.temperature",
  "condition": "point.value > 80 && point.quality == \"good\"",
  "onDelayMs": 10000,
  "clearCondition": "point.value < 75",
  "offDelayMs": 30000,
  "severity": 4
}
```

## 9. 数据契约检查

数据契约检查作为顶部动作或对象详情动作存在，不作为一级模块。

检查内容包括：

1. 数据点是否失效。
2. 数据点来源是否可用。
3. 设计中心引用是否仍有效。
4. 运行态查询或订阅契约是否完整。
5. 计算单元脚本是否能在节点侧执行。
6. 计算单元副作用动作是否具备授权和白名单。
7. 报警规则目标数据点是否有效。
8. 报警规则是否能生成节点侧执行契约。

## 10. 记录展示规则

记录不做独立日志中心，跟随对象详情展示。

| 对象 | 记录内容 |
| --- | --- |
| 接入源 | 连接测试、配置变更、预览失败 |
| 查询 | 执行记录、保存记录、数据点同步记录 |
| MQTT/Kafka | 消息样本、解析失败、Tag 发现记录 |
| 数据点 | 值预览、质量变化、来源失效 |
| 计算单元 | 调试运行、脚本错误、权限检查、副作用执行结果 |
| 报警单元 | 规则保存、目标点校验、样本试算、契约生成 |

## 11. 首期落地建议

### 11.1 第一阶段：四模块骨架

1. 建立 `数据点 / 接入源 / 计算单元 / 报警单元` 一级导航。
2. 数据点作为默认首页。
3. 接入源承接当前连接树能力。
4. 保留现有关系库、MQTT 的表、查询、订阅、Tag 能力。

### 11.2 第二阶段：数据点详情增强

1. 补齐数据点详情抽屉。
2. 展示来源、引用、运行态权限。
3. 增加失效点清理和来源跳转。
4. 增加数据契约检查入口。

### 11.3 第三阶段：接入源统一化

1. 关系库和 MQTT 迁入接入源列表。
2. 新增“设备/系统模板优先”的创建入口。
3. 保留“技术协议”高级入口。
4. 为 Kafka、TDengine、OPC UA、S7 预留类型和详情标签。

### 11.4 第四阶段：计算单元任务化

1. 计算单元支持输出数据点、执行任务、混合模式。
2. 增加脚本能力库 UI。
3. 增加定时和 Bool 数据点触发配置。
4. 增加副作用权限检查。

### 11.5 第五阶段：报警单元规则化

1. 建立规则构建器。
2. 支持目标数据点选择与校验。
3. 支持样本试算。
4. 支持节点侧执行契约预览。

## 12. 关键结论

1. 数据点是数据中心默认主对象。
2. 接入源统一承载关系库、消息、工业协议和设备模板。
3. 计算单元是可调度脚本任务，不强制输出数据点。
4. 报警单元只做规则构建，运行态事件不在数据中心展示。
5. 数据契约检查是动作，不是一级模块。
6. 记录跟随对象，不建设独立日志中心。
7. 后续协议和设备扩展不改变一级导航。
