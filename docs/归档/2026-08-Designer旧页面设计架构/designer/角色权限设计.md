# Designer 角色权限设计

## 1. 背景与目标

`designer` 负责低代码页面的设计态配置，最终工程会通过 `dev_core` 发布为部署包，并由节点侧运行态引擎独立加载运行。当前工程运行态用户、角色和用户角色绑定已经由 `dev_ide` 面向工程管理，`designer` 需要消费这些运行态角色，把页面访问、组件可见、组件可操作等权限意图配置进页面设计结果中。

本设计的目标是建立一套轻量、可发布、可由节点侧独立解释的页面角色权限模型：

- 页面可以启用或关闭本页运行态权限控制。
- 页面访问直接配置允许运行态角色，未配置时默认不限制。
- 页面内部可以创建可复用的权限方案，每个权限方案表达一组允许运行态角色。
- 组件引用权限方案来控制可见和可操作能力。
- 预览时按运行态用户模拟最终节点侧权限效果。
- 发布包携带完整权限快照和权限索引，节点侧运行态不依赖 `dev_core` 在线查询权限。

## 2. 非目标

本设计不处理 `designer` 编辑器自身的编辑权限，也不改变 `dev_ide` 管理端用户的系统角色体系。

第一阶段不引入以下能力：

- 权限方案的 deny 规则。
- 时间、班组、组织、数据范围等条件权限。
- 动作系统的独立权限编排。
- 跨页面共享权限方案。
- 节点侧运行态向开发态服务回查权限。

## 3. 系统边界

整体模式是：开发态配置，发布态快照，节点侧独立执行。

`dev_ide` 继续负责工程运行态用户、角色和用户角色绑定的管理。

`designer` 负责消费当前工程的运行态角色，在页面属性和组件属性中完成权限配置，并在预览时按运行态用户模拟权限结果。

`dev_core` 作为开发态后端，负责保存页面设计数据、校验角色引用是否合法，并在发布时把运行态用户、角色、绑定关系和页面权限配置编译进工程包。

节点侧运行态引擎加载工程包后，基于本地快照完成登录、角色解析、页面访问判断、组件可见判断、组件可操作判断和动作执行前拦截。

关键原则：节点侧运行时不依赖 `dev_core` 查询权限。`dev_core` 只负责发布前把权限资料打包完整。

## 4. 核心概念

### 4.1 页面权限控制

每个页面有一个“启用本页运行态权限控制”开关。

开关关闭时，本页页面访问和组件权限均不生效，即使页面内已经保存了角色和权限方案配置，也不限制运行态用户访问或操作。设计器 UI 应将权限配置区域置灰，并提示“关闭后本页访问和组件权限均不生效”。

开关开启时，页面访问角色和组件权限方案开始生效。

### 4.2 页面访问角色

页面访问不引用权限方案，而是直接配置允许运行态角色。

页面权限控制开启后：

- 页面未配置访问角色：不限制页面访问。
- 页面配置了访问角色：当前运行态用户至少拥有其中一个角色才允许进入页面。

角色引用以 `roleId` 为主，同时保留 `roleCode`、`roleName` 快照用于设计器显示。发布前由 `dev_core` 按 `roleId` 校验角色仍属于当前工程且处于启用状态。

### 4.3 权限方案

权限方案属于页面内部，不跨页面共享。它只表达“一组允许运行态角色”，不表达具体能力。

权限方案至少包含：

- 稳定 ID：用于组件引用，方案改名不能导致引用断裂。
- 名称：用于设计器展示。
- 角色集合：保存 `roleId` 和显示快照。

第一阶段只支持 allow 语义：当前运行态用户只要命中方案内任一角色，即视为满足该方案。未命中则不满足。多角色用户按“任一角色命中即通过”处理。

### 4.4 组件权限引用

组件不直接散落配置角色，而是引用页面内的权限方案。

第一阶段组件支持两类权限引用：

- 可见：决定组件是否显示或渲染。
- 可操作：决定按钮、输入框、选择器等交互控件是否可点击、可编辑、可触发交互。

组件未配置可见方案时默认可见。组件未配置可操作方案时默认可操作。只有配置了方案，才限制对应能力。

可操作失败时，运行态应同时处理两层效果：

- UI 层表现为禁用、只读或不可点击。
- 动作执行前再次拦截，避免脚本或事件绕过 UI 状态。

第一阶段不单独给每个事件动作配置权限。组件不可操作时，该组件上的点击、提交、写点位、调用接口、跳转等用户触发动作不执行。后续如确有需要，再扩展动作级权限。

## 5. 继承与默认行为

默认行为遵循“不配置则不限制”。

页面权限控制关闭时，本页所有权限配置均不生效。

页面权限控制开启时：

- 页面访问角色为空：页面访问不限制。
- 组件可见方案为空：组件可见不限制。
- 组件可操作方案为空：组件可操作不限制。
- 组件引用的方案不存在或失效：视为配置错误，发布前应阻断；预览态应给出明确诊断。

容器组件继承规则：

- 容器不可见时，子组件自然不可见。
- 容器不可操作不自动影响子组件，只影响容器自身交互。

不自动继承“不可操作”是为了避免隐式权限链条过深，降低排查复杂度。若业务确实需要成组禁用，设计者可以在子组件或组件组能力中显式引用相同权限方案。

## 6. 设计器配置体验

UI 改造延续现有 `designer` 的产品工具风格：右侧属性面板保持约 272px 宽度，继续使用 Element Plus 小号控件、浅灰分组标题、紧凑表单行和角色标签样式。权限配置不新增独立复杂页面，也不以大弹窗作为主流程，优先嵌入页面属性和组件属性面板。

页面属性面板中，现有“运行态”分组继续保留给打开方式、缓存模式、预加载等运行配置。页面权限相关能力单独拆为“运行态权限控制”分组，避免和缓存策略、预加载策略等概念混淆。

“运行态权限控制”分组包含：

- 启用本页运行态权限控制。
- 页面访问角色选择。

开关关闭时，本页页面访问和组件权限均不生效，相关配置整体置灰但保留已配置内容。开关开启后，页面访问角色多选开始生效。角色来源于当前工程运行态角色；未选择角色表示页面访问不限制，选择后只有命中角色的运行态用户可进入页面。

页面属性面板中再新增“权限方案”分组，用于管理页面内可复用的角色集合。每个方案以紧凑卡片展示：

- 方案名称。
- 包含的角色标签。
- 当前引用数量。
- 编辑入口。

权限方案管理支持创建、编辑、删除和查看引用情况。删除已被组件引用的方案时，应阻止删除或要求先解除引用。

组件属性面板增加“权限控制”配置区：

- 可见权限方案。
- 可操作权限方案。

组件权限控制区应显示当前页面权限控制状态，例如“页面已启用”或“页面未启用”。当页面权限控制关闭时，组件权限配置区可展示当前引用但整体置灰，避免用户误解为正在生效。

组件只通过两个下拉项引用页面内权限方案，不直接配置角色：

- “可见权限方案”未选择时默认可见；选择后按方案角色判断。
- “可操作权限方案”未选择时默认可操作；选择后按方案角色判断。

第一阶段不在 UI 中展开动作级授权配置。组件不可操作时，其交互状态置灰或只读，并且该组件上的用户触发动作在执行前被统一拦截。

角色选择数据来自当前工程运行态角色列表。设计器展示角色名称和角色编码，但保存引用时以 `roleId` 为准。

权限相关提示使用轻量信息条展示，例如：

- 页面未选择访问角色时，提示“未选择角色时不限制页面访问”。
- 当前预览用户未命中可操作方案时，提示“按钮置灰，点击动作不会执行”。
- 权限方案被引用时，删除入口提示先解除引用。

## 7. 预览设计

设计器预览只按运行态用户预览，不提供按角色预览。

预览入口沿用当前顶部工具栏的“预览”下拉，不新增独立按钮。在该下拉面板中增加“预览身份”区域，提供运行态用户选择能力。用户选择需要持久化，避免每次预览都重新选择。持久化范围建议为当前工程，必要时可以细化到当前浏览器和当前登录开发态用户。

预览用户列表展示：

- 运行态用户显示名称。
- 运行态账号。
- 已绑定角色标签或角色摘要。
- 当前选中标识。

预览时，设计器根据选中的运行态用户解析其绑定的运行态角色集合，并模拟节点侧运行态权限判断：

- 页面访问不通过时，预览显示无权限访问状态。
- 组件可见不通过时，不显示该组件或以运行态一致的方式隐藏。
- 组件可操作不通过时，组件呈现禁用或只读状态。
- 用户触发动作前再次进行可操作判断，不通过则拦截动作。

若没有选择预览用户，预览应使用明确的默认身份。推荐默认使用当前工程的运行态管理员用户；若不存在运行态用户，则以无角色身份预览，并在预览下拉中提示需要选择用户。

## 8. 发布与运行态契约

发布包需要携带两类信息：

1. 运行态安全快照：用户、角色、用户角色绑定、角色授权等工程运行态安全数据。
2. 页面权限配置与运行态权限索引：由 designer 页面权限配置编译得到，供节点侧快速判断。

现有发布流程中已经存在 `runtime-security.json`，用于携带运行态用户、角色、绑定和授权记录。页面角色权限可以继续与该快照协同工作，但不应要求节点侧从开发态服务补充数据。

建议发布时生成轻量权限索引，而不是要求节点侧每次遍历页面树判断权限。权限索引至少覆盖：

- 页面访问：`pageId -> allowedRoleIds/roleCodes`。
- 组件可见：`pageId + componentId -> schemeId -> roleIds/roleCodes`。
- 组件可操作：`pageId + componentId -> schemeId -> roleIds/roleCodes`。

页面 JSON 中仍保留设计态配置，便于排查和后续迁移；节点侧运行态优先消费编译后的权限索引。

## 9. 节点侧运行态判定

节点侧运行态引擎加载工程包后，先建立运行态用户、角色、绑定关系和权限索引的内存结构。

运行时判断流程：

1. 用户登录后，根据运行态用户 ID 获取其角色集合。
2. 路由进入页面前，判断页面访问角色。
3. 页面渲染时，对组件可见权限进行判断。
4. 组件交互状态计算时，对组件可操作权限进行判断。
5. 用户触发动作前，再次检查组件可操作权限。

页面访问、组件可见和组件可操作的命中规则统一为：没有配置则允许；配置了角色或方案则当前用户任一角色命中即允许；未命中则拒绝。

## 10. 校验与异常处理

保存或发布前需要校验：

- 页面访问角色引用的 `roleId` 属于当前工程。
- 权限方案引用的 `roleId` 属于当前工程。
- 角色处于启用状态。
- 组件引用的 `schemeId` 在当前页面存在。
- 删除权限方案时不存在组件引用，或先完成引用清理。

建议发布阶段采用严格校验：

- 角色不存在：阻止发布，并指出页面或组件位置。
- 角色被禁用：阻止发布，并指出角色名称和引用位置。
- 权限方案不存在：阻止发布。
- 页面权限控制关闭：不阻止发布，但编译出的本页权限索引应标记为不启用或直接不生成限制项。

预览阶段应尽量给出设计诊断，不应静默忽略错误引用。对于失效引用，可在属性面板和预览诊断区域提示。

## 11. 与现有授权表的关系

`project_role_grants` 已经具备资源类型、资源 ID、动作、allow/deny、条件等更通用的授权表达能力。本设计第一阶段不直接把 designer 组件权限编辑体验暴露为 grant 编辑器。

原因是页面和组件权限天然跟页面 Schema 生命周期绑定。组件复制、删除、撤销重做、页面复制等操作如果完全拆成独立授权表，会显著增加同步复杂度。

推荐方式是：

- 设计态以页面 Schema 内的权限配置为主。
- `dev_core` 在保存或发布时进行角色引用校验。
- 发布时编译成节点侧运行态可直接消费的权限索引。
- 后续如需与 `project_role_grants` 打通，可在发布阶段生成等价 grant 快照，或为高级场景提供独立转换层。

## 12. 后续扩展方向

后续可以在不破坏第一阶段模型的基础上扩展：

- 跨页面共享权限方案。
- 动作级权限，例如某个事件中的写点位动作单独控制。
- 条件权限，例如班组、时段、设备区域、数据范围。
- 权限诊断面板，集中展示页面内所有权限引用和失效引用。
- 权限方案复制、批量替换和引用追踪。

这些能力不进入第一阶段，避免把页面设计人员直接暴露在复杂 ABAC 或 grant 模型中。

## 13. 推荐第一阶段范围

第一阶段建议只实现以下闭环：

- designer 拉取当前工程运行态用户和角色。
- 页面属性支持启用本页运行态权限控制。
- 页面属性支持配置页面访问角色。
- 页面属性支持管理页面内权限方案。
- 组件属性支持引用权限方案控制可见和可操作。
- 预览下拉支持选择运行态用户，并持久化选择。
- 发布前校验角色和方案引用。
- 发布包生成节点侧可消费的权限索引。
- 节点侧运行态完成页面访问、组件可见、组件可操作和动作执行前拦截。

这个范围能覆盖当前核心诉求，同时保留后续扩展到动作级、条件级和跨页面复用的空间。
