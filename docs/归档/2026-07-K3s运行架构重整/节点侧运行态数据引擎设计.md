# 节点侧运行态数据引擎设计

## 1. 文档定位

本文档定义工程发布到节点后，节点侧数据引擎如何按工程数据能力自动生成运行拓扑，启动容器化组件或原生采集进程，承载采集、存储、报警、计算和查询能力。

本文档面向最终运行态，不约束开发态 `data_service` 的实现技术。开发态负责配置、调试和生成发布快照；运行态以性能、稳定性、可横向扩展和可运维为第一优先级。

## 2. 设计目标

1. 一个服务站点工程在节点侧对应一个独立 `docker-compose` 运行栈；原生采集站点对应一组由 `node_agent` 托管的 collector 子进程。
2. 数据引擎按工程实际使用能力裁剪启动，不启动未使用的内置库、采集器、报警、计算和内部组件。
3. 支持用户自由搭配 IF 内置库与外部接入源；外部接入源只由数据引擎连接，不随工程运行栈部署。
4. 支持同一类接入源存在多个实例，例如多个 S7 连接、多个 MySQL 连接、多个 Redis 连接。
5. 支持采集盒子独立部署，采集能力靠近现场设备，写入、报警、计算、查询和 IF 内置库集中在服务站点。
6. 支持轻量单机、高吞吐单机、双机主备和多节点分片等部署档位。
7. 采集、写入、报警、计算和查询可以按角色横向扩容。
8. 内部消息总线、协调组件和 IF 消息库边界清晰，禁止把 IF 消息库作为数据引擎内部事件总线。
9. 内置组件优先选用成熟、许可证清晰、可离线分发的开源版本。

## 3. 非目标

1. 不把平台侧 `data_service` 原样搬到节点侧运行。
2. 不要求所有工程都启动完整的数据能力全家桶。
3. 不让 `node_agent` 理解协议采集、报警规则和查询语义。
4. 不用 IF 消息库承载采集事件、报警事件、任务分发或内部可靠队列。
5. 不在首版引入 Rust 作为协议解析或计算算子的必选技术。
6. 不自研分布式可靠消息队列。

## 4. 名称与边界

### 4.1 运行态数据引擎

现有高层文档中使用 `runtime_data_service` 表示工程级运行态数据引擎组。本文档沿用这个架构名，同时建议运行二进制和镜像命名为 `runtime-data-engine`，通过不同 `role` 启动不同职责。

```text
runtime_data_service 组
└─ induforge/runtime-data-engine
   ├─ --role=collector --protocol=s7
   ├─ --role=writer
   ├─ --role=alarm
   ├─ --role=compute
   ├─ --role=scheduler
   └─ --role=bootstrap
```

### 4.2 IF 内置库

IF 内置库是随工程运行栈按需启动的工程私有能力：

| 能力     | 运行态用途                                      | 启动规则                             |
| -------- | ----------------------------------------------- | ------------------------------------ |
| IF关系库 | 业务表、报警实例、报警事件、运行态关系查询      | 工程使用 `builtin.relation` 时启动   |
| IF时序库 | 数据点历史、趋势、采集历史、计算采样历史        | 工程使用 `builtin.timeseries` 时启动 |
| IF实时库 | 当前值、质量码、短期状态、缓存                  | 工程使用 `builtin.realtime` 时启动   |
| IF消息库 | 工程 MQTT Broker、设备主题、模拟数据、MQTT 订阅 | 工程使用 `builtin.message` 时启动    |

同一类型可以有多个逻辑实例。默认做法是同类型内置库在工程 compose 内启动一个物理服务，通过 schema、database、key namespace、topic prefix 等方式隔离多个逻辑实例。只有部署档位明确要求时，才考虑同类型多物理实例。

### 4.3 外部接入源

外部接入源由用户提供服务端资源，InduForge 只提供连接和运行能力：

```text
external.mysql
external.postgresql
external.sqlserver
external.redis
external.mqtt
protocol.s7
protocol.opcua
protocol.modbus
protocol.http
```

外部接入源不会被写入工程 compose 的服务列表，只会进入数据引擎运行配置和连接池。

## 5. 总体架构

```text
project-compose
├─ project_nginx
├─ client_engine
├─ runtime_api[n]
├─ data_engine_collector_<protocol>[n]
├─ data_engine_writer[n]
├─ data_engine_alarm[n]
├─ data_engine_compute[n]
├─ data_engine_scheduler[leader/standby]
├─ data_engine_bootstrap
├─ engine_bus              # 多角色、异步写入、报警/计算触发需要时启动
├─ engine_coord            # HA、分片、租约、选主需要时启动
├─ if_relation_store       # 用到 IF关系库才启动
├─ if_timeseries_store     # 用到 IF时序库才启动
├─ if_realtime_store       # 用到 IF实时库才启动
└─ if_message_store        # 用到 IF消息库才启动，只承载 MQTT
```

核心原则：

- `project_nginx` 是工程运行栈入口，不承载业务判断。
- `client_engine` 不属于数据引擎内部，它只通过 `runtime_api` 使用运行态动态能力。
- `runtime_api` 是工程运行网关，承接登录、会话、权限、数据 API、报警动作和 WebSocket，可多副本负载均衡。
- 采集、写入、报警、计算按角色独立扩容。
- `engine_bus` 是数据引擎内部可靠事件流，固定采用 NATS JetStream，不等同于 IF消息库。
- `engine_coord` 是数据引擎内部协调组件，用于租约、选主和分片 ownership。
- 默认只有 `project_nginx` 暴露到工程外部；`runtime_api`、数据引擎角色、NATS JetStream、`engine_coord` 和 IF 内置库均只在 compose 内部网络访问。

## 6. 多站点运行模型

一个工程可以部署到一个或多个运行站点。运行站点是 `node_agent` 执行拓扑规划和启停托管的实际节点边界。服务站点默认使用 Linux 容器化运行栈；采集站点可以使用 Linux 容器、Windows 原生服务或 Linux 原生服务。

| 站点类型 | 推荐执行方式                                 | 典型位置                                               | 启动内容                                                                                      | 不启动内容                                          |
| -------- | -------------------------------------------- | ------------------------------------------------------ | --------------------------------------------------------------------------------------------- | --------------------------------------------------- |
| 服务站点 | Linux + Docker Compose                       | 机房服务器、边缘服务器、Windows Server 承载的 Linux VM | IF 内置库、NATS JetStream、`engine_coord`、runtime_api、writer、alarm、compute、client_engine | 与现场设备强绑定的采集器可不启动                    |
| 采集站点 | Windows Service / Linux systemd / Linux 容器 | 工业盒子、产线网关、设备侧小主机                       | collector、可选本地缓冲、可选本地诊断入口                                                     | IF 四库、API、writer、alarm、compute、client_engine |

采集盒子独立部署时，数据流为：

```text
collector box
└─ data_engine_collector_<protocol>
   ├─ 连接现场设备
   ├─ 标准化 DataPointEvent
   ├─ 写本地 WAL / buffer
   └─ 通过服务站点 project_nginx 上行到 NATS JetStream

server site
├─ engine_bus: NATS JetStream
├─ data_engine_writer
├─ data_engine_alarm
├─ data_engine_compute
├─ runtime_api
└─ IF 内置库 / 用户外部库连接
```

采集站点只负责把现场数据可靠送出，不承担长期存储、报警状态机、关系查询和页面运行能力。这样可以让采集靠近 PLC、S7、OPC UA 等现场网络，同时把存储和计算集中在更稳定的服务器资源上。采集站点默认连接服务站点的 `project_nginx` 入口，不直接访问服务站点内部 NATS 容器。

### 6.1 原生采集站点

原生采集站点不要求安装 Docker。节点上只注册一个常驻 `node_agent` 服务，由 `node_agent` 托管采集 worker 子进程、本地 WAL、日志、健康检查、升级和回滚。

| 执行方式                    | 适用场景                                                         | 托管方式                                                          |
| --------------------------- | ---------------------------------------------------------------- | ----------------------------------------------------------------- |
| `collector-windows-native`  | 需要 Windows 驱动、厂商 SDK、OPC DA、串口或现场已有 Windows 主机 | `node-agent.exe` 注册为 Windows Service，collector 作为子进程运行 |
| `collector-linux-native`    | Linux 工业盒子、边缘网关、轻量采集机                             | `node-agent` 注册为 systemd service，collector 作为子进程运行     |
| `collector-linux-container` | 现场盒子已标准化 Docker 运行环境                                 | `node_agent` 生成仅包含采集子栈的 compose                         |

原生采集站点的进程模型：

```text
node_agent service
├─ runtime-data-engine --role=collector --protocol=s7
├─ runtime-data-engine --role=collector --protocol=opcua
├─ local WAL / buffer
├─ 本地日志与指标采集
└─ 出站连接服务站点 project_nginx
```

原生 collector 默认不开放入站端口。诊断入口如需启用，只能监听 `127.0.0.1`；远程诊断必须由 `node_agent` 运维模式临时开启并记录审计。

Windows 原生目录建议：

```text
C:\Program Files\InduForge\node_agent\
  node-agent.exe
  runtime-data-engine.exe

C:\ProgramData\InduForge\node_agent\
  config\
  projects\<projectId>\
    current\
    versions\
    runtime-topology.json
    collector-config.json
  wal\<projectId>\
  logs\
  tmp\
```

Linux 原生目录建议：

```text
/opt/induforge/node_agent/
  node-agent
  runtime-data-engine

/var/lib/induforge/node_agent/
  config/
  projects/<projectId>/
    current/
    versions/
    runtime-topology.json
    collector-config.json
  wal/<projectId>/
  tmp/

/var/log/induforge/node_agent/
```

Windows 与 Linux 原生采集站点的运维语义必须一致：安装一个 `node_agent` 服务，`node_agent` 下载和校验采集制品，生成本地采集配置，拉起 collector 子进程，断网时写本地 WAL，上游恢复后按 sequence 补投，升级失败时回滚到上一版本。

发布制品除了页面、资源和数据域快照，还需要包含运行态能力图。能力图由平台侧 `data_service` 和 `dev_core` 在发布时生成，节点侧只消费，不重新推断业务语义。

示例：

```json
        "ha": "hot_standby"
      }
    ],
    "relationStores": [
      {
        "type": "external.mysql",
        "connectionId": "mysql_main"

        "connectionId": "redis_site"
      }
    ],
    "messageStores": [],
    "alarms": {
      "enabled": true,
      "shardPolicy": "rule_hash"
    },
    "computes": {
      "enabled": false
    },
    "ha": {
      "mode": "hot_standby",
      "scaleOut": true
```

## 8. Runtime Topology Planner

### 8.1 职责

`Runtime Topology Planner` 由 `node_agent` 在工程启动前调用。它负责把发布制品能力图和节点部署 profile 转换为可执行运行拓扑。

输入：

- `manifest.json`
- `DataDomainSnapshot`
- `RuntimeSecuritySnapshot`
- `runtimeCapabilities`
- 节点资源 profile，例如 CPU、内存、端口池、是否允许 HA
- 部署 profile，例如单机、热备、分片、副本数上限、执行方式
- 当前节点所属站点，例如 `server-main` 或 `collector-box-line-1`

输出：

- `runtime-topology.json`
- `docker-compose.runtime.yml`
- 工程 `.env`
- 内部服务注册表
- 健康检查计划
- 上游站点连接计划
- 原生采集站点的进程计划和本地目录计划

### 8.2 自动裁剪规则

| 条件                         | 启动结果                                     |
| ---------------------------- | -------------------------------------------- |
| 未使用 IF关系库              | 不启动 `if_relation_store`                   |
| 未使用 IF时序库              | 不启动 `if_timeseries_store`                 |
| 未使用 IF实时库              | 不启动 `if_realtime_store`                   |
| 未使用 IF消息库              | 不启动 `if_message_store`                    |
| 无采集源                     | 不启动 collector                             |
| 只配置 S7 采集               | 只启动 `data_engine_collector_s7`            |
| 无报警规则                   | 不启动 `data_engine_alarm`                   |
| 无计算单元                   | 不启动 `data_engine_compute`                 |
| 单进程轻量模式               | 可不启动 `engine_bus` 和 `engine_coord`      |
| 多角色、多副本或 HA          | 启动 `engine_bus`，按需要启动 `engine_coord` |
| 当前站点为采集站点           | 只启动对应 collector、可选本地缓冲和诊断入口 |
| 当前站点为服务站点且采集外置 | 不启动现场协议 collector                     |

执行方式裁剪规则：

| 执行方式                    | 生成内容                                                                      |
| --------------------------- | ----------------------------------------------------------------------------- |
| `service-linux-container`   | 生成完整 `docker-compose.runtime.yml`                                         |
| `collector-linux-container` | 生成只包含 collector、本地缓冲和可选诊断入口的 `docker-compose.runtime.yml`   |
| `collector-windows-native`  | 生成 Windows 原生进程计划、Windows Service 参数和本地目录计划，不生成 compose |
| `collector-linux-native`    | 生成 Linux 原生进程计划、systemd 参数和本地目录计划，不生成 compose           |

### 8.3 副本规划

默认副本规划应保守，避免小工程启动过多容器。

```text
runtime_api: 1，查询压力大时扩容
collector:  按协议和连接数量规划
writer:     有独立 engine_bus 时启动，按分区扩容
alarm:      有报警规则时启动，按规则数量扩容
compute:    有计算单元时启动，按任务并发扩容
scheduler:  HA/分片/多副本时启动，单 leader + standby
```

## 9. 数据引擎角色设计

### 9.1 bootstrap

`bootstrap` 是一次性任务容器。它负责：

1. 校验发布制品和能力图版本。
2. 初始化 IF 内置库逻辑空间。
3. 初始化运行态内部 schema。
4. 执行运行态数据结构迁移。
5. 校验外部连接可达性。
6. 输出启动前检查结果。

`bootstrap` 失败时，`node_agent` 不应继续拉起业务角色。

### 9.2 runtime_api

`runtime_api` 是工程运行网关，提供运行态动态 HTTP API 和 WebSocket。它负责：

- 工程运行态用户登录、登出、会话刷新和当前用户查询。
- 加载 `RuntimeSecuritySnapshot` 并执行最终权限校验。
- 关系查询。
- 时序查询。
- 实时值读取。
- 报警实例和事件查询。
- 报警确认、消音等运行态动作。
- 数据引擎状态和诊断查询。
- WebSocket 实时数据订阅。

`runtime_api` 尽量保持无状态，可通过工程 `project_nginx` 做负载均衡。客户端引擎不直接访问数据引擎内部角色、NATS、IF 内置库或外部接入源。

### 9.3 collector

`collector` 负责协议采集和外部订阅接入。不同协议使用同一镜像、不同启动参数。

```bash
runtime-data-engine --role=collector --protocol=s7
runtime-data-engine --role=collector --protocol=opcua
runtime-data-engine --role=collector --protocol=mqtt
```

采集器输出统一 `DataPointEvent`，不得把协议私有结构泄漏给 writer、alarm 或 compute。

```json
{
  "projectId": "proj_1",
  "pointId": "temp_001",
  "path": "device.line1.temp",
  "value": 35.6,
  "quality": "GOOD",
  "timestamp": "2026-05-26 10:30:00",
  "source": "s7_line_1",
  "sequence": 12345,
  "epoch": 8
}
```

采集站点上的 collector 还必须支持本地缓冲：

- 上游不可达时，写入本地 WAL。
- 上游恢复后，按 sequence 顺序补投。
- 本地缓冲有容量和保留时长上限，超过上限必须按策略丢弃或停止采集，并上报 `DEGRADED`。
- 补投事件必须保留原始采集时间，不得用补投时间替代。

### 9.4 writer

`writer` 负责批量写入实时库和时序库。

- 实时写入：写当前值、质量码、时间戳和来源 epoch。
- 时序写入：按批次、按点位分区写历史值。
- 幂等：至少基于 `pointId + timestamp + source + sequence` 防重。
- 背压：写入失败时必须暴露队列深度、重试次数和丢弃策略。

轻量模式下，collector 可以内置 writer 能力直接批写。多角色模式下，collector 通过 `engine_bus` 投递事件，由 writer 分片消费。

### 9.5 alarm

`alarm` 消费数据点事件并执行报警状态机。

- 同一规则同一目标同一时刻只能由一个 alarm shard 负责。
- 规则 ownership 由 `engine_coord` 或固定 hash 分片保证。
- 报警实例、报警事件和确认记录写入关系库。
- 报警计算使用 Go 内置规则引擎或受限表达式，不使用 JS/Python 作为高频报警热路径。

### 9.6 compute

`compute` 执行计算单元。

- 高频、简单计算优先使用 Go 内置表达式。
- JS/Python 只作为业务脚本沙箱，用于低频或中频业务计算。
- 沙箱必须限制超时、并发、内存、依赖白名单和外部访问能力。
- 计算输出重新进入 `DataPointEvent` 流程，不能绕过 writer 和报警链路。

### 9.7 scheduler

`scheduler` 负责运行态任务分配：

- collector shard 分配。
- writer partition ownership。
- alarm shard ownership。
- compute 任务调度。
- leader election。
- 故障接管和 epoch 递增。

`scheduler` 自身可以多副本启动，但同一工程同一时刻只有一个 leader 生效。

## 10. 内部通信与协调

### 10.1 通信分层

| 场景                           | 机制                  |
| ------------------------------ | --------------------- |
| 单进程内部模块通信             | Go channel / 内存队列 |
| 多角色事件流                   | `engine_bus`          |
| 任务租约、选主、分片 ownership | `engine_coord`        |
| 工程 MQTT 业务消息             | IF消息库              |
| 关系查询、报警实例、审计       | 关系库                |

### 10.2 engine_bus

`engine_bus` 只服务数据引擎内部，不暴露给用户。运行态固定采用 NATS JetStream，不再保留其他内置队列作为并列默认实现。

NATS JetStream 的职责：

- collector 向服务站点投递数据点事件。
- writer、alarm、compute 按分片或消费组消费事件。
- 支持消息 ACK、重投、保留和断线恢复。
- 支持采集盒子断网恢复后的补投。

建议主题：

```text
datapoint.raw
datapoint.normalized
datapoint.computed
alarm.trigger
compute.trigger
engine.control
```

高频采集不应逐字段滥发大 JSON。collector 应先做批量聚合，再按批次投递。

### 10.3 engine_coord

`engine_coord` 负责强一致协调。候选组件建议优先考虑 etcd。

核心 key 空间：

```text
/projects/<projectId>/leader/scheduler
/projects/<projectId>/instances/<instanceId>
/projects/<projectId>/leases/collector/<shardId>
/projects/<projectId>/leases/alarm/<shardId>
/projects/<projectId>/leases/writer/<partitionId>
/projects/<projectId>/epochs/<role>/<shardId>
```

当部署 profile 不启用 HA、多副本或分片时，可以不启动 `engine_coord`，使用本地单实例规划。

### 10.4 跨站点采集链路

采集盒子到服务站点默认通过服务站点 `project_nginx` 入口写入 NATS JetStream。`project_nginx` 负责统一入口、TLS、访问控制和转发，避免把 NATS 端口直接暴露到工程外部。数据引擎需要封装采集上行协议，避免业务逻辑散落到 NATS 客户端调用中。

采集上行协议包含：

- `DataPointEvent` 批次格式。
- `siteId`、`collectorInstanceId`、`shardId`、`epoch`、`sequence`。
- 本地 WAL offset。
- 上游 ACK 后的 WAL 清理规则。
- 断线重连和补投规则。
- 批次大小、压缩、限流和重试策略。

默认链路：

```text
collector box
└─ collector + local WAL
   └─ NATS JetStream client
      ↓
server site
├─ project_nginx
└─ engine_bus: NATS JetStream
   ├─ writer
   ├─ alarm
   └─ compute
```

若现场网络不允许 NATS 协议通过 `project_nginx` 代理，可后续增加 HTTPS/gRPC 上行接入模式。该模式下采集盒子通过 HTTPS/gRPC 上报批量事件，由服务站点接入处理器写入 NATS JetStream。该模式是安全边界增强，不是首选默认实现。

### 10.5 端口暴露原则

工程运行栈默认只暴露 `project_nginx` 对外端口。

| 组件                      | 默认是否暴露到工程外部 | 说明                                                                    |
| ------------------------- | ---------------------- | ----------------------------------------------------------------------- |
| `project_nginx`           | 是                     | 工程唯一入口，映射独立宿主机端口                                        |
| `client_engine`           | 否                     | 只被 `project_nginx` 反向代理                                           |
| `runtime_api`             | 否                     | 只在 compose 内部网络访问                                               |
| `data_engine_collector_*` | 否                     | 采集出站连接设备或上游，不对外提供入口                                  |
| `data_engine_writer`      | 否                     | 只消费内部事件并写库                                                    |
| `data_engine_alarm`       | 否                     | 只消费内部事件并写关系库                                                |
| `data_engine_compute`     | 否                     | 只消费内部任务和事件                                                    |
| NATS JetStream            | 否                     | 通过 `project_nginx` 代理采集上行，不直接暴露                           |
| `engine_coord`            | 否                     | 只给内部角色使用                                                        |
| IF关系库                  | 否                     | 只给数据引擎访问                                                        |
| IF时序库                  | 否                     | 只给数据引擎访问                                                        |
| IF实时库                  | 否                     | 只给数据引擎访问                                                        |
| IF消息库                  | 默认否                 | 需要外部设备直连 MQTT 时，应通过 `project_nginx` TCP 代理或受控入口暴露 |

调试端口默认不暴露。需要排查时，应由 `node_agent` 进入运维模式临时开启，并记录操作来源、开放范围和关闭时间。

### 10.6 IF消息库边界

IF消息库只用于工程 MQTT 能力：

- MQTT 接入。
- MQTT 订阅。
- MQTT 发布。
- 模拟设备消息。
- 工程 topic 空间。

IF消息库不用于：

- 数据点内部事件流。
- writer 队列。
- alarm 队列。
- compute 队列。
- scheduler 控制消息。
- 分布式锁或租约。

## 11. 连接与 Connector 抽象

数据引擎内部通过 connector 访问不同来源，业务上层不直接绑定具体库。

```text

├─ MySQLConnector
├─ PostgreSQLConnector
└─ SQLServerConnector

TimeseriesConnector
├─ BuiltinTimeseriesConnector
└─ ExternalTimeseriesConnector

├─ BuiltinRealtimeConnector

└─ ExternalMqttConnector

├─ S7Collector
```

IF 内置库 connector 的连接信息由 compose 服务发现和工程 namespace 生成。外部 connector 的连接信息来自发布快照和节点 secret。

## 12. HA 与扩容策略

### 12.1 部署档位

| 档位             | 说明                                                            | 关键组件                                                    |
| ---------------- | --------------------------------------------------------------- | ----------------------------------------------------------- |
| 轻量单机         | 单节点、小工程、少量能力                                        | 可不启用 engine_bus / engine_coord                          |
| 高吞吐单机       | 单节点、多副本、多连接                                          | engine_bus + 可选 engine_coord                              |
| 双机冷备         | 备用工程栈不采集，故障后接管                                    | engine_coord 或外部接管策略                                 |
| 双机热备         | 多节点同时运行，只有 owner 采集和写入                           | engine_coord + lease + epoch                                |
| 多节点分片       | 多节点按连接、设备或点位分片                                    | engine_bus + engine_coord                                   |
| 采集盒子外置     | 采集运行在现场盒子，写入和报警集中在服务站点                    | collector + local WAL + NATS JetStream                      |
| Windows 原生采集 | 现场采集依赖 Windows 驱动、厂商 SDK、OPC DA 或已有 Windows 主机 | Windows Service `node_agent` + collector 子进程 + local WAL |
| Linux 原生采集   | 现场盒子不安装 Docker 或需要更轻量的 systemd 运维               | systemd `node_agent` + collector 子进程 + local WAL         |

### 12.2 防双写

采集和写入必须携带 ownership 信息：

```text
projectId
role
shardId
ownerInstanceId
leaseId
epoch
sequence
```

writer 在写入实时库和时序库前，应校验 epoch 或幂等键，避免主备切换、采集盒子断线补投期间重复写入造成数据污染。

### 12.3 故障接管

1. 实例心跳过期。
2. scheduler 或 standby 观察到 lease 失效。
3. 新实例抢占 shard lease。
4. epoch 递增。
5. 新 owner 从已提交 offset 或最近检查点恢复。
6. writer 继续按幂等规则写入。

### 12.4 采集盒子断网策略

采集站点与服务站点网络断开时：

1. collector 继续采集并写本地 WAL。
2. 本地状态切换为 `DEGRADED`，原因标记为 `UPSTREAM_UNAVAILABLE`。
3. 达到缓冲上限前持续重试上游连接。
4. 上游恢复后按 sequence 补投。
5. 补投完成后恢复 `RUNNING`。
6. 如果缓冲耗尽，按工程策略选择停止采集、覆盖旧数据或丢弃新数据，并上报明确错误。

默认策略建议为停止采集或丢弃新数据，避免覆盖旧数据导致问题不可追溯。具体策略需要在部署 profile 中显式配置。

## 13. node_agent 编排职责

`node_agent` 负责启动和托管，不负责数据业务语义。

启动流程：

1. 下载或接收 `.ifp`。
2. 解压到版本目录。
3. 校验 `manifest.json`、能力图、摘要和协议版本。
4. 读取节点资源 profile 和部署 profile。
5. 调用 `Runtime Topology Planner` 生成拓扑。
6. 按执行方式写入 compose 或原生进程计划。
7. 服务站点先拉起 IF 内置库、NATS JetStream、`engine_coord` 等基础组件。
8. 等待内置库和内部组件健康。
9. 执行 `data_engine_bootstrap`。
10. 拉起数据引擎角色；服务站点同时拉起 `runtime_api`。
11. 服务站点准备 `client_engine` 静态资源、生成 `runtime-config.json` 并启动 `project_nginx`。
12. 验证 `project_nginx`、静态资源、`runtime-config.json` 和 `runtime_api` 可达。
13. 更新工程入口记录。
14. 标记工程运行单元为 `RUNNING` 或 `DEGRADED`。

采集站点上的 `node_agent` 启动流程相同，但拓扑规划结果只包含采集子栈。容器采集站点生成采集 compose；原生采集站点生成 collector 子进程计划并由 `node_agent` 直接托管。采集站点不注册页面访问入口，只向平台和服务站点回报采集状态、上游连接状态和本地缓冲状态。

停止流程：

1. 服务站点停止或禁用工程入口；采集站点停止接收新的采集调度。
2. 通知数据引擎停止采集并释放 lease。
3. 等待 collector 写完本地 WAL，服务站点还需要等待 writer flush。
4. 容器模式停止业务角色容器；原生模式停止 collector 子进程。
5. 服务站点停止内部组件和未共享的 IF 内置库容器。
6. 保存最后状态和错误摘要。

回滚流程：

1. 停止或禁用当前版本工程入口。
2. 停止当前 compose 或原生 collector 子进程。
3. 切换到本地已验证版本目录。
4. 重新生成或读取该版本拓扑。
5. 拉起旧版本 compose。
6. 探活成功后重新启用工程入口。

## 15. 健康与状态

每个数据引擎角色至少提供：

```text
GET /health
GET /status
GET /metrics
```

`/health` 只判断进程与关键依赖是否可服务。`/status` 返回角色、分片、ownership、连接状态、队列深度和最后错误摘要。`/metrics` 使用 Prometheus 风格文本，便于后续接入监控。

`node_agent` 聚合容器状态、原生子进程状态、角色状态和关键依赖状态，形成工程级状态：

```text
STARTING
RUNNING
DEGRADED
FAILED
STOPPING
STOPPED
```

采集站点状态还应包含：

- 上游服务站点可达性。
- 本地缓冲积压条数和磁盘占用。
- 最近成功补投时间。
- 当前采集 shard ownership。
- 现场协议连接状态。

## 16. 技术实现建议

### 16.1 主实现

数据引擎主链路使用 Go：

- 协议采集。
- 连接池。
- 批量写入。
- 报警状态机。
- 查询 API。
- HA 租约客户端。
- 内部事件消费。

Go 进程通过 goroutine 和 `GOMAXPROCS` 使用多核；横向扩展通过多容器副本、分片和租约实现。

### 16.2 脚本能力

JS/Python 只用于业务脚本计算，不进入高频报警和采集热路径。脚本 worker 可按需启动：

```text
data_engine_compute_node
data_engine_compute_python
```

没有计算单元或没有对应语言脚本时，不启动对应 worker。

### 16.3 开源组件原则

内置组件和内部组件应优先选用成熟开源、许可证清晰、可离线分发的技术。最终选型需要单独经过商务和许可证评审。

候选原则：

- 关系库：成熟开源关系数据库。
- 时序库：成熟开源时序或列式分析数据库。
- 实时库：成熟开源 Redis 协议兼容或 KV 能力。
- MQTT：成熟开源 MQTT Broker。
- 内部事件总线：成熟开源事件流或队列。
- 协调组件：成熟开源强一致协调组件。
