## 3. 当前正式产品与技术基线

- 用户只管理**物理节点接入**和**工程单节点部署**。资源池、容器编排单元和内部进程不是当前
  用户对象。
- 一个工程部署当前只绑定一台已审批且在线的物理节点；同一节点可承载访问端口不冲突的多个工程。
  多个已接入节点不等于分布式部署或高可用。
- 用户看到的运行能力固定为“工程入口”“数据运行”和可选“数据采集”。工程前端静态文件属于
  Release，由“工程入口”托管，不作为第四类服务。
- 每台物理节点独立安装 NodeAgent。Linux 节点可承载工程入口、数据运行和可选数据采集；Windows
  节点当前只作为数据采集节点。
- 正式部署必须选择不可变正式 Release；源码快照、开发预览和旧源码包均不可直接部署。
- 当前已有节点接入、审批、心跳、固定服务组调和、Release 元数据校验和本地安装基础原语，但正式
  Release Builder、NodeAgent 下载/验签/激活接线、Secret 装配及真实物理机竖链尚未闭环。
- 升级、回滚和多节点分布式部署尚未交付，当前 API/UI 必须 fail-closed，不得用旧发布链路或手工
  写库绕过。
- 中心开发与管理系统运行于 Linux Docker；工程运行流量由物理节点上的“工程入口”直接承载，
  不经中心平台转发。

## 4. 未来可选内部实现（非当前基线）

未来多节点分布式部署可以在节点内部采用 K3s、Pod、Namespace、site-controller 或其他编排技术，
但这些都不是已冻结实现，更不是用户模型。即使采用，普通用户仍只选择物理节点、部署拓扑、工程
版本和数据采集需求；内部编排对象不得出现在默认 UI、公共 API、错误文案或验收口径中。

[运维与节点运行态总体架构](./02-系统设计/运维与节点运行态总体架构.md)和
[平台运维体系设计](./06-运维与安全/平台运维体系设计.md)当前仅作为未来多节点、容灾和内部编排
设计参考，不是当前功能、公共契约或验收依据。

## 5. 文档规则

- 正式文档必须区分“当前已交付”“当前未闭环”和“未来可选实现”，不得把目标设计写成当前事实。
- 实现计划、阶段总结、临时方案和 AI 辅助规格放入 `归档/过程文档/`，不作为正式依据。
- 旧设计被替代时必须归档并注明替代文档。
- 跨模块协议以 `04-契约与规范/跨模块契约/` 为准。
- 当前代码与正式契约不一致时，应明确记录差异，不能让旧文档继续充当目标架构。
