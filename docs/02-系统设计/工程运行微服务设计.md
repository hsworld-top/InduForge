# 工程运行微服务设计

## 1. 组件与服务组

当前实现以物理节点上的本机进程组成一个工程单节点部署。NodeAgent 的服务组是中心可操作的最小单位；一个服务组可包含多个本机组件，且必须全部通过本机健康检查才回报 `running`。

| 服务组          | 组件                 | 当前职责                                                                    | 监听与边界                                       |
| --------------- | -------------------- | --------------------------------------------------------------------------- | ------------------------------------------------ |
| `project_entry` | Project Gateway      | 入口健康、静态文件托管、API/WS 反向代理、部署身份头注入                     | 对外 HTTP(S)；Runtime API URL 只能为本机回环地址 |
| `project_entry` | Runtime API          | 会话、目录、当前值/历史值、报警/计算只读查询、实时订阅                      | 必须仅监听回环地址                               |
| `data_runtime`  | RuntimeEngine        | Artifact 校验、NATS/数据库预检、writer/alarm/compute 等已配置逻辑角色、排空 | 本机健康端口；不作为浏览器入口                   |
| `collector`     | Industrial Collector | 可选现场协议采集与数据上行                                                  | 本机健康端口和设备网络；不由浏览器访问           |

静态前端位于 Release 的 `client/`；它由 Gateway 读取并返回，**不是 Node 服务、不是独立服务组，也不拥有 PID**。

## 2. Project Gateway

Gateway 是唯一工程入口。它要求 `client-root` 包含普通 `index.html`，目录树不允许符号链接；扩展名资源缺失返回 404，只有前端路由可回退到 `index.html`。Gateway 向 Runtime API 代理请求时注入：

- `X-InduForge-Deployment-Id`
- `X-InduForge-Project-Id`

Gateway 的 `/health` 表示入口进程可服务；`/api/v1/status` 同时探测 Runtime API，后者不可用时入口状态降级而非伪装健康。

## 3. Runtime API 与 Runtime SDK

Runtime API 是发布工程唯一的动态 HTTP/WebSocket 边界。它加载 Runtime Artifact、受限 PostgreSQL 凭据、运行会话 token 和 NATS 凭据；这些均为本机受控文件，不能经浏览器或中心命令下发暴露。

已实现的 V1 是只读切片：会话、目录、当前值、受限时间窗口历史值、当前报警、计算目录，以及 `/ws/v1/points`。设备写入、报警动作、任意发布和人工计算运行尚无冻结的审计契约，服务端返回 `501 / code=50031`。SDK 的 `createHttpRuntime()` 默认同源访问 Gateway，不直接访问内部依赖。完整端点见 [Runtime API 契约](../04-契约与规范/跨模块契约/runtime-api-contract.md)。

## 4. RuntimeEngine

RuntimeEngine 不创建 PostgreSQL 表、NATS Stream 或 Consumer；部署前必须提供已存在的依赖和相应 Secret/index。它在 `RUNNING` 且 `HEALTHY` 或 `DEGRADED` 时的 `/health` 返回 `200/UP`，排空、停止或失败时返回 `503/DOWN`；收到 SIGTERM/SIGINT 后进入 `STOPPING`，最多排空 20 秒。

物理节点使用 `runtime-engine.config.v2`，仅接受 `native-linux` 和 `native-release`。Loader 会拒绝非绝对或未规范化路径、符号链接、越出 release 根的 Artifact、可写挂载及不匹配的原始 SHA-256。v1 仍是旧的 k3s/PVC 契约，不能用于本机 NodeAgent 托管。

当前代码中 roles 是同一进程内按配置启用的逻辑角色，不是用户可选择的独立部署单元；分片、多个实例和角色级故障切换均未交付。

## 5. Collector

Collector 是可选组：没有采集需求的工程不应创建或声称运行该服务。NodeAgent 仅以本机声明的可执行文件、参数和环境托管它；中心只发送服务组和期望状态，不能远程执行任意命令。

Collector 二进制的包构建已接入脚本，但设备驱动、现场连接、WAL、断线补传、Assignment/epoch 切换和真实工业设备验收仍需按 Collector 自身交付物验证，不能由 NodeAgent 的 PID 或 HTTP 成功替代。

## 6. 进程故障与停止

NodeAgent 持久化每个服务组的 PID/组件 PID、generation 和状态，启动时可恢复已配置的本机进程。停止先向组件发送正常终止信号，以便组件自行排空；到 `drainTimeout` 后才强制终止。某组件启动或健康失败时，服务组整体失败并停止已启动的同组组件。

该恢复只适用于同一节点、同一明确配置和已验证 release；它不是跨节点调度、自动迁移、滚动升级或高可用。
