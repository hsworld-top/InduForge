# 工程开发工作空间网络架构

## 1. 文档定位

本文档定义中心平台中工程开发工作空间的容器、端口、网络、路由和工程隔离边界。

工程开发工作空间用于承载 AI 页面开发，不属于运行站点的工程运行栈，也不改变
`project-nginx`、`runtime-api` 和运行站点 Ingress 的既有边界。

## 2. 开发工作空间组成

每个工程拥有一个独立开发容器，容器内共享同一份 `/workspace`：

```text
工程开发容器
├─ Pi Web       30141  AI 对话和 Agent 会话
├─ code-server   3000  源码、版本、运行和终端开发环境
├─ Vite Preview  5173  Designer iframe 加载的开发态页面
├─ Preview Ctrl  5174  Vite 状态与启停控制
├─ /workspace           当前工程源码
└─ /home/coder/.pi/agent
                       当前工程 Pi 配置和会话
```

Pi Web、code-server、Preview Control 和 Vite Preview 使用同一非 root 用户运行。Pi 修改工程文件后，
code-server 和 Vite Preview 直接观察同一份文件，不通过额外文件同步服务中转。

Pi Web 使用固定版本 `@induforge/pi-web@0.8.8-induforge.1`。其工作目录固定为 `/workspace`，
用户与工程插件自动发现关闭，Project Skills 固定为 `/workspace/.pi/skills`，平台只读 Extension
固定从 `/opt/induforge/pi/extensions` 加载。

Pi Web Fork 源码位于 `designer/pi-web`，开发镜像在多阶段构建中直接编译，不依赖外部发布包。
镜像内 `/opt/induforge/templates` 只读保存四套 Vite 官方模板。空工程通过 Preview Control 首次选择
模板并初始化 `/workspace`，初始化前不启动 Vite。

Designer 通过原生 iframe 分别加载 Pi Web、Vite Preview 和 code-server。Preview Control
独立管理 Vite 生命周期；code-server 使用原生 Explorer、Monaco、SCM、Terminal、Problems 和
Output 提供源码开发能力。

工作台布局、标签协议和状态交互由
[AI 页面开发工作台设计](../03-模块设计/designer/AI页面开发工作台设计.md)定义，本文不重复规定界面实现。

## 3. 环境网络模型

### 3.1 开发环境

#### Mac 前端连接 Linux 中心

仓库根目录的 `pnpm run dev:frontend` 使用显式 `frontend-linux` 模式。IDE、数据中心、
Designer 分别运行于 `18601–18603`；独立工作区代理运行于 `18604`，目标由根目录
`.env.frontend-linux` 配置。开发人员访问 `http://localhost:18601`，无需安装本机证书。

开发代理负责 API、Socket.IO 和工作区跨域适配。工作区使用各自的 `*.localhost` 地址；
浏览器将它们与 `localhost` 判为跨站，因此开发代理将工作区会话 Cookie 转为
`SameSite=None; Secure; Partitioned`，保留 host-only、HttpOnly 和有效期。这里的 Secure
利用浏览器对 localhost 回环地址的可信处理，不要求本地入口改用 HTTPS。代理同时折叠
网关和工作区返回的完全相同的 CORS Origin，避免浏览器拒绝重复响应头。

这套适配仅用于显式开发代理，不进入生产静态构建，也不修改远端网关的生产 Cookie 策略。
生产环境继续使用 HTTPS 和正式工作区鉴权。平台访问的开发／生产配置与工程“开发版／生产版”
部署是两个独立概念，选择工程开发版不会关闭生产平台的安全配置。

#### 本机容器开发

开发环境允许将容器内部四个服务发布为仅绑定 `127.0.0.1` 的动态宿主机端口：

```text
浏览器
├─ 127.0.0.1:{动态端口} → 工程容器:30141  Pi Web
├─ 127.0.0.1:{动态端口} → 工程容器:3000   code-server
├─ 127.0.0.1:{动态端口} → 工程容器:5173   Vite Preview
└─ 127.0.0.1:{动态端口} → 工程容器:5174   Preview Control
```

动态端口只用于本机调试。`dev_core` 通过 Docker Inspect 读取实际宿主机端口，并在
工作空间状态接口中返回四个服务的完整 URL。Designer 使用 `services.ai.url`、
`services.preview.url` 和 `services.code.url` 创建三个 iframe，并使用
`services.previewControl.url` 管理预览进程；任何前端都不得拼接端口。

动态端口不得默认绑定 `0.0.0.0`。确需局域网联调时，应由开发人员显式修改绑定地址，
并确认宿主机防火墙和访问边界。

### 3.2 生产与离线环境

生产和离线环境中，工程开发容器不发布任何宿主机端口。容器只暴露内部端口并加入
Docker 内部网络，由 Traefik 发现和转发：

```text
浏览器
  │ HTTPS :443
  ▼
Traefik
  ├─ 平台静态页面 ─────────────→ Nginx:80
  ├─ /api/v1 ─────────────────→ dev_core:18101
  ├─ 工程 A AI/工作台/预览路由 → 工程 A 开发容器
  └─ 工程 B AI/工作台/预览路由 → 工程 B 开发容器
```

中心平台对外只开放 Traefik 的 HTTPS 入口。Nginx 作为内部静态服务器，只负责托管
`dev_ide`、`designer`、`datacenter` 等构建产物，不负责发现和代理动态工程容器。

Traefik 的 Docker Provider 必须配置为默认不暴露容器。只有包含
`traefik.enable=true` 且具备受控路由标签的工程开发容器才能进入外部路由。

## 4. 路由模型

工程工作空间优先采用独立子域名，不采用多层路径前缀：

```text
ai-{projectId}.workspace.example.com      → 容器:30141
code-{projectId}.workspace.example.com    → 容器:3000   定制 code-server 工作台
preview-{projectId}.workspace.example.com → 容器:5173
preview-control-{projectId}.workspace.example.com → 容器:5174
```

四个服务均使用根路径运行。这样可以避免 Pi Web 的 Next.js 资源、code-server 重定向、
Vite HMR 和 WebSocket 在路径前缀下产生额外适配。Preview 使用独立 Origin，由 Designer
iframe 直接加载。

部署环境需要准备：

- `*.workspace.example.com` 指向中心 Traefik 的 DNS 记录。
- 对应通配符 TLS 证书，或能够覆盖工作空间子域名的证书签发机制。
- 每个 Traefik Service 明确声明目标容器端口，禁止依赖多端口容器的默认端口选择。
- Pi Web、code-server 和 Vite HMR 的 HTTP/WebSocket 流量均通过同一 HTTPS 入口。
- Preview 路由允许当前工程的 Designer 嵌入，但不得允许其他工程或任意站点嵌入。
- Preview 路由同时允许用户在新标签打开；新标签复用工作空间 HttpOnly 会话并使用浏览器原生开发者工具。

工作空间状态接口在不同环境返回相同结构：

```json
{
  "status": "running",
  "containerName": "induforge-code-project-id",
  "services": {
    "ai": {
      "url": "https://ai-project-id.workspace.example.com",
      "hostPort": null
    },
    "code": {
      "url": "https://code-project-id.workspace.example.com",
      "hostPort": null
    },
    "preview": {
      "url": "https://preview-project-id.workspace.example.com",
      "hostPort": null
    },
    "previewControl": {
      "url": "https://preview-control-project-id.workspace.example.com",
      "hostPort": null
    }
  }
}
```

开发环境可返回动态 `hostPort`，Designer 仍只使用 `url`。

字段职责为：

| 字段 | 消费方 | 用途 |
| --- | --- | --- |
| `services.ai.url` | Designer | 创建 Pi Web iframe。 |
| `services.code.url` | Designer | 创建持续存活的 code-server iframe。 |
| `services.preview.url` | Designer | 创建持续存活的 Vite Preview iframe。 |
| `services.previewControl.url` | Designer | 查询、启动、停止和重启 Vite。 |

工作空间接口不提供任意 VS Code 命令或可由前端拼装的内部地址。

## 5. 工程隔离

工程开发工作空间以 `projectId` 作为容器、卷、网络、路由和权限归属标识。

### 5.1 文件与状态隔离

每个工程只挂载自己的持久化子目录：

| 宿主卷子目录 | 容器目录 | 权限 |
| --- | --- | --- |
| `{projectId}/workspace` | `/workspace` | 读写 |
| `{projectId}/context-state/current` | `/workspace/.induforge/context` | 只读 |
| `{projectId}/code-server-data` | `/home/coder/.local/share/code-server` | 读写 |
| `{projectId}/code-server-config` | `/home/coder/.config/code-server` | 读写 |
| `{projectId}/pi-agent` | `/home/coder/.pi/agent` | 读写 |
| `{projectId}/cache` | `/cache` | 读写 |

开发容器不得挂载 Docker Socket、控制面工作目录、其他工程卷或平台数据库凭据。

### 5.2 网络隔离

生产和离线环境采用每工程独立 Docker 网络：

```text
Traefik
├─ induforge-workspace-{projectA} ── 工程 A 开发容器
├─ induforge-workspace-{projectB} ── 工程 B 开发容器
└─ induforge-workspace-{projectC} ── 工程 C 开发容器
```

Traefik 加入各工程网络以访问对应容器，工程容器之间不共享同一个工作空间网络，
默认不能通过容器名或内部端口互相访问。

若 Docker 或部署工具对动态网络数量存在实际限制，需要变更为共享网络时，必须另行设计
工程间网络访问控制，不能把共享 Docker 网络本身视为隔离措施。

### 5.3 路由与权限隔离

每个外部请求必须同时满足：

- 路由中的工程标识与目标容器标签一致。
- 当前用户属于同一租户并具备目标工程写权限。
- 访问凭据只授权当前工程和当前工作空间服务。

iframe 导航不能依赖前端附加 Bearer Header。生产接入应由 `dev_core` 签发短期、工程级
工作空间票据，经 Traefik ForwardAuth 或等效认证链路校验后建立 HttpOnly 会话。
长期平台访问令牌不得放入 iframe URL。

Pi Web、code-server、Preview 和 Preview Control 使用同站点下的独立 Origin。认证优先由
工作空间短期票据建立同站点 HttpOnly 会话，不得在 iframe URL 或控制请求中注入长期 Bearer Token。

## 6. 容器发现与生命周期

`dev_core` 负责：

- 创建、启动、停止、重建工程开发容器。
- 创建并维护工程独立 Docker 网络。
- 写入工程、服务端口和 Traefik 路由标签。
- 校验已存在容器的 `managed`、`project-id` 和 `role` 标签。
- 返回 Pi Web、code-server、Preview 和 Preview Control 的环境无关 URL。
- 删除工程时停止并删除开发容器与工程网络；持久化目录按工程删除规则处理。

工程创建和 Docker 操作不是同一个数据库事务。工程主数据创建成功但开发容器创建失败时，
不得删除已经创建的工程。平台应保留工程并将开发工作空间标记为可重试状态。

## 7. 安全约束

- 工程开发容器统一使用非 root 用户。
- 生产环境不发布工程容器宿主机端口。
- Traefik 是动态工程服务的唯一外部入口。
- Nginx 只作为内部静态服务器，不持有 Docker 发现权限。
- Traefik Docker Provider 应使用最小权限访问方式，后续优先评估 Socket Proxy，避免直接暴露完整 Docker Socket。
- Pi Web、code-server 和 Preview 均不得绕过平台认证直接暴露到不可信网络。
- Designer 的 Preview Control 请求必须通过工程级鉴权；Preview 新标签访问必须经过相同的工作空间鉴权。
- 容器资源、进程数和网络出口需要配置上限；是否允许访问公网模型服务由平台策略控制。
- 所有 Agent 文件修改、命令执行和模型调用应进入工程审计链路。

## 8. 当前决策与后续实现

已确定：

- 一个工程对应一个独立开发容器。
- Pi Web、code-server 和 Vite Preview 共享当前工程工作区。
- Designer 使用 Wujie 接入 `dev_ide`，Pi Web、Vite Preview 与 code-server 使用原生 iframe。
- Preview 与 code-server iframe 持续存活，右侧菜单只切换可见性。
- 开发环境使用仅本机可达的动态宿主端口。
- 生产环境由 Traefik 单端口对外，工程容器不发布宿主机端口。
- Nginx 负责中心平台静态前端，Traefik 负责统一入口和动态容器路由。
- 生产环境按工程建立独立 Docker 网络。

后续实现需补齐：

- `dev_core` 的多服务端口、Docker 网络和 Traefik 标签模型。
- 工程创建后的开发容器预置与失败重试。
- 工作空间票据和网关鉴权接口。
- `dev_core` 的 Preview Control 服务 URL、路由与生产鉴权接入。
- Preview 构建错误反馈、嵌入鉴权和 Vite HMR 代理验证。

当前开发镜像已完成：

- Pi Web 固定 `/workspace`，移除项目选择、Plugins、系统提示词入口和 Worktree。
- Designer 与 Pi Web 通过严格 Origin 的 READY/CONTEXT 消息同步 IDE 语言和主题。
- 空工作区首次选择四套官方 Vite 模板之一，成功后创建本地 Git 仓库和初始提交，不配置远端。
- 非空且没有 `/workspace/.induforge/project.json` 标记的工作区不会被自动覆盖。
