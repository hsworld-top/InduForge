# 节点管理与交付架构

## 1. 系统定位

节点管理与交付系统连接中心控制面和每台受管物理节点，负责节点接入、身份确认、状态上报及工程
部署。用户管理物理节点、运行环境、基础服务和工程部署；内部进程和编排对象留在技术诊断中。当前部署形态以 [平台部署拓扑架构](./平台部署拓扑架构.md) 为准。

## 2. 当前组成

```text
dev_core 节点与工程部署管理
└─ NodeAgent 主动出站连接 1..N 台物理节点
   ├─ 节点身份与接入
   ├─ 主机资源摘要
   ├─ 本机固定服务组调和
   ├─ Release 本地存储基础原语
   └─ 状态与操作结果回传
```

## 3. NodeAgent 当前部署边界

- Linux 工程节点：每台物理机一个 systemd 服务，固定具备工程入口和数据运行能力，可在安装时
  同时启用数据采集。
- Windows 采集节点：每台物理机一个 Windows Service，固定只提供数据采集能力。
- NodeAgent 只管理本机明确安装和配置过的服务组，不托管其他物理节点的进程。
- Center 命令只引用目标节点、工程部署、正式 Release、服务组和目标状态；不包含 shell、路径、
  参数、环境变量、Secret 明文或长期对象存储凭据。
- Project Gateway、Runtime API、Runtime Engine 和 Collector 的可执行配置来自节点本地受控配置
  与已验证 Release，不能由普通用户自由拼装。

## 4. 物理节点接入

```text
管理员选择平台和节点用途
→ Center 生成一次性接入码
→ 管理员在目标物理节点手工执行安装命令
→ NodeAgent 领取独立 nodeId 与 token
→ 管理员核对主机名和机器指纹
→ 人工确认后节点才可获取工程部署目标
```

- 接入码只在创建结果中显示一次，不进入普通日志或长期配置；领取成功后 NodeAgent 清除接入码。
- 远程节点的 Center 地址必须是该节点可访问的 HTTPS 根地址；loopback HTTP 只允许同机安装。
- Linux 能力固定派生为工程入口、数据运行和可选数据采集；Windows 固定为数据采集，用户不能
  提交任意能力组合。
- 未确认、已撤销、离线或能力不满足的节点不能创建部署。

## 5. 当前工程单节点部署

创建部署的输入只有：

```text
projectId
applicationVersionId（正式 Release）
nodeId（一台已确认且在线的物理节点）
enableCollector（可选）
```

控制面创建稳定的 ProjectDeployment、一个初始部署配置 revision、工程入口和数据运行服务记录，
以及可选数据采集记录。当前约束为：

- 一个工程只能有一个单节点部署；
- 一台物理节点可承载多个工程，但客户选择的四端口运行区间不得重叠；
- 工程入口和数据运行必须同节点；
- 启用数据采集时，节点能力和 Release 都必须包含采集支持；
- 多节点、同工程重复部署和手工指定内部服务组合均被拒绝。

普通用户界面把 `DeploymentBinding` 表述为“部署配置”，只展示物理节点、是否启用采集和检查结果；
端口、Secret 引用、内部 revision 和进程配置不作为默认用户输入。

## 6. 当前状态与操作

Center 保存目标状态，NodeAgent 回传当前状态和最后上报时间。普通用户只看到：

- 节点：等待领取、待确认、已接入、未连接、已撤销；
- 工程部署：等待节点、部署中、运行中、已停止、运行异常、状态未知；
- 服务：工程入口、数据运行、数据采集；
- 最近操作：已受理、进度、安全错误说明和诊断编号。

当前已有 deploy/start/stop/restart 的基础记录与固定服务组调和，但默认产品操作应面向整个工程；
逐服务操作只适合作为高级诊断能力，避免产生入口与数据运行不一致的半部署状态。

进程 PID、路径、内部代次、副本数和 Agent 原始错误不得直接进入普通用户 DTO 或页面。Agent 原始
诊断先映射为稳定原因码和安全中文说明，完整信息仅进入受权限控制的诊断记录。

## 7. 正式 Release 交付状态

当前已经具备：

- 正式 Release Manifest、摘要、签名和部署配置 Schema；
- Center 创建部署前对 Release 元数据、工程归属和可选采集工件的校验；
- NodeAgent 本地流式接收/落盘、解包限制、摘要/签名验证和原子激活的基础原语。

以下仍未闭环：

- 从工程源码生成、签名并上传完整 Release 的正式 Builder；
- Center 命令与 NodeAgent Release/部署配置下载端点的网络接线；
- 信任根、Secret、端口和每工程目录装配；
- 安装后将目标 Release 绑定到 Supervisor，再启动、健康检查并确认当前版本；
- Linux/Windows 真实安装、断线、重试和现场运行端到端验收。

因此本地安装原语存在不等于正式部署已交付。只要 Builder 或 Agent wiring 未启用，创建 Release
和部署必须由服务端能力门禁 fail-closed；服务组健康不能替代目标 Release 身份验证。

## 8. 升级与回滚目标（未交付）

安全升级/回滚至少需要：

- ProjectDeployment 分离 `currentRelease`、`targetRelease` 和 `lastSuccessfulRevision`；
- 每次操作记录不可变 DeploymentRun、Release 和部署配置 revision；
- 升级先下载、校验、准备、启动和健康检查，成功后才切换当前版本；
- 失败时保留上一成功版本和工程入口；
- 回滚只能选择该部署的成功历史 revision，并创建新的 DeploymentRun；
- 写接口携带幂等键和预期当前版本，拒绝并发操作与过期页面状态。

上述对象和 API 尚未完整实现，当前 UI/API 必须隐藏并拒绝升级、回滚，不得复用旧源码部署接口。

## 9. 安全

- Center 与每台 NodeAgent 使用独立身份；节点主动出站，Center 不主动连接宿主机。
- Release 下载使用短期授权，不下发长期中心密钥；摘要、签名、Release、节点和部署配置必须一致。
- NodeAgent 普通协调进程与最小特权 helper 分离；提权动作必须来自签名白名单并可审计。
- Collector 只持有目标工程的最小权限凭据；设备写入需额外安全门禁。
- 一次性接入码、Agent token、运行 Secret 和对象存储内部键不得出现在公共 API、页面或普通日志。

## 10. 未来多节点分布式与可选内部实现（未交付）

未来一个工程可绑定多台物理节点，并在用户界面展示物理拓扑、角色分配、容量、版本一致性、故障
状态和切换结果。开放前必须实现数据角色分片、唯一 owner、fencing、排空、检查点、故障检测、
Release/Secret 一致性和故障注入验收。

实现层可以选择 K3s、Pod、Namespace、site-controller、infrastructure-controller、ServiceAccount、
Ingress、PVC、Lease 或其他技术。它们只属于未来可选内部实现：用户仍管理物理节点和工程分布式
部署，Center 不向普通用户暴露内部控制器、凭据或资源对象。
