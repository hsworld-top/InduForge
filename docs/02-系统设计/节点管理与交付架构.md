# 节点管理与交付架构

## 1. 系统定位

节点管理与交付系统连接中心控制面、每台受管宿主机、站点 K3s 和原生采集进程，负责将工程
期望状态转换为可执行部署，并在 K3s 不可用时保留独立的宿主机恢复入口。

```text
├─ 出站 mTLS ── HostNode 1..N

│                   ├─ Native Process Executor
│                   ├─ Resource Snapshot
│                   └─ Upgrade / Recovery
└─ 出站 mTLS ── K3s / induforge-system
                 ├─ site-controller
                 │  ├─ Desired State Reconciler
                 │  ├─ Project Resource Planner
                 │  ├─ Release State Manager
                 │  └─ Project Health Aggregator
                 └─ infrastructure-controller
                    ├─ Foundation Reconciler
                    └─ Backup / Telemetry Coordinator
```

## 3. NodeAgent 部署

- 每台 Linux 服务节点：一个 systemd 服务，运行在 K3s 外部。
- 每台 Windows 采集节点：一个 Windows Service。
- 每台 Linux 采集节点：一个 systemd 服务。

NodeAgent 位于 K3s 外，是为了在 K3s 不可用时仍能上报本机资源，检查、修复和升级本机 K3s
组件，并托管本机原生 Collector。单个 NodeAgent 不直接托管其他宿主机的进程。

## 4. K3s 管理边界

site-controller 运行在 `induforge-system` Namespace，负责工程部署；infrastructure-controller
以独立 ServiceAccount 和 CRD 负责 NATS、Ingress、遥测、备份控制和站点数据底座。首版可以
复用镜像，但不能共用无限制高权限身份。

site-controller 负责：

- 创建工程 Namespace、ServiceAccount、ConfigMap、Secret、PVC 和工作负载。
- 应用工程 Release 对应的 Kubernetes 资源。
- 观察 Deployment、Job、Pod、Ingress 和 PVC 状态。
- 协调 Desired/Observed/LastSuccessful Release，聚合工程部署状态。
- 使用 Kubernetes Lease 选举活动协调者。

NodeAgent 负责安装、启停、升级和修复本机 K3s Server/Agent，以及 K3s 完全不可用时的恢复。
site-controller 不持有宿主机管理员权限；NodeAgent 不负责 Kubernetes 业务资源日常协调。二者都
不自行调度 Pod，也不解释工程业务配置。

## 5. 原生采集进程边界

所有 Windows/Linux Collector 都由 NodeAgent 通过 `native-processes.json` 托管：

```text
NodeAgent
├─ collector-deployment-a-prod
├─ collector-deployment-b-dev
└─ opcda-worker-deployment-a-prod（Windows 可选）
```

NodeAgent 负责二进制安装、工程配置下载、启停、探活、升级和回滚，不解释设备地址与变量语义。

## 6. 多工程模型

- 一个站点共享一套 K3s 和 JetStream。
- 一个 ProjectDeployment 使用稳定 `deploymentId`，对应一个 Namespace、NATS Account 和数据空间；
  同一工程的开发、预发、生产实例可以在同一 Site 并存。
- 一个采集节点可承载多个 deployment，但默认每个 deployment 一个 Collector 进程。
- 工程停用时先停止调度和采集分配，保留 Namespace、数据空间、最后成功 Release 和备份。
- 工程归档或删除通过独立的下线计划执行；只有完成备份确认、保留期和二次审批后，才清理
  Namespace、NATS Account、运行数据空间和采集版本目录。

## 7. 期望状态

中心下发的核心对象：

```text
SiteDesiredState
HostNodeDesiredState
ProjectDeploymentDesiredState
DeploymentBinding
NativeCollectorAssignmentDesiredState
InfrastructureDesiredState
SiteBootstrapPlan
```

NodeAgent 回传：

```text
HostNodeObservedState
ObservedState
ReleaseApplyResult
WorkloadHealth
NativeProcessHealth
InfrastructureHealth
NodeResourceSnapshot
```

site-controller 回传 ProjectDeployment 观测状态；infrastructure-controller 回传公共基础设施
状态；NodeAgent 回传本机、K3s 组件和原生进程状态。声明式对象统一使用
`desiredRevision / observedRevision / observedAt`；只有可发布对象额外维护
`desiredReleaseId / observedReleaseId / lastSuccessfulReleaseId`。

## 8. 站点首次引导

- 中心签发限时 `SiteBootstrapPlan` 并指定唯一 bootstrap owner NodeAgent。
- 首节点创建 K3s，其他 NodeAgent 使用一次性 join 凭据加入。
- bootstrap owner 安装最小系统基线、infrastructure-controller 和 site-controller，控制器 Ready
  后撤销临时权限。
- 引导步骤按 `commandId + desiredRevision` 幂等；site-controller 不负责安装自己。

## 9. 发布和回滚

- 同一不可变 Release 在 development、staging 和 production 之间晋级；站点、Secret、连接和
  资源差异保存在版本化 DeploymentBinding。
- 新 Release 先下载、校验、预热和探活，再切换入口或业务所有权。
- 新版本失败时旧版本继续运行。
- 回滚按 Release ID 恢复，不从当前版本反向修改文件。
- NodeAgent 不通过消息总线传输大型 Release 文件。
- writer、alarm、compute 和 Collector 等有副作用角色使用 Lease + epoch 单权切换，不能只依赖
  Kubernetes RollingUpdate。
- 真实设备不能校验 epoch 时，只允许读采集自动接管；设备写入必须依赖排他会话、写入网关、
  网络 fencing 等硬隔离，否则歧义故障期间暂停并人工恢复。

## 10. 安全

- 中心、NodeAgent 和 site-controller 使用独立设备身份和双向认证。
- S3 下载使用短期授权，不下发长期中心密钥。
- 中心不保存 K3s 管理凭据；site-controller 使用集群内 ServiceAccount，NodeAgent 只保留本机
  恢复所需权限。
- NodeAgent 的普通协调进程与最小特权 helper 分离；helper 只执行签名白名单命令并记录提权审计。
- Collector 只持有目标工程 NATS Account 的最小权限凭据。
- 中心通道由站点和节点主动出站连接，控制命令带命令 ID、目标 revision、有效期和防重放信息。
