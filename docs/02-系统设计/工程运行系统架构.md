# 工程运行系统架构

## 1. 当前交付边界

当前正式运行模型只面向两类对象：**物理节点**与部署到该节点上的**工程单节点部署**。中心负责接入、审批、创建部署及发出服务状态目标；物理节点上的 NodeAgent 只托管本机明确配置过的服务组。用户界面和 API 不把资源池、K3s、Pod 或容器作为工程运行模型的一部分。

一个工程部署绑定一台已审批且在线的物理节点，并由三个服务组组成：

| 服务组          | 实际组件                                                      | 是否可选 | 对外可见性                           |
| --------------- | ------------------------------------------------------------- | -------- | ------------------------------------ |
| `project_entry` | Project Gateway、Runtime API、Release 中的 `client/` 静态文件 | 否       | Gateway 是工程唯一 HTTP(S) 入口      |
| `data_runtime`  | RuntimeEngine                                                 | 否       | 仅本机健康端口；不直接作为浏览器入口 |
| `collector`     | Industrial Collector                                          | 是       | 仅本机健康端口和现场设备网络         |

`client/` 是静态构建产物，不是服务、进程或可被中心单独启停的部署单元。Project Gateway 托管它，并把 `/api/v1/*`、`/ws/*` 代理到本机回环地址的 Runtime API。

Center 已为每个工程单节点部署生成最小 `DeploymentBinding`，绑定节点、部署、Release 身份、客户选择的访问端口与启用服务组；它不含命令、路径、环境、下载 URL 或 Secret 明文。同一节点允许多个工程，但四端口运行区间不得重叠；Center 检查部署记录，NodeAgent 启动前复核本机真实占用。Secret 供给、资源配额、完整进程隔离和正式启动器仍未交付。

## 2. 单节点物理边界

Center（`dev_core` 及其管理界面）与 NodeAgent 始终是两个独立安装：独立服务账户、安装/数据/日志目录、监听端口和网络连接。即使两者恰好安装在同一台物理机，也不得以内嵌进程、共享身份文件、共享数据目录或进程内调用替代该边界。

```text
中心管理用户
  → Center /api/v1/ops/*
      ← NodeAgent 主动领取、心跳、拉取命令

物理节点（独立服务账户和根目录）
  NodeAgent
    ├─ project_entry
    │   ├─ Project Gateway : 公共工程入口
    │   ├─ Runtime API     : 127.0.0.1 回环监听
    │   └─ client/         : 只读静态文件，不是进程
    ├─ data_runtime → RuntimeEngine
    └─ collector    → Industrial Collector（可选）
```

中心不向 NodeAgent 下发 shell 命令、可执行文件路径、参数或环境变量。中心命令只能指向已分配到该节点的 `project_entry`、`data_runtime`、`collector` 服务组及其期望状态；本地声明式 `ServiceConfig` 才决定组件、命令、环境和健康 URL。

## 3. 当前单节点运行链路

1. 管理员创建带一个或多个服务能力的接入任务；NodeAgent 用一次性接入码领取物理节点身份，审批后才获得命令。
2. 创建工程单节点部署时指定工程、正式版本、目标物理节点，并按需启用采集。中心为该部署创建 `project_entry`、`data_runtime`，以及可选 `collector` 的服务记录。
3. NodeAgent 心跳后拉取**仅属于自身 nodeId** 的目标。正式命令携带 Release 摘要和 Binding revision；Agent 再用自己的 token 取得 Binding 和同源 Release 流，拒绝重定向、外部 URL、对象存储键和非本节点数据。
4. Agent 从本地 trust store 取得签名公钥，限额流式校验归档，安全解包、核验 Ed25519 签名与所有摘要、版本和能力后，内容寻址保存并原子更新该部署的 `current.json`。任一步失败不会改写已有当前版本。
5. 当前没有正式启动器把 Activation 中的端口、Secret、内层工件与真实只读挂载落实为进程。因此已验证安装的正式 Release 会记录明确失败，绝不回退到旧静态 Supervisor；只有启动器交付并通过实际健康检查后，服务组才可视为运行。

RuntimeEngine 的本机配置使用 `runtime-engine.config.v2`：`executionForm=native-linux`、`artifactMount.source=native-release`、明确 `nodeId`，并从绝对、无符号链接、实际只读的 release 根读取 Artifact。它不会把 v1 的 `k3s-workload/release-pvc` 配置自动解释为本机部署。

## 4. 工程访问与数据链路

```text
浏览器 → Project Gateway
       ├─ 静态路径 → release/client/
       └─ /api/v1/*、/ws/* → 127.0.0.1 Runtime API

Collector（可选） → NATS JetStream → RuntimeEngine → PostgreSQL/NATS
                                      └→ Runtime API → WebSocket → 浏览器
```

Runtime API 仅监听本机回环地址，Gateway 会注入部署和工程身份头；浏览器不应直连 Runtime API、PostgreSQL、NATS、中心对象存储或现场 Secret。Runtime SDK 默认走 Gateway 的同源 `/api/v1/runtime` 与 `/ws/v1/points`。

## 5. 发布与交付的当前边界

这套进程托管能力不等于完整工程发布系统。当前 NodeAgent 包构建脚本会尝试构建并携带 Gateway、Runtime API、RuntimeEngine 与 Collector 二进制；缺少相应工具链时会 fail-fast，而不会生成声称可运行的空包。

当前已具备以下受限链路：Center 创建并校验节点专属 Binding、以节点 token 提供 `application/zstd` Release 流；Agent 实际拉取、验签、安全安装并原子选择 Release。`releasebuilder` 也能对**已构建、受控的字节输入**生成确定性签名 Release。

但以下链路尚未交付或未完成端到端验证：

- Builder 与工程源码/已构建产物来源、密钥管理、Center ReleaseStore 写入及 `application_versions` 状态流转的接入；
- Secret 供给、内层工件物化和节点派生的 `runtime-activation.v1` 到启动器的受信交接；Activation 不是用户可见的部署模型；
- Runtime Foundation 的真实 PostgreSQL/NATS JetStream 供给、schema/stream/consumer 初始化及运行健康；当前 Foundation 只持久化 `declared` 意图；
- Release 根以真实只读 bind/挂载提供给 RuntimeEngine 的安装器自动化，以及正式启动、停止、升级与回滚；
- 按工程的 Secret、资源配额与完整进程隔离；客户端口选择和冲突门禁已交付；
- Linux 真实安装包的完整接入—部署—运行验收，以及 Windows 真实服务验收；
- Runtime API 的设备写入和人工计算命令契约（当前明确返回 `501 / code=50031`）。

因此“部署运行中”只证明中心收到 Agent 对已配置服务组的观测；只有完成本节缺口对应的真实环境验收，才能声称某个工程 Release 已生产交付。

## 6. 未来多节点分布式部署（未交付）

未来可以把一个工程部署扩展到多个物理节点，并为数据角色定义分片、唯一 owner、epoch、排空、检查点、故障转移和一致的 Release/Secret 选择。该能力当前**禁用且未交付**：多个已接入节点不等于分布式运行，亦不等于高可用；不得把多个单节点进程、多个 NodeAgent 或“运行中”状态宣传为 HA。

在该能力实现并完成故障注入验收前，工程仍只能选择一台物理节点，服务副本数为 1。
