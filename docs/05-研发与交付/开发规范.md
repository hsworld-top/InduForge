# 开发规范

## 1. 适用范围

本文档定义 InduForge 的开发、数据库、基础设施和交付操作口径。仓库级强制规则以根目录 [AGENTS.md](../../AGENTS.md) 为准；模块实现细则以各模块目录下更近的 `AGENTS.md` 为准。

## 2. 开发与验证

- 简单且明确的局部改动直接实现并验证；复杂、风险高或需求不清的任务，先说明方案、影响范围和验证方式，确认后实施。
- 修改应保持最小范围，不做无关重构、格式化或清理。业务逻辑由需求方验收；开发者负责消除基础语法、类型、构建和最贴近变更面的自动化校验错误。
- 根目录常用检查命令为 `pnpm format:check`、`pnpm lint`、`pnpm typecheck`、`pnpm test`；`pnpm format` 与 `pnpm fix` 会写入文件。Go 模块的局部验证以本模块 `Makefile` 或其 `AGENTS.md` 为准。
- `pnpm run dev:core` 与 `pnpm run dev:data` 使用 Air 自动重编译和重启服务；Go 开发环境需预先安装 Air 并确保 `air` 在 `PATH` 中可用。
- 未经用户明确要求，Agent 不得启动、重启或常驻运行任何业务项目、前端开发服务器或本地服务进程。需要接口验证时优先使用用户已启动的服务；服务未运行时记录未验证原因，不得为验证自行启动项目。

### 根脚本分组

- `dev:*`：启动单个开发服务；`dev:env` 仅确保根 `.env` 存在。
- `build:*`、`test:*`、`lint:*`、`typecheck:*`：执行对应模块或分组的只读构建、测试与检查；无后缀的 `build`、`test`、`lint`、`typecheck` 为默认聚合入口。
- `format:check:*`：只检查格式；`format:*`：写入格式化结果；`lint:fix:*` 与 `fix`：显式修复 ESLint 与格式问题。
- `collector:*`：Collector 的 .NET 恢复、构建、测试和开发态发布工具，不纳入默认 `build` 或 `test`。
- 前端统一使用 `dayjs` 的模块为 `dev_core`、`dev_ide`、`datacenter`、`designer`；时间字符串使用 `YYYY-MM-DD HH:mm:ss`。

## 3. 环境与依赖

- Windows 为优先开发环境；Windows + WSL2 场景中，WSL2 只承载 Docker 基础设施，依赖安装和业务项目启动优先在 Windows 侧执行。
- Node 依赖由根目录 pnpm workspace 统一管理：只在仓库根目录执行 `pnpm install`，只提交根目录 `pnpm-lock.yaml`，不在子项目单独安装依赖。
- Prettier 配置统一在根目录维护；ESLint 公共全局变量、忽略目录和基础规则维护在 `eslint.shared.mjs`，前端模块从自身 `eslint.config.*` 引入。
- 环境变量统一使用根目录 `.env`，模板为 `.env.development.example` 与 `.env.production.example`。执行任一根目录 `pnpm run dev:*` 时，若 `.env` 不存在会自动从 `.env.development.example` 生成；已有 `.env` 不会被覆盖。端口和暴露边界以 [环境端口规划](../06-运维与安全/环境端口规划.md) 为准：开发宿主机端口使用 `18xxx`，生产或离线环境仅暴露 edge/Nginx 入口。

## 4. 数据库演进

- 后端仅维护从零创建当前最终结构的建库基线，不维护版本迁移、down 脚本、旧表搬迁、字段回填或启动时兼容修复逻辑。
- 开发数据库已有表、字段、约束或数据需要调整时，直接对当前 WSL/Docker 开发数据库执行 SQL，并同步更新最终建库基线。
- 服务只允许在空数据库创建完整结构；检测到已有业务表时不得自动 `ALTER`、`DROP`、`UPDATE`、`DELETE` 或补齐历史结构。
- 结构变更后必须验证空库可完整创建、当前开发数据库已直接调整，并确认代码不存在对应历史迁移或兼容逻辑。
- 控制面最终结构基线为 `dev_core/db/schema/core-schema.sql`；数据域最终结构基线为 `data_service/internal/db/schema/schema.sql`。详细数据边界见 [数据库设计](../04-契约与规范/数据库设计.md)。

## 5. 接口与数据处理

- API 统一遵守 [统一 REST 接口规范与清单](../04-契约与规范/统一REST接口规范与清单.md)。成功条件为 `HTTP 2xx + code = 0`；业务失败使用 `HTTP 2xx + code != 0`；技术异常使用 `HTTP 4xx/5xx + code != 0`。
- 分页信息放入 `data.pagination`，列表主体放入 `data.list`。增长型表格、树、清单和历史记录默认按页或按需加载，禁止以前端全量拉取替代服务端分页、搜索和排序。
- 批量新增、更新、删除和映射优先设计后端批量接口；需要多条数据一致性的写入或删除优先使用事务。查询大量 ID 时使用 POST 请求体或专用批量接口，避免超长 URL。
- 错误码优先复用；新增错误码时更新 [统一错误码枚举表](../04-契约与规范/统一错误码枚举表.md)。数据库操作必须使用参数化查询。

## 6. 基础设施与交付

- 开发基础设施入口为 `scripts/dev/init-linux.sh`。该脚本只检查 Docker、生成 `.env`、启动基础设施容器、创建 `if_core`、`if_data`、`if_dev_data` 并启用开发态时序扩展；不安装 Node 依赖，也不启动业务服务或前端。
- `dev_core` 开发环境使用 `DB_AUTO_SCHEMA_SYNC=true` 同步 `if_core` 表结构和默认数据；生产/离线环境必须保持 `DB_AUTO_SCHEMA_SYNC=false`，仅在安装阶段初始化数据库结构。
- 测试打包入口为 `scripts/release/build-offline-package-linux.sh`；离线安装入口为 `scripts/offline/install.sh` 与 `scripts/offline/install.ps1`。离线镜像缓存位于 `scripts/docker/images/`，镜像 tar 不提交 Git，交付镜像使用 `induforge/*` 产品体系命名。

## 7. 文档与交付

- 正式业务文档使用 `docs/` 下的分类目录；阶段计划、临时方案和 AI 过程文档使用 `.superpower/`，不作为正式架构依据，也默认不提交。
- 新增正式文档优先使用中文文件名。替代旧设计时，按 [文档中心](../README.md) 的规则归档并说明替代关系。
- 交付说明应包含修改范围、自动化验证结果、未验证项、剩余风险，以及建议人工验收的成功和失败路径。
