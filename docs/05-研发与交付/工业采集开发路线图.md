# 工业采集开发路线图

## 1. 目标

建设独立于中心容器和站点 K3s 的工业采集体系，并明确区分：

- **采集调试代理（Collector Dev Agent）**：可选安装的 Windows 托盘程序，向中心注册，只承担开发态短链测试；关闭窗口时继续驻留托盘，只有显式退出才断开。
- **工程采集器（Runtime Collector）**：工程部署后的运行组件，由站点 NodeAgent 管理，承担长期采集、WAL 和 JetStream 发布。

两者共享驱动契约和协议适配器，但使用不同宿主程序、认证方式和生命周期。平台公开模型只使用 OPC UA、Modbus、S7、三菱、欧姆龙等协议或设备能力名称，不暴露底层 SDK 供应商、授权方式和实现版本。

## 2. 总体阶段

| 阶段               | 交付目标             | 主要范围                                                                | 完成标志                                              |
| ------------------ | -------------------- | ----------------------------------------------------------------------- | ----------------------------------------------------- |
| M0 开发基础设施    | 提供本地 JetStream   | WSL2 Docker、`18222/18223`、健康检查                                    | Windows 可访问 `/jsz`，JetStream 已启用               |
| M1 OPC UA 调试代理 | 已完成开发态短链闭环 | Agent 注册、心跳、任务、OPC UA Connect/Browse/Read、数据中心 Agent 管理 | 已通过 Windows Agent 真实浏览并读取模拟器点位         |
| M2 通用驱动接入    | 形成协议无关工作台   | 能力清单、Schema 表单、Modbus/S7 等协议适配、短时 Write/Subscribe       | 新协议接入不新增独立工作台，只新增内部适配器和 Schema |
| M3 工程采集器      | 跑通长期采集闭环     | Runtime Host、工程配置、WAL、JetStream 发布、写入命令                   | 工程采集数据持续进入工程 Stream，断线后可以补投       |
| M4 站点生命周期    | 纳入工程部署体系     | NodeAgent 能力包、进程计划、凭据注入、升级回滚、状态汇聚                | 工程发布后可自动部署和管理每工程 Collector            |

## 3. 第一阶段范围：M1

### 3.1 必须实现

- 新增独立 `.NET 10 LTS` 采集解决方案。
- 使用 OPC Foundation 官方 .NET SDK 实现 OPC UA 驱动。
- Agent 使用一次性注册码向中心注册并取得长期凭据。
- Agent 主动向中心发送心跳并轮询短时调试任务。
- 中心支持创建、领取、完成、失败、取消和过期任务。
- 第一批任务类型：
  - `connection.test`
  - `opcua.browse`
  - `opcua.read`
- 数据中心展示可用 Agent、驱动能力、在线状态和任务结果。
- 没有 Agent 时允许继续离线建模，并明确提示安装调试代理。
- 使用现有工业模拟器 `opc.tcp://127.0.0.1:18540/induforge/sim` 完成端到端验证。

### 3.2 明确不做

- 不接入商业工业通信 SDK。
- 不实现 OPC DA。
- 不实现长期 Subscription。
- 不实现 WAL 和 JetStream 数据发布。
- 不让 NodeAgent 托管调试代理。
- 不做 Linux 安装包。
- 不删除中心现有 OPC UA、Modbus、S7 代码。
- 不提前实现 K3s 工程部署。

## 4. M1 架构

```text
数据中心前端
  → data_service 用户 API
  → collector_dev_tasks
  ← 任务状态与结果

Windows Collector Dev Agent
  → 使用注册码注册
  → 心跳上报能力
  → 主动领取任务
  → OPC UA Driver 连接设备
  → 回传 Browse / Read 结果

OPC UA 模拟设备
  ← opc.tcp://127.0.0.1:18540/induforge/sim
```

第一阶段采用 Agent 主动短轮询，原因是：

- 只要求 Agent 能访问中心，不要求中心访问设备内网。
- 无需提前引入 WebSocket、gRPC 或 NATS 控制面。
- 任务表天然保留审计、超时和失败信息。
- 后续可以替换为长轮询或流式传输，上层任务契约不变。

## 5. 核心数据模型

### 5.1 `collector_dev_agents`

保存 Agent 身份、版本、在线状态和能力摘要，不保存设备密码或工程敏感配置。

关键字段：

- `id`
- `tenant_id`
- `name`
- `os`
- `arch`
- `version`
- `status`
- `credential_hash`
- `capabilities`
- `last_seen_at`
- `created_at`
- `updated_at`

### 5.2 `collector_dev_registration_codes`

保存一次性注册码的哈希、有效期和使用状态。中心只在创建时返回一次明文注册码。

### 5.3 `collector_dev_tasks`

关键字段：

- `id`
- `tenant_id`
- `project_id`
- `agent_id`
- `operation`
- `status`
- `request_payload`
- `result_payload`
- `error_code`
- `error_message`
- `deadline_at`
- `claimed_at`
- `finished_at`
- `created_by`
- `created_at`
- `updated_at`

任务状态限定为：

```text
queued → running → succeeded
                 → failed
queued/running → cancelled
queued/running → expired
```

## 6. API 边界

### 6.1 平台用户 API

统一使用平台 JWT：

```text
POST   /api/v1/data/collector-dev/registration-codes
GET    /api/v1/data/collector-dev/agents
DELETE /api/v1/data/collector-dev/agents/{agentId}
POST   /api/v1/data/projects/{projectId}/collector-dev/tasks
GET    /api/v1/data/projects/{projectId}/collector-dev/tasks/{taskId}
DELETE /api/v1/data/projects/{projectId}/collector-dev/tasks/{taskId}
```

### 6.2 Agent API

注册接口使用一次性注册码；其余接口使用 Agent Bearer Token：

```text
POST /api/v1/data/collector-dev/agent/register
POST /api/v1/data/collector-dev/agent/heartbeat
POST /api/v1/data/collector-dev/agent/tasks/claim
POST /api/v1/data/collector-dev/agent/tasks/{taskId}/complete
```

## 7. 安全原则

- 注册码和 Agent Token 只存 SHA-256 哈希。
- 注册码默认 10 分钟过期且只能使用一次。
- Agent Token 只在注册成功时返回一次。
- Agent 只能领取明确分配给自己的任务。
- 任务完成接口必须校验任务归属和当前状态。
- 第一阶段仅支持匿名认证，不接收连接密码和证书私钥。
- Browse、Read 默认只读；Write 在 M2 单独增加权限和二次确认。
- Agent 离线判断使用中心时间，不信任客户端上报时间。

## 8. 后续阶段进入条件

M1 已于 2026-07-13 完成真实端到端验收。进入 M2 前继续保持以下契约稳定：

- 驱动能力描述。
- 统一任务请求和结果信封。
- OPC UA Node 描述结构。
- Agent 注册、认证和心跳机制。
- 数据中心无 Agent 时的降级交互。
