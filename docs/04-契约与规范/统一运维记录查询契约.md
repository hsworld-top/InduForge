# 统一运维记录查询契约

## 范围和接口

`GET /api/v1/ops/records` 只读合并 `deployment_runs`、`runtime_cluster_events`、`runtime_environment_events`。不改数据库结构、不补写历史状态、不按文本或时间猜测任务关联。部署 run 每任务一行；基础服务和环境请求没有正式任务 ID，保留原始事件来源，但明确人工操作归 `operation`，不能伪装为系统事件或可追踪任务。

参数：`page` 默认 1、`limit` 默认 20/上限 200；`search` 最多 200 个字符，对标题、对象名称、消息做不区分大小写的字面包含匹配（`%`、`_`、反斜杠不是通配符）；`recordType=operation|event`；`objectType=deployment|foundation|environment|node|cluster`；`objectId`、`environmentId` 为 UUID；`status=accepted|running|success|failed|warning|recovered|info`；`from`、`to` 为 RFC3339，含起止边界，起始不得晚于结束；`sort=time_desc|time_asc`，默认倒序。

响应遵守 `code/msg/data/reqId`，`data={list:[],pagination:{page,limit,total}}`。空页不丢 total。数据库中 UNION、筛选、计数及分页，固定两次查询，不逐行查用户或任务事件；按记录时间与带来源前缀的 ID 同向排序。并发写入时使用普通分页快照语义，刷新第一页对账。

## 记录字段

| 字段 | 含义 |
| --- | --- |
| `id` | `deployment_run:<UUID>`、`cluster_event:<UUID>` 或 `environment_event:<UUID>`；跨来源稳定唯一 |
| `sourceKind` | `deployment_run`、`cluster_event`、`environment_event` |
| `recordType` | `operation`（操作记录）或 `event`（平台事件）；能否展开任务由 taskRef 决定 |
| `objectType` / `objectId` / `objectName` | 部署、基础服务环境整体、环境、节点或集群；基础服务对象 ID 是环境 ID，不冒充单服务 ID |
| `environmentId` | 可准确关联的环境 UUID；cluster 来源为 null |
| `title` / `message` | 操作或事件的真实摘要；deploy 且正式消息以“重新部署”开头显示“重新部署工程” |
| `status` | 下节定义的展示语义，不把事件结果当任务完成 |
| `eventResult` | 事件保留原始 `success/failed`；任务为空字符串 |
| `actorDisplayName` | 同租户 full_name 优先 username；非空创建者但不可查为“未知用户”；事件创建者 NULL 无法区分系统与删除用户，显示“系统或已删除用户” |
| `time` | run.started_at 或 event.created_at |
| `completedAt` / `durationMs` | 仅任务可有完成时间与非负真实毫秒差；事件和未完成任务为 null，不使用浏览器时间 |
| `taskRef` | 可访问任务为 `{runId,deploymentId}`，展开复用 `/ops/deployment-runs/:id/events/page`；其他为 null |
| `detailUnavailableReason` | 已删除部署任务为“对象已删除，保留操作摘要”，其他为空字符串 |

逻辑删除的部署、环境记录仍保留审计摘要。现有历史/事件详情接口拒绝删除部署的边界不变，因此已删除部署不会生成可展开 taskRef。关联名称只从同租户表取得，不输出用户 ID、联系方式、凭据或业务配置。

## 分类与状态语义

`deployment_run` 均为 operation。以下显式 event_type 也归 operation：`environment_created`、`environment_updated`、`environment_delete_requested`、`node_added`、`node_unassigned`、`foundation_migration_requested`、`foundation_deploy_requested`、`foundation_redeploy_requested`、`worker_join_requested`、`worker_remove_requested`。其他来源事件归 event，不根据 created_by 是否为空猜人工/系统来源。

- 任务：observed_status=failed 为 `failed`；已完成且 observed_status=running/stopped 为 `success`；其他为 `running`（执行中）。任务的“运行中”不表示工程当前正在运行。
- 事件：类型以 `_requested` 结尾且 result=success 为 `accepted`，只表示请求已接受，绝不借后续消息补成功终态。
- 显式人工操作的非请求事件使用真实 result 对应 `success/failed`（例如环境编辑已同步提交）。平台事件 result=failed 为 `warning`；node_online 为 `recovered`；其他为 `info`。时间同步 success 可能只是校准中，基础服务 state_changed success 也可能仍在部署，均不猜执行成功。
- 前端应按 status 解释状态，不直接把 `eventResult=success` 显示为“执行成功”；展开依据 taskRef，不依据 operation 分类。系统异常和恢复始终是事件，不制造任务耗时、进度或阶段。

## 镜像、环境归属与权限

节点 `node_online/node_offline/node_time_sync_changed` 在当前写入路径同时生成 cluster 规范事件和 environment 扇出镜像。统一入口固定只展示 cluster 来源，排除 environment 这三类；这是来源选择规则，不使用名称/时间匹配去重。环境其他关联事件保留；其表没有 node_id，不通过 target 名称反查节点。

cluster 事件没有历史 environment_id，不能借当前成员关系反推，故返回 null。环境筛选只匹配可精确关联记录，不包含这类节点/集群事件；需要查看节点历史时使用 objectType=node、objectId。未指定环境时仍展示其规范节点事件。

租户只从鉴权会话取得；每个 SQL 分支独立限定 tenant。任务源要求 `node:read`；完整事件源同时要求 `node:read`、`environment:read`，与统一实时 `events` 主题一致。客户端筛选不能扩大权限。记录页订阅 `deployments` 和 `events`，按已实现的事件合并/节流刷新；HTTP 首次快照和断线对账策略不变，无新连接、ticker 或写入生命周期。
