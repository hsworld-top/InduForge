# 工程开发态快照与恢复契约

## 1. 边界

`authoring-snapshot.v1` 是生产版本对应的完整、不可变开发态快照。它用于在同一工程内恢复后继续编辑，
不作为节点运行包。生产节点仍只消费现有 Release；节点不参与构建或恢复。

快照必须包含同一逻辑时点的：

- 中心工程工作区源码（排除 `node_modules`、构建输出、缓存和代码工作区状态）；
- 可编辑场景当前态，包括场景草稿、当前已提交修订、资源当前代次、资源草稿和绑定；
- Data Service `ProjectSnapshot`，包括已有加密密文块。

快照禁止包含运行值、报警与通知历史、节点或环境分配、预览会话和编辑器会话。

## 2. 存储与完整性

生产版本快照固定写入：

```text
authoring-snapshots/<tenantId>/<projectId>/<versionId>/<contentHash>.tar.zst
```

恢复前自动备份固定写入：

```text
authoring-backups/<tenantId>/<projectId>/<backupId>/<contentHash>.tar.zst
```

对象在中心 IF 对象库中使用 AES-256-GCM 应用层加密。租户、工程和工程修订作为附加认证数据；
数据库只保存对象引用、明文内容 SHA-256、密文 SHA-256、大小、schema 和 key ID，不保存快照正文或密钥。

现有运行包路径保持不变：

- `ifp-artifacts/release/<tenant>/<project>/<version>/<sha>.tar.zst`
- `ifp-artifacts/development/<tenant>/<project>/<releaseId>/<sha>.tar.zst`

## 3. 发布一致性

正式发布必须先取得工程写栅栏并生成一次不可变快照，再从该快照的 staging 工作区及领域内容构建
client、runtime 和 collector。禁止在构建期间再次读取可变工程源。版本只有在恢复快照、运行包、签名及其
相互引用全部成功后，才可在一次数据库更新中进入 `ready` 且 `restorable=true`。

## 4. 恢复接口

```http
POST /api/v1/publish/versions/{versionId}/restore-development
Content-Type: application/json

{"confirmation":"RESTORE"}
```

成功受理返回 HTTP 202 和统一响应包络，`data` 为：

```json
{"taskId":"uuid","state":"queued","stage":"queued","backupId":null,"rolledBack":false,"currentProjectRevision":"epoch-N"}
```

任务查询：

```http
GET /api/v1/publish/restore-tasks/{taskId}
```

调用者必须同时具备目标工程的 `project:write` 与 `release:publish`。服务端只接受同租户、同工程、
`ready` 且 `restorable=true` 的版本。运行中的部署及 `application_versions` 历史不得被修改。

## 5. 任务、补偿与并发

恢复任务持久记录阶段：`queued`、`staging`、`restoring_workspace`、`restoring_scenes`、
`restoring_data`、`finalizing`、`compensating`、`succeeded`、`failed`。同一工程最多一个活动恢复或正式构建。
`backupId` 不是独立可操作资源；它等于任务 ID，仅表示该任务已经持久化了任务作用域内的恢复前恢复点。

执行恢复前必须在同一写栅栏内生成完整自动备份。工作区使用持久 staging 和目录原子切换；场景与数据域
分别使用事务。任一阶段失败必须进入 `compensating` 并用备份反向恢复，只有补偿完成后才能标记 `failed`。
进程重启后依据持久阶段继续执行或补偿，不得把未知半完成状态报告为成功。

恢复期间必须停止代码工作区并使已有场景编辑会话失效；所有工程写接口必须识别恢复栅栏并拒绝并发写入。
服务端在受理时先取得持久工程栅栏，再捕获当前开发态并将其内容摘要记录为任务的
`currentProjectRevision`。版本上的 `authoringProjectRevision` 只描述历史快照，禁止将其当作当前态前置条件；
恢复旧版本不要求当前工程仍等于发布该版本时的状态。请求体不接受客户端 revision；服务端在持久 fence
内捕获当前 opaque revision，避免把历史版本 revision 错当作当前开发态并发条件。
