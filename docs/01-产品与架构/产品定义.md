# 产品定义

## 1. 文档定位

本文档定义 InduForge 的当前正式用户模型、产品分层、一级模块职责与演进边界。文中明确区分
当前已交付、当前未闭环和未来能力；未来设计不得被解释为现有功能。

## 2. 产品目标与核心价值

InduForge 是面向工业互联网场景的 AI 工程开发与运行平台，目标是贯通数据接入、2D/3D 场景
创作、前端应用开发、工程构建发布、节点运行和运维管理。

- 面向方案与实施人员：通过 AI 组织工程页面、工业场景和数据能力，缩短应用交付路径。
- 面向研发人员：保留标准 Vue/React Vite 源码和 code-server 工作台，使工程具备持续开发、预览和调试能力。
- 面向运维人员：当前以物理节点接入和工程单节点部署为正式模型；升级、回滚和多节点分布式部署
  只有在完整交付链验收后才能开放。

## 3. 产品分层

InduForge 分为四层：

- 工程开发层：`designer`、HT 2D/3D 编辑器和工程开发容器。
- 平台数据层：`datacenter`、`data_service`。
- 控制与管理层：`dev_core`、`dev_ide`。
- 运行与节点层：工程入口（内部组件 `project-gateway`）、Runtime API（目录 `runtime_api`）、
  `runtime-engine`、NodeAgent（目录 `runtime/node_agent`）、NodeAgent Front（目录
  `runtime/node_agent_front`）和工业采集进程。

工程前端是标准 Vue 或 React Vite 源码，经构建后形成静态产物。平台通过
`@induforge/runtime-sdk` 为工程源码提供鉴权、权限、数据点和 HT 场景访问能力，不在运行端解释
另一套页面模型。

## 4. 工程开发层

### 4.1 `designer`

**职责**

- 提供由 Pi Web 和定制 code-server 组成的 AI 页面开发工作台。
- 通过持续存活的 Vite Preview 与 code-server iframe 分别承载实时预览和源码开发能力。
- 展示当前工程的上下文同步状态和场景、数据点摘要。
- 提供 HT 2D 和 HT 3D 工具入口；源码通过右侧 code-server 文件视图访问。

**协作边界**

- AI 直接维护工程 Vite 源码，源码和路由是页面行为的唯一事实。
- Designer 不直接操作 HT 编辑器，只消费 HT 保存后的场景公开契约。
- Designer 不管理数据点主数据，通过工程上下文和 Runtime SDK 使用数据能力。
- Designer 不负责生产运行页面托管和运行数据处理。

### 4.2 HT 2D/3D 编辑器

- 独立完成工业场景、模型、材质和资源创作。
- 保存场景运行产物和面向页面的公开契约。
- 不向 AI 暴露 HT 私有画布结构或要求 AI 模拟编辑器操作。

### 4.3 工程开发容器

- 每个工程拥有独立容器和 `/workspace`。
- 空工程首次从 Vue/React 与 JavaScript/TypeScript 四套 Vite 官方模板中选择，之后不再套用模板。
- Pi Web、code-server 和 Vite 共享同一工作区。
- Designer 通过原生 iframe 嵌入 Pi Web、Vite Preview 和 code-server。
- 平台向容器挂载只读的数据点和场景上下文。

## 5. 平台数据层

### 5.1 `datacenter`

- 为工程提供连接、查询、数据点、协议接入、计算与调试等数据工作台能力。
- 负责数据配置界面，不承担数据域后端和页面开发职责。

### 5.2 `data_service`

- 提供平台侧和开发态的数据连接、查询、数据点、采集、计算、存储和预览数据服务。
- 为工程上下文包提供数据点公开信息。
- 与运行态数据服务共享领域契约，但不是同一部署实体。

## 6. 控制与管理层

### 6.1 `dev_core`

- 负责租户、用户、工程、权限、开发工作空间、上下文包、场景公开契约和审计。
- 产品职责包括工程前端构建、运行资源聚合、Release 签名、发布和部署；当前正式 Release Builder
  与节点交付竖链尚未闭环，未通过门禁时必须拒绝创建可部署版本。
- 不承担页面渲染、工业协议长连接或节点本地托管。

### 6.2 `dev_ide`

- 提供平台管理、工程入口、发布部署和运维视图。
- 作为 Designer、数据中心和 HT 编辑器的标签宿主；code-server 由 Designer 内部承载。
- 负责工程身份、鉴权注入、标签去重和 iframe 生命周期，不复制子应用业务功能。

## 7. 运行与节点层

### 7.1 工程入口

- 工程 Vite 源码在发布时构建为 `dist`，作为不可变前端静态产物进入 Release。
- 内部组件 Project Gateway 托管前端静态产物，并代理同一物理节点上的 Runtime API 与
  WebSocket；普通用户只看到“工程入口”。
- 浏览器通过 `@induforge/runtime-sdk` 使用运行能力，不访问中心平台和中心 S3。
- 静态文件不是独立服务、进程或部署对象，与 Runtime API 共同属于“工程入口”。

### 7.2 Runtime API（`runtime_api`）

- 提供工程运行态登录、会话、权限、数据 API、报警动作和 WebSocket。
- 加载 Release 中的运行安全快照和运行配置。
- 不执行工业协议采集和批量数据写入。

### 7.3 `runtime-engine`

- 为单个运行工程提供数据接入、计算、存储、查询和报警处理能力。
- 按工程隔离部署，不作为多个工程共享的公共数据服务。
- 内部数据处理职责统一属于用户看到的“数据运行”，当前不提供可自由拼装的计算、报警或查询
  服务项。

### 7.4 NodeAgent（`runtime/node_agent`）

- 每台物理节点独立安装一个 NodeAgent，负责接入、主机身份、本机资源、固定服务组和原生进程。
- 中心只下发工程部署、服务组、目标状态和版本引用，不向节点下发任意命令、可执行路径、参数、
  环境变量或长期中心凭据。
- 当前 Linux 节点固定具备工程入口和数据运行，可按需启用数据采集；Windows 节点固定为数据采集
  节点。用户不能自由拼装内部能力组合。
- 不解释工程页面、场景或采集配置语义。

### 7.5 NodeAgent Front（`runtime/node_agent_front`）

- 提供节点本地状态查看和受控运维操作入口。
- 不承担中心平台治理和工程开发职责。

## 8. 当前正式运行模型

用户的运维路径固定为：

```text
接入并确认物理节点
→ 选择工程和可部署的正式 Release
→ 选择一台满足条件的物理节点
→ 按需启用数据采集
→ 创建工程单节点部署
→ 通过工程入口访问页面、API 和实时连接
```

一个工程部署当前只绑定一台物理节点。工程入口与数据运行必须位于同一节点；数据采集为可选能力。
同一节点可承载多个工程，客户在部署阶段选择工程访问端口；Center 检查部署记录区间，NodeAgent
复核操作系统真实占用。资源配额和完整进程隔离仍需继续验收。

## 9. 正式 Release 链路与当前门禁

```text
AI 或 code-server 修改 Vite 工程源码
→ Designer Preview iframe 通过 Vite HMR 更新开发态预览
→ 正式 Release Builder 执行锁定依赖和 pnpm build
→ dist 打包为 client-assets.tar.zst
→ HT 场景与运行配置打包为 runtime-artifact.tar.zst
→ 生成、签名并发布不可变 Release
→ NodeAgent 下载、验签、解包并原子激活目标 Release
→ 启动工程入口、数据运行和可选数据采集
→ 通过健康检查后确认当前运行版本
```

上面是正式交付必须达到的完整链路，不是当前完成度声明。当前已有正式 Release Schema、元数据
校验、节点接入与本地 Release 安装基础原语；Builder、中心到 Agent 的下载/Binding 接线、信任根与
Secret 装配、进程切换及真实物理机端到端验收仍未闭环。因此：

- 源码快照和开发预览不得标记为可部署 Release；
- Builder 或节点交付能力未启用时，发布、部署、升级和回滚写接口必须 fail-closed；
- 当前“服务运行中”不能单独证明用户所选 Release 已成功安装；
- 升级和回滚尚未交付，UI/API 不得显示为可用功能。

页面中的数据点和场景调用必须通过 Runtime SDK，开发态和运行态使用同一调用语义，只切换服务端
连接和授权上下文。

## 10. 未来多节点分布式部署（未交付）

未来一个工程可以选择多台物理节点，并由产品展示节点拓扑、角色分配、版本一致性、故障状态和
切换结果。实现必须先冻结数据角色分片、唯一 owner、排空、检查点、故障转移和一致的
Release/Secret 选择，再开放 UI/API。

节点内部未来可以选择 K3s、Pod、Namespace、site-controller、infrastructure-controller 或其他
编排技术，但这些只属于可替换内部实现。用户仍只管理物理节点和工程分布式部署，不接触内部编排
对象、凭据或控制器状态。

## 11. 产品边界

- 平台聚焦工业应用开发、交付和运行，不以通用办公流程平台为目标。
- 中心平台不进入物理节点上的工程实时运行链路。
- 工程前端不携带模型密钥、开发上下文或 Pi 会话状态。
- HT 场景和资源属于运行资源包，不重复复制到工程前端静态产物。
- 开发态与运行态数据域共享契约，但不共享部署实例。
- 当前多个物理节点不代表一个分布式部署，也不得宣传为高可用。
