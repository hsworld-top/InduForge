# IDE 子应用宿主化通信改造设计

## 1. 背景与目标

当前 `dev_ide` 通过 iframe 打开 `designer` 与 `datacenter`，但子应用启动依赖 URL 参数传递以下运行时上下文：

- `token`
- `refreshToken`
- `pid`
- `tenant`
- `theme`
- `locale`

这套方式存在三个主要问题：

- 敏感信息暴露在地址栏、历史记录、日志和截图中，安全边界弱。
- 子应用正式入口与独立调试入口未区分，用户直接访问子应用地址时行为不稳定。
- 宿主态上下文和子应用内部状态耦合在 URL 上，扩展与排障成本偏高。

本次改造目标是：

- 将正式入口的上下文传递从 URL 参数切换为 `postMessage` bootstrap 握手。
- 将 `designer`、`datacenter` 正式入口收口为仅允许 `dev_ide` 宿主打开。
- 保留专用调试入口，支持开发联调和独立排障。
- 保持子应用现有请求封装、接口访问方式与 token 自动续租机制不被整体推翻。

## 2. 设计原则

- 只改“入口协议”和“宿主同步机制”，不改业务 API 通信模式。
- `postMessage` 仅用于启动注入和少量运行时同步，不扩展为高频业务消息总线。
- 正式入口和调试入口必须物理分离，避免通过 query 参数混合模式。
- 优先复用 `designer`、`datacenter` 现有 `Storage`、路由守卫、请求封装和刷新 token 逻辑。
- 安全校验优先于兼容便利，禁止继续使用 `postMessage('*')` 作为长期方案。
- 改造按双轨兼容逐步切换，避免一次性切断旧链路。

## 3. 当前实现现状

### 3.1 `dev_ide`

- `EmbeddedApp.vue` 通过 iframe 挂载子应用。
- `appUrl.js` 当前会拼接 `token`、`refreshToken`、`pid`、`tenant`、`theme`、`locale` 到子应用 URL。
- `Dashboard.vue` 已具备对嵌入 iframe 广播主题、语言的能力。
- `embeddedIframeSync.js` 已存在基础的消息广播辅助方法，但目标 origin 仍为 `'*'`。

### 3.2 `designer`

- 已具备主题、语言的 `postMessage` 同步与来源校验基础。
- 路由守卫仍会从 URL 中消费 `token`、`refreshToken`、`pid`、`tenant`、`theme`、`locale`。
- 请求封装内已实现 `401 -> refresh -> 重放请求`。
- refresh 失败时会向父窗口发送 `AUTH_EXPIRED`。

### 3.3 `datacenter`

- 路由守卫当前会从 URL 中消费 `token`、`refreshToken`、`theme`、`pid`、`tenant`。
- 请求封装内已实现独立的 refresh token 逻辑。
- 已存在 `messageHandler`，但消息来源校验较宽松，`postMessage` 目标 origin 也仍为 `'*'`。

## 4. 目标架构

### 4.1 入口形态

- `dev_ide` 继续作为宿主，维持 iframe 承载模式。
- 正式入口保持为：
  - `/designer/`
  - `/datacenter/`
- 新增专用调试入口：
  - `/designer/debug`
  - `/datacenter/debug`

### 4.2 模式划分

子应用统一存在两种运行模式：

- 宿主模式：仅在 iframe 内由 `dev_ide` 打开，依赖 bootstrap 消息获取完整上下文。
- 调试模式：仅通过 `/debug` 路由独立访问，允许本地独立调试和手工注入最小上下文。

正式入口不再承担独立访问职责。

## 5. 入口与重定向契约

### 5.1 `dev_ide` iframe 地址

`dev_ide` 打开子应用时，iframe 地址默认保留纯净入口，并允许附带一个不敏感的恢复标识：

- `designer` -> `/designer/?handoff=<opaque-id>`
- `datacenter` -> `/datacenter/?handoff=<opaque-id>`

正式入口 URL 不再拼接以下敏感或宿主态参数：

- `token`
- `refreshToken`
- `theme`
- `locale`
- `pid`
- `tenant`

其中 `handoff` 为短期有效的 opaque id，只用于恢复“这个子应用页面原本属于哪个 IDE 标签页/工程上下文”，不直接暴露工程敏感信息。

如果后续存在纯页面定位类信息，例如 `pageId`，也应优先通过 bootstrap 下发；仅在确有必要支持浏览器回退/深链时，才允许与 `handoff` 一样作为非敏感参数保留。

### 5.2 子应用正式入口行为

子应用启动后先判断当前模式：

- 命中 `/debug` 路由：进入调试模式。
- 非 `/debug` 且 `window.parent === window`：视为用户直接访问正式入口，立即重定向回 `dev_ide`。
- 非 `/debug` 且 `window.parent !== window`：进入宿主模式，等待 bootstrap。

### 5.3 直接访问正式入口的回跳规则

若用户直接访问 `/designer/` 或 `/datacenter/`：

- 允许读取并透传非敏感恢复参数，例如 `handoff`、`pageId`。
- 禁止透传任何 token。
- 统一重定向到 `dev_ide`，由 `dev_ide` 决定打开对应标签页或回到工程列表。

如果 `handoff` 可解析，则恢复到对应的 `appType/projectId/tabKey`。

如果 `handoff` 缺失、过期或无法解析，则回到 `dev_ide` 默认首页，不允许子应用在正式入口下独立运行。

### 5.4 iframe 内刷新与脱离宿主后的刷新

需要显式区分两类刷新场景：

- iframe 仍嵌在 `dev_ide` 内部时刷新：页面重新加载后继续走 bootstrap，请求宿主重新注入上下文。
- iframe 被浏览器“在新标签页中打开”或被复制正式入口地址后，顶层页面刷新：由于 `window.parent === window`，正式入口不继续独立运行，而是依赖 `handoff` 重定向回 `dev_ide` 恢复原标签页。

这意味着本次设计不是简单禁止“顶层访问正式入口”，而是要保证“从 IDE 派生出来的正式入口在脱离宿主后仍能安全回附到 IDE”。

## 6. Bootstrap 握手协议

### 6.1 设计目标

bootstrap 协议负责解决以下问题：

- 子应用初次加载时如何获得鉴权和工程上下文。
- iframe 刷新或重建后如何无状态恢复。
- 宿主如何向不同 iframe 精确下发各自上下文，避免工程串线。

### 6.2 消息方向

启动流程采用“子应用请求，宿主响应”的双向握手：

1. 子应用加载正式入口。
2. 子应用进入 `waiting-for-host` 状态并发送 `APP_BOOTSTRAP_REQUEST`。
3. `dev_ide` 校验来源后返回 `APP_BOOTSTRAP_RESPONSE`。
4. 子应用写入本地存储并继续正常初始化。

### 6.3 `APP_BOOTSTRAP_REQUEST`

子应用发送给父窗口的请求体包含：

- `type: 'APP_BOOTSTRAP_REQUEST'`
- `app`: `designer` 或 `datacenter`
- `requestId`: 本次握手唯一 ID
- `handoff`
- `requestedPath`: 当前路由路径
- `requestedQuery`: 非敏感查询参数快照

该请求不携带 token 等敏感数据。

### 6.4 `APP_BOOTSTRAP_RESPONSE`

宿主回包包含：

- `type: 'APP_BOOTSTRAP_RESPONSE'`
- `app`
- `requestId`
- `handoff`
- `projectId`
- `tenantId`
- `token`
- `refreshToken`
- `theme`
- `locale`
- `debug: false`

如后续存在更多正式宿主态字段，例如用户信息摘要，也应由该响应统一注入，而不是重新回到 URL 传参。

### 6.5 幂等与重试

为避免消息时序问题，协议必须满足以下约束：

- 子应用在 `waiting-for-host` 状态下带超时重试发送 `APP_BOOTSTRAP_REQUEST`。
- 宿主在 iframe 创建前即注册消息监听。
- 相同 `requestId` 的响应只消费一次。
- iframe 刷新或重新挂载时允许再次获取完整 bootstrap 上下文。

## 7. 子应用初始化与状态落地

### 7.1 正式宿主模式

子应用在收到 `APP_BOOTSTRAP_RESPONSE` 后，按现有逻辑落地到本地 `Storage`：

- `token`
- `refreshToken`
- `tenantId`
- `projectId`
- `theme`
- `locale`

落地完成后再继续：

- 路由守卫鉴权
- 工程加载
- 页面渲染
- API 请求

这意味着本次改造复用现有 `request` 和 `router`，只替换“上下文来源”，不替换“应用内部状态读取方式”。

### 7.2 调试模式

`/debug` 路由允许独立访问，但只用于开发联调，不作为正式用户入口。调试模式允许以下能力：

- 从本地 `Storage` 读取 token、refresh token、主题和语言。
- 允许通过明确的调试注入方式指定 `projectId`、`tenantId`。
- 允许显示更明确的缺参提示，便于本地开发人员排错。

调试模式不要求依赖父窗口 bootstrap。

## 8. 运行时同步协议

bootstrap 之外，宿主仅承担低频运行时同步职责：

- `THEME_UPDATE`
- `LOCALE_UPDATE`
- `AUTH_EXPIRED`
- `AUTH_REFRESHED`

其中：

- `THEME_UPDATE`：IDE 切换主题时同步所有相关 iframe。
- `LOCALE_UPDATE`：IDE 切换语言时同步对应 iframe。
- `AUTH_EXPIRED`：子应用 refresh 失败，通知 IDE 统一登出和跳转。
- `AUTH_REFRESHED`：子应用 refresh 成功后，将最新 token 状态回传给 IDE。

### 8.1 不纳入本次范围的消息

以下能力明确不纳入本次设计：

- 查询执行改为通过 IDE 转发
- 画布数据、数据查询结果通过消息总线流转
- 宿主代理全部 API 请求

原因是这些高频消息会显著增加复杂度、调试成本和宿主单点风险。

## 9. iframe 内 token 续租策略

### 9.1 结论

第一阶段保留 `designer`、`datacenter` 各自现有的 refresh token 逻辑，不迁移到 `dev_ide` 集中续租。

### 9.2 原因

- 现有逻辑已在线路上存在，复用成本最低。
- 子应用 refresh 路径最短，不依赖父窗口中转。
- iframe 单独刷新后，仍可依靠 bootstrap + 本地续租恢复。
- 避免第一阶段把宿主变成统一鉴权中心，导致耦合和故障半径扩大。

### 9.3 续租事件回传

为了避免 `dev_ide` 持有旧 token，并在后续新开标签页时继续注入旧值，子应用在 refresh 成功后需要回传：

- `type: 'AUTH_REFRESHED'`
- `app`
- `token`
- `refreshToken`（如后端返回新值）

`dev_ide` 收到后更新自身缓存。第一阶段可只更新宿主缓存，不强制立即广播给其他 iframe。

### 9.4 续租失败处理

子应用 refresh 失败后发送 `AUTH_EXPIRED` 给 `dev_ide`，由宿主统一执行：

- 清理登录态
- 跳转登录页
- 必要时广播通知其他嵌入子应用停止继续操作

## 10. 安全边界

### 10.1 来源校验

所有消息必须同时校验：

- `event.origin` 是否在白名单中
- `event.source` 是否为预期窗口对象

校验规则：

- 子应用只接受 `window.parent` 且 origin 命中 IDE 白名单的消息。
- `dev_ide` 只接受来自已注册 iframe 的 `contentWindow` 消息。

### 10.2 目标 origin

所有 `postMessage` 必须替换当前 `'*'` 的用法，改为显式目标 origin。

### 10.3 敏感信息边界

正式模式下禁止以下信息进入 URL：

- access token
- refresh token
- 用户身份敏感字段

敏感上下文只允许通过 bootstrap 消息传递和本地存储复用。

`handoff` 虽允许进入 URL，但必须满足：

- 为随机 opaque id，不可直接反推出 `projectId`、`tenantId`、token。
- 必须带过期时间或可回收机制。
- 仅用于恢复正式入口与 IDE 标签页之间的映射关系。

## 11. 宿主侧 iframe 注册表

`dev_ide` 需要维护 iframe 注册信息，用于精确回包和后续同步。建议最小字段包括：

- `appType`
- `projectId`
- `tenantId`
- `handoff`
- `origin`
- `contentWindow`
- `tabKey`

该注册表用于解决：

- 不同工程的多标签页 iframe 不能串上下文。
- 主题、语言广播要能定位到目标 iframe。
- `AUTH_EXPIRED`、`AUTH_REFRESHED` 要能回写到正确的宿主状态。

除 iframe 注册表外，还需要维护 `handoff` 映射表。建议最小字段包括：

- `handoff`
- `appType`
- `projectId`
- `tenantId`
- `tabKey`
- `issuedAt`
- `expiresAt`

该映射表用于支持以下场景：

- 浏览器将 iframe 正式入口单独打开为新标签页。
- 顶层标签页刷新后重新附着回 IDE。
- 用户复制正式入口地址后，IDE 至少能尝试恢复原始标签上下文。

## 12. 迁移策略

### 12.1 第一步：双轨兼容

- `dev_ide` 新增 bootstrap 协议，但临时保留旧 URL 注入能力。
- `designer`、`datacenter` 优先消费 bootstrap；若未拿到，再兼容旧 URL 逻辑。
- 目标是先验证消息握手与时序稳定性。

### 12.2 第二步：正式收口

- `dev_ide` 停止在 iframe URL 中拼接 token、refresh token、theme、locale、pid、tenant。
- `designer`、`datacenter` 删除正式入口对 URL 注入的依赖。
- 仅 `/debug` 路由保留独立调试模式。

## 13. 实施顺序

建议按以下顺序落地：

1. 抽取共享消息协议定义与校验辅助逻辑。
2. 改 `dev_ide`：
  - iframe 地址纯净化
  - iframe 注册表
  - bootstrap 监听与响应
3. 改 `designer`：
  - 先实现宿主模式/调试模式分流
  - 接入 bootstrap
  - 保留现有 refresh 逻辑并补 `AUTH_REFRESHED`
4. 改 `datacenter`：
  - 同步接入 bootstrap
  - 收紧 `messageHandler` 的来源校验
  - 保留现有 refresh 逻辑并补 `AUTH_REFRESHED`
5. 清理兼容分支与旧测试。

## 14. 风险与回归重点

### 14.1 主要风险

- bootstrap 消息时序不稳定导致首屏空白或卡在等待态。
- 多个 iframe 同时打开不同工程时，宿主注册表映射错误导致工程串线。
- `handoff` 失效策略不合理，导致单独标签页刷新后无法恢复或恢复到错误标签。
- 某个 iframe refresh 成功但 IDE 未同步最新 token，导致新开标签页注入旧 token。
- 旧 URL 兼容分支清理过早，造成线上回退困难。

### 14.2 必测场景

- 从 `dev_ide` 打开 `designer`，首屏正常加载。
- 从 `dev_ide` 打开 `datacenter`，首屏正常加载。
- 刷新 iframe 后上下文可恢复。
- 将 iframe 页面单独打开为浏览器标签页后，会回跳 IDE 并恢复到对应工程标签。
- 脱离宿主的正式入口页面再次刷新后，仍能依赖 `handoff` 回附到 IDE。
- 同时打开多个不同工程的 `designer/datacenter` 标签页，不出现串工程。
- IDE 切换主题、语言，子应用同步正确。
- 子应用 refresh 成功后，IDE 能更新缓存。
- 子应用 refresh 失败后，IDE 能统一登出。
- 用户直接访问 `/designer/`、`/datacenter/` 时会回跳 IDE。
- 用户直接访问 `/designer/debug`、`/datacenter/debug` 时可用于独立调试。

## 15. 非目标

本次设计明确不处理以下内容：

- 将 `designer`、`datacenter` 改造为 IDE 内部同构子路由应用
- 将全部 API 请求统一改为由 `dev_ide` 代理
- 合并 `designer` 与 `datacenter` 的全部 token 刷新实现
- 顺手重构现有业务 store、页面结构或接口契约

## 16. 设计结论

本次改造采用“宿主化正式入口 + 专用调试入口 + bootstrap 握手注入 + iframe 内保留独立续租”的方案。

该方案的核心价值是：

- 去除 URL 中的敏感上下文，提升稳定性与安全边界。
- 保持现有业务请求路径和刷新 token 机制，控制改造成本。
- 通过专用 `/debug` 路由保留开发联调能力，同时收紧正式用户入口。
- 通过分阶段兼容迁移降低切换风险。
